# 模块化单体 + MyBatis：通用设计约束

本文件约束从 FM 到实现任务的映射，不提供行业默认业务。规范来源见 [upstream.md](upstream.md)，工作单元和身份算法见 [slicing-policy.md](slicing-policy.md)。

## 1. 一个部署单元，明确业务模块

固定采用模块化单体：后端是统一构建和发布的应用，各模块在应用实例内通过 Java 公开契约协作。运行多个应用副本不改变模块的进程内边界；不为 Context 自动创建服务、RPC 或消息基础设施。

业务模块由行为内聚性、数据所有权和变更原因确定。domain/api/persistent 是技术分层，不是业务模块清单；FM Context 与业务模块需要有来源的映射，不要求一一对应。组合根与实现库形式见 [backend-layout.md](backend-layout.md)。

每项受影响的设计必须明确：

- **业务拥有者**：哪些源 Context、实体、根集合和规则属于该模块，以及映射/合并/拆分理由。
- **公开契约**：允许其他模块调用哪些业务能力、查询、身份或不可变值；模块内部实体实现、Mapper 和可变状态不随意泄漏。
- **数据所有权**：表、迁移和写入入口的唯一拥有者。共用数据库不表示可跨模块任意 JOIN、读写私有表或直接访问 Mapper；需要联合查询时通过已明确的查询契约或拥有者提供的投影。
- **依赖方向**：模块只依赖声明的公开契约；用包可见性、构建依赖和架构测试限制内部访问与依赖环。必要时提取有业务意义的窄契约，不增加万能 common 包。
- **本地一致性**：按实际业务操作说明事务入口、参与者、数据源/事务管理器与回滚结果，不由同进程或同库直接推导大事务。

缺少数据库引擎或模块接口时只阻塞相应工作；纯进程内实现不需要先确定远程拓扑。外部系统与独立部署必须有明确需求和设计依据，不能从业务上的外部 Context、Evidence Role 或跨上下文关系推导联网调用。

## 2. 共享实体先行，业务拥有者不变

从源关系和场景识别跨上下文共用的稳定主体、Thing、ID 和值类型。按首个可验收场景所需最小契约安排前置工作，不先建设完整用户、目录或其他 CRUD 平台。

主体是一份稳定身份，其在不同实例中的 Role 不复制成不同主体。被不同合同引用的标的仍由自己的领域拥有；共享通过明确的身份、值与能力契约实现，不把所有实体挪到 common 包或开放其他模块的内部可变对象。

FM 声明 ID 是模型类型身份，不自动等于领域实例主键。确定 Entity/Description/值对象的选择要依据业务身份、属性和生命周期，不机械地把每个节点生成实体表。

## 3. Context、根集合与成员实例

Context 表达边界；`rootRefs` 指向入口集合的成员类型；根集合负责定位及有依据的登记/创建。单个成员拥有身份、不可变描述、关联和业务行为。

- 根集合不是普通 List，也不是万能 Repository/Service。
- 根创建行为允许有业务语义；实体拥有的关联写能力仍应保持内部使用。
- 子履约按源父子和关系从实际实例进入，不自行创建另一套全局 CRUD 根。
- 外部上下文可以有证据导航而没有本平台办理 API。没有合同的领域模型不补造履约。

## 4. 关联契约和统一持久化

| 语义                         | 契约选择                  |
| ---------------------------- | ------------------------- |
| 无独立身份                   | 不可变 Description/值对象 |
| 只需记录另一身份             | 强类型 ID / Ref           |
| 保证一个可导航成员           | HasOne                    |
| 零到多个成员                 | HasMany                   |
| 零或一个有意义               | 具名 Optional 读取关联    |
| 关系有自身身份/属性/生命周期 | 关系实体后再关联          |

可变关联遵循 `Owner.field → Owner.WideInterface → OwnerField adapter → Mapper`。宽接口类型供适配器实现，宽字段 private，公开 getter 只返回窄接口；只读关联不虚构写能力。

所有本系统持久化实现使用 MyBatis。内存 Fake 验证领域契约，生产适配器验证实际 SQL、加载、hydrate、批量/分页、并发及错误转换。关联拥有者、加载方式和表结构是不同决定；FM 一条关系不必对应一张表，业务包含关系不必对应一个大事务。

仅当来源明确要求与第三方系统交互时才规划协议适配器；外部凭证也可能通过人工登记或已有本地记录取得。协议、地址、验签与失败处理不能由上下文名称猜测，也不替换本系统 MyBatis 持久化栈。

## 5. 行为与两种 Role

```text
Jersey Resource
  → 根集合
  → 实体 / 绑定实际实例的 ContextRole
  → 拥有者内部的关联契约
  → MyBatis 或必要的外部协议适配器
```

业务规则不能进入 Resource、Mapper、技术事务包装器或负责拼接 Repository 的 Service/Handler。bootstrap 装配；领域不依赖 Spring、Jersey、Jackson、MyBatis。

- 主体角色使用 `ContextRole<Actor, Context>` / `ContextSwitcher`，核验可信 Actor、实例归属与代表权限。角色名不是认证证据。
- 证明角色是消费方能力接口或原凭证包装视图；不生成新凭证、独立签发时刻或用户权限。不把一种具体资金/其他结果的责任转移给消费者。
- 实现了证明接口不表示证明合格；匹配、数量、时间、来源与可见性由源规则判断。
- 按变化点定义消费契约，集成适配层连接玩家，消费领域不直接依赖每个外部实现包。

## 6. 事实、时间和规则不改写

每项关键值明确直接记录、引用、确定性派生或未知来源。模型中的字段与代码赋值来源不可混为一谈。

- 冻结的合同事实不被动态目录覆盖；保存已签合同不代表执行签署。
- Request/RFP/Proposal 保留 started_at/expired_at；Contract 用 signed_at；Confirmation 用 confirmed_at；补充凭证用 created_at。不为时刻凭证补区间。
- 业务签署/扣减/到账/提供时刻不同于建档、回调到达和服务器当前时间；原事件时刻不同于记录形成时刻。
- 凭证按实际业务约束追加，不以状态覆盖抹去迟到、冲正或历史违约。结果存在、HTTP 成功、按时完成和当前资格分别判断。
- 幂等通知不等于两个不同结果是同一事实。规则的 exists、精确数量、聚合、边界闭合、币种及实例匹配均保留。
- Java 或 CEL 执行方案需要实现映射与测试依据；程序提取 Rule 工作单元不证明规则已执行。

## 7. 事务、幂等和实时权限

本地事务覆盖有明确依据的原子领域操作。事务协调不能替代行为拥有者：若确需多个业务模块共同提交，应通过各自公开契约调用，明确共同事务管理器、参与操作和失败回滚；不能靠直接写其他模块的表实现。多数据源或独立事务不自动原子提交。

并发唯一性、版本/锁、原子变更和证据追加需要真实数据库验证；单体也可能面对并发请求或多个应用副本，顺序 Fake 不能证明并发安全。

仅对已确认的远程调用规划超时、重试、幂等和结果登记。本地事务不覆盖远程副作用；没有业务依据不增加补偿义务、罚息或自动逆操作。未要求远程集成时，不生成对应任务来补齐技术清单。

授权在实际操作点验证，不仅控制页面或 HAL 链接展示。受权益变化影响的查询按源规则的实际判断时点重新检查，旧链接不能天然授予权限。

## 8. 切片与证据

从具体场景定义业务增量，再把所需单元分配给有明确拥有者和操作的工作组。相关规则合为一个领域操作任务时保留全部检查；生产关联、API 投影、真实集成验收依赖它，不重复实现规则。

implementation 任务包含实现、自动回归和验收；verify 任务定位并复跑已有行为。复用工作应有既有代码/测试来源和真实重跑；没有命令或环境就列准备依赖/缺口，不制造通过结果。

Q1–Q4 按目的区分，规划领域规则、模块公开接口、禁止依赖/内部访问、表与迁移归属、本地事务回滚、真实数据库并发、身份隔离、HTTP 结果和适用人工评估。存在已确认外部调用时另补故障检查；没有该依赖不强制远程测试。既有质量命令按实际脚本读取，不假定 lint 覆盖后端。

计算 key、单元唯一归属和 API 覆盖不能替代语义审查：特别检查同义设计 ID、过大任务、错误拥有者、事务跨界以及为消除重复而合并了不同时间口径。
