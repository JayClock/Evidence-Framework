# 领域语言进入日常表达

以下均为合成输入与表达样例，不是项目业务事实，不授权编辑业务文件。只演示同一概念在不同工作中如何保持同一叫法。

## 别名输入，规范名称输出

假设词汇入口中的规范名称是“到账证明”，`aliases` 包含“银行小票”。用户说：“银行小票已经收到，继续核对。”

理解用户说的是到账证明，后续表达保持一致：

- 访谈承接：已收到到账证明，接下来核对它对应哪一笔付款请求。
- 需求故事标题：核对到账证明。
- 任务标题：校验到账证明与付款请求的匹配。
- 测试说明：到账证明与付款请求不匹配时拒绝确认。
- 交接：下一轮继续核对到账证明的匹配依据。

不在自己的叙述中交替使用银行小票、收款单、支付凭证。引用用户原话时保留原文；如果收款单指另一种业务对象，先区分含义，不按相近叫法合并。

## 同名异义，先定位上下文

合成词汇入口中，“完成”在付款上下文表示到账证明满足付款请求的完成规则，在交稿上下文表示收稿回执满足交稿请求的完成规则。

用户只说“这次完成了”，而当前材料同时涉及两项履约时，先定位是在说付款完成还是交稿完成。明确上下文后沿用相应概念，不把一个完成结论扩展到另一项履约。

## 只读讨论，使用不等于保存

用户说：“沿用已有词汇解释，今天只聊不落盘。”

读取相关条目并用规范名称解释，不更新词汇表、FM 或 API。需要指出叫法冲突时说明具体差异，不在交接中声称术语已保存，也不创建 Markdown 词典。

## 缺词或模型定义缺失，不自行定论

用户提出“有效到账”，但材料尚未说明它与已有“到账证明”的区别。将差异作为必要未知交给当前允许的澄清分支，不因它听起来更精确就选为规范名称；没有保存授权时，说明术语建议未保存。

若相关 model 条目指向的 FM 目标没有业务说明，报告目标定义缺口，不拿名称代替定义，也不在词汇表补一份。目标已有明确名称与含义时直接复用，是否更正仍由模型编辑权限决定。
