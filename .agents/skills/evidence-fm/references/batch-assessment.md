# 按事实依赖评估本批次

评估是 Agent 对已有业务依据的解释，不是人工回答、批准或范围排除。采用普通 Markdown 即可，不依赖宿主状态版本或专用提交工具。

## 评估步骤

1. 读取全部与本次目标相关的历史发现、现有模型、来源、问题和案例。保存来源版本或必要摘录；来源变化先复核其消费者，不拿旧摘要当新事实。
2. 列出各上下文本批次的具体职责、已知事实和剩余未知。Context 是组织知识的单位，不是不可拆分的包。
3. 标识职责真正需要的结构、来源及决策事实，并沿依赖检查。将未解决问题映射到实际受影响事实，不笼统标成“全局不能建模”。
4. 标记 ready、support、pending，保留正常、边界和异常回放的预期依据及缺口。
5. 输出事实／来源到模型 ID 的对应关系以及未纳入原因；编辑后核对实际 YAML 和引用是否一致。

| 类型         | 必要事实的判断方向                                                 |
| ------------ | ------------------------------------------------------------------ |
| Domain       | 当前对象的业务身份、所需结构和相关规则，不要求整个领域生命周期完整 |
| Pre-contract | 当前真实双方、凭证、有效性、相关回应及规则，不要求已签合同         |
| Contract     | 身份、双方及本次消费的约定，不要求全部条款完整                     |
| Fulfillment  | 父合同相关双方与承诺、请求、期限确定依据、完成证明和判断规则       |

## 支撑投影与阻塞

一个未完成的上下文仍可提供有来源的身份或金额；只能纳入实际需要且已知的部分，不把整个上下文宣称完成。引用要求必须能在 FM 中合法表达，结构不合法就明确当前模型未通过校验。

假设来源已明确付款请求、期限及支付机构的扣款证明，但退款后的赔付责任尚未明确：若当前付款判断不依赖那条赔付规则，付款可以 ready，赔付 pending。若连本次付款金额依据也未知，则不能只保留一个任意金额输入而宣称付款完成。

上述例子不是业务默认规则。每项纳入都须有本项目依据；不允许为让主流程通过校验省略它本来依赖的规则。已有正式事实也不能因为“本次 pending”被静默删除：保留有效部分，来源失效的部分显式提出撤回及依赖影响，交由本次授权范围处理。

## 未决项处理

跳过、未知、停止不是来源。已有事实完整覆盖历史问题时可链接原文和推导解决，不造回答；真实冲突不能靠 Agent 选取方便的一方消除。用户未授权询问时仅保留缺口。

没有可纳入职责也保存真实评估。FM 表达能力缺口保留给后续设计和验证，但缺失业务规则不交下游自行决定。
