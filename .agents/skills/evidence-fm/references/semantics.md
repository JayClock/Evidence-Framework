# FM 对象含义与协作边界

本页解释建模选择，不复制 JSON 字段、枚举或必填项。结构直接读取 [Schema 入口](format.md#结构契约)，机器可检查的跨对象约束定位到下列校验函数。业务事实仍来自实际材料与人类决定，代码只证明已实现的检查能力。

先按 [业务分析](business-analysis.md) 理解现金权责、目标—实际对比、实际约定与责任双方，再作对象选择。技术组件、目录和页面分组不构成业务边界；纯领域或独立协商不补造合同。

## 上下文与履约

上下文表达合同责任、领域知识或合同前协商的边界；履约是合同内部的一项权利义务，不是新的上下文，也不自动对应软件模块、事务或部署单元。

上下文不是预先建立的空容器。合同上下文以唯一的本地 Contract 为根并共同维护双方角色；领域上下文以实际本地业务对象为根（Thing、领域参与身份或业务记录），不能用自身、其他 Context、Fulfillment 或未展开协作角色充当根；协商上下文至少已有本地邀请、方案或回应凭证，角色或常量规则本身不证明协商存在。这些均属于一致性约束，由 [validate_context_roots](../scripts/fm_model.py) 检查，不推迟到范围结束。尚无履约、部分属性或时间未明与空上下文不同，不要求为此补造履约、主体或完成规则。

上下文归属、子上下文与履约归属分别表达不同关系，不能互相替代。入口指向业务上下文，不把当前展示的履约切片冒充合同范围。机器约束见 [validate_manifest](../scripts/fm_model.py)、[validate_entities](../scripts/fm_model.py) 和 [validate_fulfillment_ref](../scripts/fm_model.py)。

## 责任身份与稳定主体

角色表示当前上下文中的身份，主体表示跨上下文仍保持同一性的个人、组织或领域事物。客户本人、客户档案和客户的合同身份不是同一个对象；具体分析按 [领域建模](domain-modeling.md)。

合同凭证绑定责任双方，其余合同凭证复用所属合同的一方承担责任，不能按履约或阶段复制合同角色。经办人、上传人和证明提供方不替代责任方；实际主体未知不补玩家，同名也不证明身份相同。角色扮演只表达有依据的对应，不授予未约定的全部操作权限。

责任与角色归属的检查分别见 [validate_evidence_responsibility](../scripts/fm_model.py)、[validate_party_role_owner](../scripts/fm_model.py)；扮演端点见 [validate_relationships](../scripts/fm_model.py)。最小保存单元由 [责任方法](responsibility-closure.md) 维护。

## 领域复用的角色选择

选择取决于当前抽象的对象，不是公司内外或部署位置；识别领域边界不自动创建 Domain Context。

- 抽象需要什么专业能力时使用领域能力角色，不限定实现系统。
- 只消费既有系统或协作者时表达系统边界；图示的 `3rd-system` 对应当前 Schema 的系统协作角色，不是新类型。
- 确需展开内部知识且有授权时才建立领域上下文；已展开上下文的角色化协作用上下文角色。

角色不是结果凭证。能力声明、系统回调或方案成熟度不能证明履约完成；具体字段与合法端点分别读取 [Entity Schema](../schemas/entity.schema.json) 和 [validate_relationships](../scripts/fm_model.py)。

## 未澄清合同与证明插槽

当前合同确实依赖另一未澄清合同的协作边界时，用 Context Role 保留所需能力及未知；无关联合同只留在交接。不创建虚构合同、内部履约或玩家，也不以外部处理转移当前合同责任。后续依据充分且获授权时接入真实上下文，保留角色身份。

Context Role 不代替 Evidence Role，也不代表结果已经存在。Evidence Role 是跨上下文的开放证明插槽：消费方声明采信约定，具体结果保留提供方上下文、责任与业务时间。插槽自身不签发凭证实例；业务规则必须解析实际玩家，不能凭字段相同接受无关凭证。

无需替换证明方式时可直接引用有依据的外部确定结果，不机械增加插槽。同合同内的不同履约不构成跨上下文，不借证明角色中转。具体允许的引用和扮演组合以 [validate_relationships](../scripts/fm_model.py) 检查，使用对照见 [结构样例](../examples/structural-contrasts.md) 与 [合同级样例](../examples/contract-batch.md)。必要证明不明仍是交付缺口，角色不能补齐它。

## 请求、结果与业务时间

请求记录要求及适用时段，确认记录完成或部分完成结果，补充凭证提供采信依据；确认不默认人工审批，也不自动结束整项责任。同类多次结果用不同实例，不按批次复制类型；同合同共享确认保留唯一形成归属，各请求独立判断。

类型引用按消费方指向依据；实例依赖指向当时已经形成的具体凭证。引用不证明实例存在，也不单独规定时间先后。签约、生效、确认、补录、回调和入库时间各有含义，不能相互替代。

时间属性契约直接读 [EVIDENCE_TIME_ATTRIBUTES](../scripts/fm_model.py) 与 [validate_evidence_times](../scripts/fm_model.py)，属性结构读 [Entity Schema](../schemas/entity.schema.json)。这里区分渐进保存与范围完整性，不生成默认日期或期限；是否继续追溯业务口径按 [来源方法](provenance.md) 决定。

运行时凭证只追加；取消、更正、退款、冲正与赔偿保留原事实，用新增凭证及实际新义务表达。这不表示领域对象的状态永不变化，实例执行与时间线见 [追溯与模拟](traceability-and-simulation.md)。

## 完成、异常与协商

履约是已经识别的请求—确认交互的包裹，不是先建的空容器。每项履约必须关联恰好一个请求及至少一个有效结果端；缺任一端即为一致性错误，不推迟到范围完整性检查。只有单端的有据凭证可以暂不包裹，范围结束前仍须处理其必要关联。结果端可以是明确归属的确认角色；请求引用的普通支撑证明角色不自动成为结果端。履约的请求、结果和完成规则由各成员归属及引用共同组成，不在履约上复制成员索引或计算逻辑。部分确认、迟到结果与整体完成分别判断，异常新义务仍回到业务分析；完整结构和共享确认关联由 [validate_fulfillments](../scripts/fm_model.py) 检查，计算表达见 [CEL 方法](cel-rules.md)。

合同前的邀请、方案和回应按实际出现表达，不强制完整询报价流水线；合同只追溯实际接受的方案，不虚构未来合同或履约。形成顺序不等于依据引用方向。

关系基数声明只说明已知数量约束，不自动表达拥有权或级联操作。静态检查见 [validate_relationship_cardinality](../scripts/fm_model.py)；当前没有通用关系实例，不能声称运行验证了实例数量。

## 一致性不是范围结束

[validate_model](../scripts/fm_model.py) 检查当前已表达内容；[completeness_gaps](../scripts/fm_scope.py) 区分范围仍缺什么。可暂缺内容不等于允许错误引用、矛盾类型或依赖环。机器不能证明责任全部发现、人类确认有效或业务已批准。

保存、责任终点、范围结束及人类确认只由 [责任方法](responsibility-closure.md) 维护；实际命令和检查结果只由 [校验纪律](validation.md) 维护。来源或语义更正后核对受影响的检查与下游，不通过改分类、删场景或缩范围制造完整。
