# 业务分析：从约定骨架展开证据

本页唯一维护业务结构的发现方法，供访谈和输入复核读取。合同与履约先确定权责结构，再展开支撑它的凭证；正式 JSON 的组装顺序不是访谈顺序。读取方法、展示骨架或保存工作理解都不授权编辑正式 FM。

## 初步上下文识别与分流

先理解合约、经营目的及真实材料，再按内容性质识别初步上下文及关联；不把合约章节直接当成上下文，也不将所有上下文等同于合同。初步划分是有依据、可随分析修正的工作理解，不是正式模型或部署决定。

- **合同上下文**：根据下文的经营依据、双方交换责任与独立边界识别，再列全部主履约并展开请求—确认。
- **领域上下文**：根据有独立身份的对象、知识与规则识别，说明服务哪个业务判断、与合同如何关联；不要求独立收费、KPI 或另一份合同。按 [领域建模](domain-modeling.md)优先复用成熟方案，先澄清当前业务消费的身份、能力、结果及适用条件，必要时才深入内部规则。
- **合同前协商**：根据真实邀请、方案及接受依据识别，按本页渠道协商分支展开；不强制补齐 RFP 或制造已成立合同。

同一条款可以同时提供合同责任依据和领域规则依据：不因划入领域而删除合同责任。保留其原约定归属、适用条件与依赖；账户管理不自动成为独立合同，账户对象也不自动成为承担合同责任的人或组织。缺少合同依据不等于已经证明属于领域；边界依据不足时保留具体线索和缺口，不包装成可选上下文。工具／胶水按实际用途说明，不为导航补造上下文。

先展示有充分依据的混合上下文总览，由用户选择分析焦点；已有有效焦点或明确指定目标时直接承接。合同项沿下文经营主线解释，领域项说明对象与规则边界，协商项说明形成何种约定及参与关系。导航、切换与结束交互由 Discovery 维护；选择不排除其他责任。深入后发现分类或边界不成立，核对关联判断及确认失效影响，再由用户决定焦点，不静默迁移责任。

### 分类验证：先检验，再展示

业务（Business）具有运营特定、领域中立的倾向：规则来自如何经营、交换权责或内部目标约定。领域（Domain）具有运营中立、领域特定的倾向：复杂度来自问题自身的知识、约束或算法。两者是识别逻辑的视角，不是给整个功能模块强制二选一，也不直接决定部署方式。没有收费或书面合同不能证明属于领域；有对象、状态和规则也不能证明属于领域。

在首次总览展示前，对分析结果执行以下 Sensors；后续新增事实或更正影响边界时，只复核受影响部分：

1. **拆开混合逻辑。** 从具体规则与责任判断入手，区分运营责任、专业能力及工具或集成。不把“库存与发货管理”等功能名称直接当作领域上下文，也不要求工具另成上下文。
2. **核对两种变化。** 保留能力而改变运营方式，哪些权责、费用、目标或完成认定会变？保留运营方式而替换经营对象，哪些责任结构还能复用？使用真实差异优先；假设只用于反例检验，不能把假设当成现行事实，也不要求业务方设计另一套运营模式。
3. **核对正面依据。** 合同按经营依据、交换责任及独立边界判断；领域须能说明具体问题、专业规则和运营中立的范围；协商须有真实方案及拟形成的约定。没找到合同不是领域成立的证据，可复用也不等于运营中立。
4. **检查责任守恒。** 拆出领域能力后，付款、交付、异常、信息保护及内部绩效等已知责任仍有归属或明确的边界缺口。能力结果不自动等于履约完成证明。
5. **据反馈调整。** 依据充分则保留分类；混合则拆开；被反例推翻则撤回或修正；不足则保留线索与必要未知，不作为已识别上下文展示，不让用户通过选择来替代验证。

验证的是当前边界判断，不代表责任已闭合或业务获批。对外只说明业务目的、边界及关联，不附资料出处、方法文章信息或内部检查清单；业务凭证及其证明作用仍需说明。交互分支与无可展示项时的处理归 Discovery。

## 1. 从经营目标与真实材料选择主线

```text
现金权责／目标—实际约束及来源 → 识别合同上下文与双方 → 全部主履约清单
                                  ↓ 对当前履约
                         请求—确认骨架 → 履约内凭证追溯
                                  ↓
                         异常新义务 → 重复同一循环
                                  ↓
                         单据推演 → 参与者与角色扮演 → 变化点与边界
```

这是分析依赖，不是逐项问卷，也不是必须逐关填满的流程。材料已提供的事实立即复用；身份、凭证或案例中的必要依赖可以提前处理，切换焦点时说明原因。先识别并记录全部主履约，再逐枝展开；当前进度展示聚焦一个请求或确认，不把显示范围当成业务范围，也不能把当前实现切片当成业务范围。

先理解收入换来哪些义务、支出换来哪些权利，无现金往来时目标与实际产出如何比较。现金权责与目标—实际是业务发现的两条主线，不是 Contract 的两种 Schema 类型，也不是每项履约都必须具有金额或 KPI 属性。经营依据帮助发现责任，不凭常识补造条款。合同履约、渠道协商和领域对象可以并存；纯领域、工具／胶水不强套收入或合同。

已有合约、订单、报价、政策、绩效约定和单据先读适用版本。材料不足时优先请求业务专家或法务专家提供约定或权责说明；明确口头约定也是来源，不强求纸质合同。无法取得时，从一件真实业务及其必须保留的凭证逆推待核实权责；凭证存在不等于完整条款已经成立。

现行事实澄清与新业务设计分开。尚无约定就保留待决事项；新约定设计须另有授权，建议不是现行事实，也不是法律结论。范围从材料中发现，由人类定义或明确确认；不能为放行排除未知责任。

### 合同上下文的识别依据

从经营角度寻找合同上下文：经营主线 → 真实约定与双方责任 → 独立责任边界 → 合同上下文，不先按功能或协议标题列合同再补贴经营标签。合同清单只列经营依据和独立边界充分的上下文。经营主线标注为“现金权责”或“目标与实际”；现金主线的收入／支出说明须注明观察主体，不将双方不同的现金方向固化为合同类型。不以泛泛的赚钱、省钱目的替代具体权责依据。

依据材料直接识别合同上下文，再让用户选择分析哪一个。合同上下文是有来源的分析结果，不是交给用户筛选或确认的候选；不要求用户确认合同是否存在。每个识别结果都须解释下列依据及其来源，不能只在全局写一句经营目标：

| 判断     | 必须解释的内容                                                                           |
| -------- | ---------------------------------------------------------------------------------------- |
| 经营依据 | 哪笔收入或支出产生权责，或哪项有来源的目标需要与实际产出比较；说明它如何属于本次经营主线 |
| 交换责任 | 收钱应履行什么、付钱有权要求什么；无现金时由谁向谁承诺什么工作产出、怎样检查目标与实际   |
| 约定来源 | 支撑双方、标的、责任及形成依据的条款、口头约定、专家说明或真实凭证及适用版本             |
| 边界理由 | 为什么属于双方独立的责任边界，还是既有合同的一项履约、附属约束、合同前协商或领域能力     |

不能仅凭协议名称、功能清单、注册动作、权限或隐私授权认定独立合同上下文；一份文档不等于一个上下文，一个功能也不等于一项履约。收费换取什么服务须有来源，不推定平台保证成交、商品质量或全部功能可用。

沿现金主线区分商品价款、服务费、代收或托管的商品货款与实际收入；经第三方支付机构收取、冻结或分账，不表示平台取得该笔商品货款收入。免费功能可以支撑已识别的现金主线，但不能因此推定每位用户都有缴费义务或每个功能都有独立合同。目标—实际主线须有承诺方、目标形成依据和实际产出，不把任意统计数、界面提示或服务期限当作 KPI。

已知收费或目标约定但金额或费率尚未明确，仍可依据双方、交换责任、约定来源与独立边界识别合同，保留参数缺口，不要求先填具体数字；参数缺口不阻塞合同识别。尚不能定位经营依据或独立边界时，只保留有来源的条款、责任线索和具体材料缺口，不进入合同总览，也不生成候选合同让用户选择。后续核对其现金权责或目标—实际约束及既有约定归属，不只标记“缺资料”；不自动判为领域或工具，不补造收费或绩效目标，不删除已知责任。材料已给出合同及责任时复用，经营解释不足不是重问全部条款的理由。

交付、交稿、退货、退款、信息保护及其他有依据的合规或风险责任，按真实约定归入相应责任链，不要求每项单独收费或另有 KPI，不以未查到现金或 KPI 为由删除。独立法定责任或尚不能归属的义务保留来源与边界缺口，不用“合规／风险”标签替代经营解释，也不自行排除人类确认范围。

## 2. 合同：确定约定边界

合同回答“谁和谁，就什么，达成了什么约定”。承接已识别的经营依据和边界理由，先确定名称与身份、双方角色、标的及适用依据，再吸收已明确的约定参数。合同不要求已有名为“合同”的电子文件，订单、协议或口头约定须按真实形成依据识别。

区分属性、关联、履约项与结果凭证：

| 信息                                                 | 分析时的位置                                                   |
| ---------------------------------------------------- | -------------------------------------------------------------- |
| 签订时间的业务含义，以及约定价格、数量、比例、周期等 | 合同事实或对已接受方案的引用；仅记录有依据且后续判断需要的内容 |
| 双方角色及标的物                                     | 对象关联，不因表格需要而复制成一组身份字段                     |
| 谁应付款、交付、提供服务或补偿                       | 主履约或异常义务，不压成合同状态字段                           |
| 实付金额、到货数量、交稿结果和实际确认时间           | 后续结果凭证，不提前当作签约事实                               |

这不是通用合同字段表。已知参数立即吸收，其他参数随履约中的关键数据追溯补充；不预填金额、有效期、赔偿或权限。签订时间不等于创建、生效或某次履约开始，类型时间含义按 [来源追溯](provenance.md) 展开，不索取一笔实际签约日期来完成类型分析。

双方先确定 Role，实际主体已明确就复用，未知不制造 Party；主体、代表办理人和凭证提供方不是同一身份。履约期间产生的请求与确认归合同责任边界，不为每项履约另建上下文。

**退出条件**：经营依据、交换责任、约定来源与独立边界理由均有充分材料支撑，约定、双方角色及标的可定位，才将其作为合同上下文展示。仅记录缺口不满足识别条件；依据不足的线索继续保留，不包装成合同。识别充分不要求一次补齐全部字段或凭证，也不表示法律效力裁决、全部责任闭合或正式建模准入。

用户选择后，承接已有双方和全部主履约，定位当前请求或确认，不再泛问交易如何成立。合同的成立条件或时点只有实际影响当前义务发生、期限或版本判断时才沿该依赖追溯，不把合同前协商当成必经关卡。材料更正或冲突使识别依据失效时，保留来源和影响，重新核对受影响上下文，不例行索取重复确认。

## 3. 履约：先画请求—确认骨架

先列出人类确认范围内全部主履约，包括有条件发生及完成后继续产生的义务。对当前履约画出：

```text
所属约定及双方
  └─ 履约请求 ─────────→ 履约确认
     谁向谁提出什么要求     什么结果表示本次义务已完成
     请求开始及截止的含义   确认时间及证明作用
```

骨架是权责的结构，不是已经找到全部单据。请求、确认本身也是凭证；骨架存在不等于完成证明已经查清。可以先标明“完成证明待明确”，再沿当前判断所需的依据追溯；不能因缺证明抹去已知义务，也不能把未知确认当作可自由填写的结果。

分别核对请求与具体确认的责任 Role、要求与期限依据、确认所证明的结果。Confirmation 不默认人工审批或验收动作，不从请求方推断证明提供方；提交、收到、验收合格、全额完成可能是不同事实，按约定区分。不把点击、导入、内部计算和流转都当成履约项。

使用简短的中文（英文）业务名称，细节和未知放在说明里，不用 Request／Confirmation 分类替代对象名称。箭头是从要求到结果证明的方向，不是资金方向。已知付款义务而期限未知时，只保留期限缺口；不要为骨架齐全编起算事件或固定时长。

以下仅为结构示意，不提供当前项目事实：

```text
所属约定：平台方（Platform Party）与作者（Author）的创作协议（Creation Agreement）
履约：交稿（Manuscript Delivery）
请求：平台方（Platform Party）→ 作者（Author），按约定交稿；期限依据待明确
请求责任人：作者（Author）；实际主体待明确
确认：完成证明及凭证责任人待明确
```

**退出条件**：当前履约的要求与结果语义可读，已知和未知分开，能够指出下一处需要追溯的依据；不是正式建模准入。

## 4. 凭证：沿骨架追溯关键数据

以请求和确认中的关键金额、数量、比例、身份、版本及业务时间为锚点，按 [来源追溯](provenance.md) 的统一循环展开：

1. 请求为什么成立：引用哪份约定、订单、方案或其他履约凭证。
2. 完成为什么成立：什么具体凭证证明结果，它的提供方、形成上下文和采信条件是什么。
3. 关键数据从哪里来：沿前序凭证追回直接记录、有效约定或有依据的派生规则；不把复制字段当作独立事实。
4. 怎样判断属于本次业务：核对合同、请求、主体和标的匹配，以及金额计算、适用版本和时间约束。

同一凭证可以有多条来源链，一个业务判断也可以涉及多个凭证。以一个业务焦点组织交互，各来源链深度优先深入依据再回溯；相关凭证及关键数据分支可以并行，不能把多个字段机械地串成逐项问卷，也不先扫描所有凭证再深入：

- 保留主焦点及各活跃凭证的当前位置、责任角色、已明确实际主体与上层回溯关系，分别核对经办人、证明提供方和受益者，不从合同一方或主焦点自动继承责任。
- 共同约定、适用版本或匹配关系影响多项数据时，先追溯共同依据；它得到回答后同时更新受影响来源链，不逐字段重复提问。
- 同一业务焦点下各相关凭证前置依据充分、彼此独立的缺口可并行澄清；一个分支依赖未知时保留该依赖，不阻塞其他获准继续的独立分支。
- 部分回答立即更新相应分支并重算依赖。依据查清只说明分析推进，不表示该凭证已经形成、履约已经完成或责任已经结束。

引用不自动表示先后。请求可引用更早的约定和同合同其他履约的凭证，追溯不局限于请求与确认之间；不要求每项履约都有固定的中间单据，也不为“证明凭证”再造一张无业务依据的凭证。

先解释具体证明作用，再区分“需要什么证明”的 Evidence Role 与“实际形成了什么”的 Evidence。证明插槽没有自己的责任人或形成时间；外部玩家保留其真实责任。不同履约属于同一合同，可直接引用具体凭证，不为履约分组建立证明角色；跨独立上下文的确定结果按 [语义](semantics.md) 直接引用，需要可替换证明约定时才使用 Evidence Role。

必需补充证明须先存在才能形成被证明凭证。分别核对它由谁形成、所属上下文、证明作用、当前可见性及本次实例关联，不把补充证据强加成固定流程阶段。上传时间不能替代业务形成时间。

**退出条件**：请求依据、完成证明及关键数据的来源、匹配和约束可解释，剩余缺口能定位到原对象；字段齐全不等于来源充分。

## 5. 异常：对新义务重复同一循环

逐项、递归核对违约责任，方法和终点判断唯一归 [全部追责结束](responsibility-closure.md)。当前履约的骨架与证明可解释后，核对各适用异常；材料已明确的异常立即吸收，不为了顺序延迟记录。

异常产生新义务时，仍先画它的请求—确认骨架，再追溯依据、期限和完成证明，再检查它的各层异常。找到退款、赔付或外部接手不等于责任结束；每条分支须到达人类确认、有依据的终点。

每轮可读的业务视图以当前合同、当前履约项的请求或确认中的一个判断为主焦点；沿相关凭证分析主张依据、完成证明和后续责任，多凭证并行不等于展开其他合同的全部责任。具体展示及问答形式由 Discovery 协议维护。全部主履约、异常分支与剩余缺口持续参与当前业务理解，完整核对责任覆盖。每条来源链按深度优先深入和回溯，按当前依赖选择可推进的独立链，不将一个分支的阻塞转成全局串行等待；责任终点仍逐枝核对，同一合同局部履约充分不能放行正式模型；独立合同完整闭合后按合同级准入分批建模。

## 6. 用单据推演检验理解

主要凭证链已经可解释时，选正常业务与相关争议，按真实角色走一遍；异常分支也须核对。优先复用脱敏单据，无实例时明确标为合成，不伪造已发生事件。每一步只使用当时已有的凭证，检查能否作出业务判断。

对金额、版本、时刻或责任的质疑，应能从结果追回原约定；缺什么就回到原对象，不临时增设审批或赔偿。记录实际推演结果与未决项，未执行不声称通过。对话推演不需要正式模型或 Python，不等于机器模拟，具体边界见 [场景校验](scenario-validation.md)。

## 7. 寻找参与者与角色扮演关系

主要证明链可解释后沿角色主动寻找 Party，不等 API 设计再补。这是分析依赖，不是硬性关卡：材料已明确主体时立即复用；身份影响判断时提前处理；纯领域和独立渠道不以合同或单据推演为前提。

1. **从责任定位角色**：在哪个上下文，对什么要求或凭证承担责任；责任身份与提供方分开。
2. **寻找实际主体**：沿合约署名、单据和专家说明定位个人或组织；未知保留，不制造主体补槽位。
3. **核对跨上下文同一性**：稳定身份及来源能否支持同一主体；同名不能证明同一，不同角色名也不证明主体不同。
4. **区分代表与责任主体**：谁代表谁办理本事项，依据是什么；经办人不自动承担合同义务，不扩展全部操作权限。
5. **形成有来源的对应关系**：核对主体、角色、同一性及代表依据的对应关系；已有正式对象只引用，访谈不写正式 `plays_role`。

付款经办人不自动成为付款义务方，银行出具证明不自动使银行成为当前合同一方。未知主体不抹去已知凭证链；影响责任闭合时，受影响合同或本轮确认范围不能进入正式建模。

## 8. 从实际差异发现变化点与边界

比较有来源的不同主体、渠道、证明或领域能力，判断哪些责任不变、哪些前提与采信条件变化。先有具体案例再抽取模式，不征集无边界的未来功能，不让业务方填写 Evidence Role 技术槽位。

当前只消费支撑方结果时，保留证明含义、真实责任、采信条件及本次边界；不要求展开所有供应商内部业务。只有内部规则影响当前判断或属于授权范围时深入。只有一个案例时，复用保持候选。领域、合同及履约边界不直接决定部署方案。

## 9. 领域对象与渠道协商走各自分支

### 领域对象

从领域边界与已有方案进入，优先复用成熟知识和能力，先澄清业务连接点；只有不适用、特有规则、影响当前判断的内部未知或明确设计要求时才深入，具体方法归 [领域建模](domain-modeling.md)。深入时分析对象身份、属性、关系和规则，不要求有合同或凭证。档案去重不扩成全企业数据字典；客户主体与档案、独立联系方式与普通属性须区分。身份冲突、业务基数、资格、合并条件和授权均是业务知识，不交数据库主键替代。

规则与适用版本须有依据，不编公式；代码只证明当前行为，不能裁决业务。FM 对操作、状态迁移、复杂算法或关系实例数量表达不足时保留能力限制，不造假 Evidence／Fulfillment 来宣称已模拟。具体见 [领域建模](domain-modeling.md)。

### 渠道协商

沿真实邀请、报价、方案及回应识别双方、标的、有效时间和接受依据。RFP → Proposal → Contract 是可能主线，不是必须完整走完的流水线。固定套餐不补 RFP，报价未接受不补合同，签约前协商不伪装成履约。

合同只消费最终形成它的约定和必要追溯，不搬入渠道内部所有过程；是否形成签约有真实歧义才保留缺口。

## 10. 将发现交给正式表达

上述合同、骨架、凭证和责任分支都是当前业务理解，不是第二份正式 FM。术语名称与含义由 [领域语言方法](domain-language.md) 指定的唯一拥有者维护，分析时复用明确术语及实际业务依据。

正式编辑先按 [追责结束准入](responsibility-closure.md) 核对本轮合同或合同组的完整责任图、各终点及人类合同级结束确认，再核对编辑授权。相关未澄清合同使用 Context Role，必要外部证明仍须查清；完整业务范围继续保留，整体结束另核对全局明确确认。门槛满足后按 [批次评估](batch-assessment.md) 映射对象、属性、关联、规则和场景；业务未知只交接，不用技术表达或范围排除制造通过。
