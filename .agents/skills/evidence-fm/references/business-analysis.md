# 业务建模判断准则

用于识别已有材料中的业务结构及真正缺口，供输入复核和专业访谈只读使用。读取本页不授权生成模型，也不启动问答；访谈的选题、等待、停止与恢复由访谈任务负责。

## 1. 从经营目标与真实材料建立主线

业务分析沿“经营目标与材料 → 合约权责 → 凭证追溯 → 单据推演 → 参与者与角色扮演 → 变化点与边界”推进。这是推导关系，不是逐项问卷或必须依次完成的阶段；恢复时从已有依据继续，缺口只决定这条主线下一步缺什么，不代替主线本身。

先从现有材料判断业务如何取得收入、承担支出或兑现内部绩效目标。现金收入对应哪些义务，现金支出换取哪些权利，没有现金往来时，目标与实际产出如何比较。借此发现尚未提及但与当前目标相关的权责，不凭常识补造条款。

范围是发现成果，不是前置问卷；不让用户先选择建模模式。

从业务叙述、痛点和真实材料识别有依据的上下文。没有约定依据时先核对一件真实发生的事，不凭空提供完整模型让用户挑选。不按产品名称或关键词硬分类：“客户”不自动意味着销售合同，“绩效”不自动意味着主管负责发起请求，没有“合同”字样也不等于没有约定。

合同、领域与渠道可以并存，沿实际责任与对象关系组合。材料未提及不等于范围外；未展开、边界待定和有依据的排除分开，外部活动仍可能提供本职责必需的输入或证明。

所有关键金额、数量、比例、凭证时间、身份和领域结论均按 [业务来源追溯](./provenance.md) 复核，不以是否疑似派生为开关。技术缺口、模型表达缺口和业务知识缺口分别记录。

### 取得约定依据，而不是现场编规则

已有合约、报价、订单、政策、绩效约定或单据先读原文及适用版本，不让用户重述已提供内容。材料不足时，优先请求业务专家或法务专家提供适用合约或权责说明；已有明确口头约定也可以作为来源，不强求纸质合同。

无法取得合约时，从一件真实业务及其必须留存的凭证逆推：哪些凭证必须保留和追溯，它们证明什么权责，发生违约时依据哪份约定追责。候选合同只能是待核实理解，不能把单据存在当成完整条款已经成立。

现行事实澄清与新业务设计分开。若业务本身尚无约定，记录待决事项；用户明确授权设计新约定后，才比较方案、后果和待业务方决定的条款。设计建议不是现行事实，也不是法律结论。

### 以可读的业务视图共同推理

围绕当前真实案例展示“约定与双方 → 主张及依据 → 完成证明 → 后续责任”，标出来源、推断、缺口以及本轮变化。业务方应能据此解释发生了什么、为何成立、争议如何追溯。术语在这条链上澄清，词汇表只是入口，不以定义条数衡量理解程度。简化视图引用已有对象和来源，保存在已有发现记录中，不成为第二份正式模型。

## 2. 合同与履约

```text
候选合同上下文 → 双方角色与约定 → 履约项
```

合同是双方的业务约定，不要求已有名为“合同”的电子文件。系统、API、调度器不是业务 Party。每项履约分别确定 Request 与 Confirmation 的责任 Role；同一 Role 可以在不同履约中负责不同类型的凭证。不把每个流程步骤都当成履约项；点击、导入、内部计算和流转须有独立约定、请求与确认语义才成为履约。

Confirmation 不默认是人工审批，不从请求凭证责任角色推导确认人；独立验收须有业务依据。确认回答的是谁提供或形成什么凭证、证明什么结果，不是增设“执行 → 验收”阶段。只有凭证名称不能确定提供方或采信作用。

先区分“需要什么证明”的 Evidence Role 与“实际形成了什么”的具体 Evidence。Evidence Role 没有责任人或自身形成时间，不追问其签发人；沿明确的外部玩家核对实际提供方、结果及采信依据。不得仅因角色名含“凭证”就建成 `other_evidence`，也不得把外部玩家的责任强加给本合同双方。

如果某凭证需要 `other_evidence` 作为补充证明，分别核对证据由谁形成、属于哪个非履约 Context、证明什么、当前是否存在及能否关联本次业务实例。合同履行期间由本合同形成的补充凭证属于父 Contract Context，即使只服务于一项子履约；它与直接子履约凭证通过 `evidences`／`precedes` 关联，而不是改归 Fulfillment。必需证据先存在，才能形成被证明凭证。该结构适用于合同前凭证、合同、履约请求和确认等，不为凑流程而添加补充证据。其业务形成时间与上传时间不同，技术录入方式不能改变形成前提。表达细节复用 [语义](semantics.md#5-evidence)。

内部绩效沿实际目标提出、回应与变更约定展开，不预设主管永远负责发起请求，不自动创建“目标设定履约”。角色、凭证与跨上下文证明的正式表达按 [语义](semantics.md)。

### 业务称谓与数量关系

使用业务实际称谓描述对象与办理行为，不用 Request、Confirmation 等分类替代业务名称。分别核对每份协议下的申请数量、每份申请下的结果数量，以及具体证明材料的归属范围；一个正常案例只有一份，不足以证明上限为一。复用已有明示基数和有依据的确定性推导，缺失或矛盾保留缺口，不为缩短 URI 决定业务事实。存在阶段、有效结果与更正记录的计数范围需要区分，接口单复数不是访谈问题。

### 逐项、递归核对违约责任

逐项检查主要履约的违约情况，包括逾期、拒绝、部分完成及结果不符；对新增的补偿履约重复检查，不因已有一项赔付就认为整个合同的异常已覆盖。

```text
主要义务 → 有来源的违约触发条件 → 新请求与确认凭证
                                  ↓
                          新义务仍未完成怎么办
                                  ↓
                          继续检查至有依据的终点
```

- 缺少责任约定时，提出具体违约情景和责任缺口；反例不表示违约已经发生，也不构成新责任的依据。
- 有来源时先展示“前序履约 → 违约触发条件 → 新履约候选”，再说明请求、确认和局部未知；不默认存在罚息、退款、赔偿或直接诉讼。
- 对退款、补交、返工、赔付继续检查；复用原身份，连接同一合同内的直接前序与触发依据，不能循环。追加补偿凭证，不覆盖原凭证。
- 若有依据表明未付款使合同自动作废且不产生额外义务，也无需另一次确认，记录终止规则，不造独立履约。不能仅因由系统自动执行就排除真实的退款或赔付义务。
- 有依据时确认只能诉诸法律，或按约终止且没有后续义务；未明确就保留缺口，不要求本轮全部找到终点。法律处理作为外部边界，不自动扩成诉讼管理软件。
- 未知、跳过、暂缓和范围外都不等于责任链已经闭合。范围外记录真实依赖与排除依据，不写成无后续责任。
- 记录未检查、待核实、已明确新责任、已明确终点及来源，不新建结构化检查表或第二套状态字段。逐项检查是 Agent 的分析责任，不是预排问卷。

完整责任链是持续发现方向，**不是首版模型或独立主履约产出的全局准入条件**。后续未知不能自动阻塞不依赖它的主要义务；也不能为了产出而删掉当前义务真正需要的前提。

### 候选结构与局部未知

名称与分析分离：用单行业务短名称识别对象，职责、来源、缺口和候选状态写详细说明，不堆进标题。请求与确认各用简短说明；不能为简洁删除真实业务条件。局部未知不抹去已知事实，已知付款义务但期限未知时只保留期限缺口；候选结论与事实依据分开。

以下仅为结构示意，不提供当前项目事实：

```text
所属约定：平台与作者的创作协议（来源）
候选履约：交稿
履约请求：平台（有来源时写编辑代表）→ 作者
要求／依据：按协议持续交稿
期限：以本次请求的 expired_at 为准；确定依据待明确
确认凭证：待明确——谁提供什么证明本次交稿完成
```

“履约请求 → 确认凭证”连接要求与结果证明。箭头表示从要求到结果证明的履约方向，不是资金方向。不默认编辑验收通过，不因作者提交就认定成功；选题、试写、样稿协商留在渠道主线。

## 3. 领域身份与规则

```text
候选领域上下文与对象 → 身份 → 属性与关系
```

从对象身份、属性与关系核对变化条件、资格、不变条件和计算。不要求有合同或凭证才能讨论领域知识；档案去重聚焦身份，不扩成整个企业的数据字典。

- 区分稳定参与者与其档案、属性与独立对象、身份插槽与具体玩家。
- 不要求用户决定数据库主键；唯一性范围、身份冲突、关系基数、合并条件与授权是业务知识，不能一律推给架构。
- 资格、前置条件、不变条件、变化规则、计算及适用版本须有依据，无依据不编公式。
- 同名不同人、共享联系人、归档后修改是可选反例，不是项目默认事实。
- 代码是现状证据，不自动优先于业务决定。具体表达和能力边界见 [领域建模](domain-modeling.md)。

FM 对操作、状态迁移或复杂算法表达不足时，如实记录业务要求和待实现／验证部分。关系基数可声明并静态校验，但当前不能用通用 Relationship Instance 运行验证；不得造假 Evidence 或 Fulfillment 来声称已模拟领域操作或实例数量。

## 4. 渠道协商

```text
真实邀请、报价或方案 → 请求与回应 → 协商规则
```

沿真实邀请、报价或方案、请求与回应核对实际双方、版本、有效性与接受依据。RFP → Proposal → Contract 是可能的时间线，不是必须走完的流水线。

固定套餐不补造 RFP；报价尚未接受不补造已签合同；接受是否构成签约有真实歧义才形成缺口。签约前异步请求与响应不伪装成履约。发现独立领域规则或真实协议时再连接相应上下文。

## 5. 用单据推演检验理解

在主要凭证链已经可解释时，选一件正常业务和一个与当前约定有关的争议，按真实角色走一遍。可复用脱敏单据；没有实例时明确标为合成，不伪造已发生事件。每一步只使用当时已有的凭证，检查能否据此作出业务判断。

重点不是流程能否走完，而是证明是否足够：对方质疑金额、适用版本、时刻或责任时，能否从结果沿关键值追回原约定。缺什么就回到原对象继续追溯，不凭空增设审批或证明材料。争议只是检验案例，不意味着现实已经违约，也不授权创设赔偿责任。

记录案例依据、使用的凭证引用、实际推演结果和暴露的缺口。未决预期交给业务方澄清，不能由 Agent 同时编规则和答案。对话中的推演不同于生成 validation 或执行机器模拟；具体边界见 [场景校验](scenario-validation.md)。

## 6. 寻找参与者与角色扮演关系

权责分析先确定 Role，主要凭证链可解释并经单据推演检查后，沿凭证主动寻找实际扮演者 Party，再检查变化点。这是分析依赖，不是硬性关卡：材料已明确主体时立即复用；身份未知影响当前判断时提前澄清，不等 API 设计再补。纯领域或独立渠道从其对象、行为和参与身份开始，不以合同或单据推演为前提。

按当前切片逐个核对 Party Role，而不是先罗列组织架构：

1. **从责任定位角色**：该角色在哪个上下文对哪份凭证承担什么权责；责任身份与凭证提供方、经办岗位分开。
2. **寻找实际主体**：从合约署名、单据和已知业务说明寻找谁以该身份参与，是个人还是组织。没有来源时保留“玩家待明确”，不为补齐图形制造 Party。
3. **核对跨上下文同一性**：同一主体是否在不同上下文扮演不同角色，以稳定业务身份及来源判断；同名不能证明同一，不同角色名也不证明主体不同。不把账号、档案或联系人默认当成责任主体。
4. **区分代表与责任主体**：核对谁代表谁办理当前事项及其依据；经办人不自动成为合同一方，代表一次办理不等于具有该角色的全部操作权限。
5. **形成有来源的对应关系**：在发现记录的 `participants` 中记录上下文／角色、主体或候选、同一性依据、代表关系及未决项；已有正式对象只引用。模型编辑另获授权时才建立或复用 Participant Party，并以 `plays_role` 连接 Role，Party 保持在 Context 外。

例如，材料明确同一用户兼任读者和作者时，保留一个主体与两个上下文中的角色；材料只给出同名时，不合并，也不据此断言一定是两个人。财务人员代公司付款不自动使其承担公司的合同付款义务。Evidence provider 可能属于另一合同，其凭证扮演 Evidence Role 不等于该提供方扮演当前合同的 Party Role。

主体缺口只阻塞依赖其身份或扮演关系的判断，不抹去已知角色与凭证链。访谈每轮只选一个影响判断的身份或代表关系问题，已知事实直接复用，不让用户填写 `plays_role` 技术字段。按本轮权限保存来源和术语；不把映射讨论变成正式模型编辑。

## 7. 从实际差异发现变化点与边界

比较已有或有来源的业务方式：更换支付证明提供方、合同形成渠道、参与者或领域能力后，哪些权责仍成立，哪些完成证明和前提不同。外部合同的结果能否提供同一种合格证明，按来源判断；角色化是分析结论，不让业务方填写 Evidence Role 等技术槽位。

先有具体可判断的业务模型，再考虑提取可复用模式。不用“未来还能支持什么”进行无边界发散，不把没有实例支持的抽象当成已验证模式。仅有一个案例时，模式保持候选；对核心业务模式的分析不要求展开所有供应商内部业务。

当前只消费支撑方结果时，记录接口之外的业务含义、采信条件及真实责任来源即可；只有其内部规则影响当前判断或属于授权目标时才深入。简化支撑部分不等于它没有合同或责任。领域、合同与履约边界不直接决定部署方案。

## 8. 可纳入判断与缺口交接

按 [批次评估](batch-assessment.md) 检查当前职责的必要事实，复用已知条件和确定性推导，只纳入被消费的已知支撑事实，不要求上游全部完成。业务事实充分但缺格式映射时由 FM 表达，不把技术槽位变成访谈问题。

案例及模拟边界按 [场景校验](scenario-validation.md)。对必要业务缺口给出对象、来源、已有事实、不能作出的判断与影响，交给访谈处理；模型仍保留未决项，不借缺口输出自动开始提问或修改模型。
