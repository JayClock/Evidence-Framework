# 业务建模判断准则

用于识别已有材料中的业务结构及真正缺口，供输入复核和专业访谈只读使用。读取本页不授权生成模型，也不启动问答；访谈的选题、等待、停止与恢复由访谈任务负责。

## 1. 识别范围与候选

范围是发现成果，不是前置问卷；不让用户先选择建模模式。

从业务叙述、痛点和真实材料识别有依据的上下文。没有约定依据时先核对一件真实发生的事，不凭空提供完整模型让用户挑选。不按产品名称或关键词硬分类：“客户”不自动意味着销售合同，“绩效”不自动意味着主管负责发起请求，没有“合同”字样也不等于没有约定。

合同、领域与渠道可以并存，沿实际责任与对象关系组合。材料未提及不等于范围外；未展开、边界待定和有依据的排除分开，外部活动仍可能提供本职责必需的输入或证明。

所有关键金额、数量、比例、凭证时间、身份和领域结论均按 [业务来源追溯](./provenance.md) 复核，不以是否疑似派生为开关。技术缺口、模型表达缺口和业务知识缺口分别记录。

## 2. 合同与履约

```text
候选合同上下文 → 双方角色与约定 → 履约项
```

合同是双方的业务约定，不要求已有名为“合同”的电子文件。系统、API、调度器不是业务 Party。每项履约分别确定 Request 与 Confirmation 的责任 Role；同一 Role 可以在不同履约中负责不同类型的凭证。不把每个流程步骤都当成履约项；点击、导入、内部计算和流转须有独立约定、请求与确认语义才成为履约。

Confirmation 不默认是人工审批，不从请求凭证责任角色推导确认人；独立验收须有业务依据。确认回答的是谁提供或形成什么凭证、证明什么结果，不是增设“执行 → 验收”阶段。只有凭证名称不能确定提供方或采信作用。

内部绩效沿实际目标提出、回应与变更约定展开，不预设主管永远负责发起请求，不自动创建“目标设定履约”。角色、凭证与跨上下文证明的正式表达按 [语义](semantics.md)。

### 逐项、递归核对违约责任

逐项检查主要履约的违约情况，包括逾期、拒绝、部分完成及结果不符；对新增的补偿履约重复检查，不因已有一项赔付就认为整个合同的异常已覆盖。

```text
主要义务 → 有来源的违约触发条件 → 新请求与确认凭证
                                  ↓
                          新义务仍未完成怎么办
                                  ↓
                          继续检查至有依据的终点
```

- 缺少责任约定时，提出具体违约情景和责任缺口；反例不表示违约已经发生，也不构成新责任的依据。
- 有来源时先展示“前序履约 → 违约触发条件 → 新履约候选”，再说明请求、确认和局部未知；不默认存在罚息、退款、赔偿或直接诉讼。
- 对退款、补交、返工、赔付继续检查；复用原身份，连接同一合同内的直接前序与触发依据，不能循环。追加补偿凭证，不覆盖原凭证。
- 若有依据表明未付款使合同自动作废且不产生额外义务，也无需另一次确认，记录终止规则，不造独立履约。不能仅因由系统自动执行就排除真实的退款或赔付义务。
- 有依据时确认只能诉诸法律，或按约终止且没有后续义务；未明确就保留缺口，不要求本轮全部找到终点。法律处理作为外部边界，不自动扩成诉讼管理软件。
- 未知、跳过、暂缓和范围外都不等于责任链已经闭合。范围外记录真实依赖与排除依据，不写成无后续责任。
- 记录未检查、待核实、已明确新责任、已明确终点及来源，不新建结构化检查表或第二套状态字段。逐项检查是 Agent 的分析责任，不是预排问卷。

完整责任链是持续发现方向，**不是首版模型或独立主履约产出的全局准入条件**。后续未知不能自动阻塞不依赖它的主要义务；也不能为了产出而删掉当前义务真正需要的前提。

### 候选结构与局部未知

名称与分析分离：用单行业务短名称识别对象，职责、来源、缺口和候选状态写详细说明，不堆进标题。请求与确认各用简短说明；不能为简洁删除真实业务条件。局部未知不抹去已知事实，已知付款义务但期限未知时只保留期限缺口；候选审核状态与事实依据分开。

以下仅为结构示意，不提供当前项目事实：

```text
所属约定：平台与作者的创作协议（来源）
候选履约：交稿
履约请求：平台（有来源时写编辑代表）→ 作者
要求／依据：按协议持续交稿
期限：以本次请求的 expired_at 为准；确定依据待明确
确认凭证：待明确——谁提供什么证明本次交稿完成
```

“履约请求 → 确认凭证”连接要求与结果证明。箭头表示从要求到结果证明的履约方向，不是资金方向。不默认编辑验收通过，不因作者提交就认定成功；选题、试写、样稿协商留在渠道主线。

## 3. 领域身份与规则

```text
候选领域上下文与对象 → 身份 → 属性与关系
```

从对象身份、属性与关系核对变化条件、资格、不变条件和计算。不要求有合同或凭证才能讨论领域知识；档案去重聚焦身份，不扩成整个企业的数据字典。

- 区分稳定参与者与其档案、属性与独立对象、身份插槽与具体玩家。
- 不要求用户决定数据库主键；唯一性范围、身份冲突、关系基数、合并条件与授权是业务知识，不能一律推给架构。
- 资格、前置条件、不变条件、变化规则、计算及适用版本须有依据，无依据不编公式。
- 同名不同人、共享联系人、归档后修改是可选反例，不是项目默认事实。
- 代码是现状证据，不自动优先于业务决定。具体表达和能力边界见 [领域建模](domain-modeling.md)。

FM 对操作、状态迁移、关系基数或复杂算法表达不足时，如实记录业务要求和待实现／验证部分，不造假 Evidence 或 Fulfillment 来声称已模拟领域操作。

## 4. 渠道协商

```text
真实邀请、报价或方案 → 请求与回应 → 协商规则
```

沿真实邀请、报价或方案、请求与回应核对实际双方、版本、有效性与接受依据。RFP → Proposal → Contract 是可能的时间线，不是必须走完的流水线。

固定套餐不补造 RFP；报价尚未接受不补造已签合同；接受是否构成签约有真实歧义才形成缺口。签约前异步请求与响应不伪装成履约。发现独立领域规则或真实协议时再连接相应上下文。

## 5. 可纳入判断与缺口交接

按 [批次评估](batch-assessment.md) 检查当前职责的必要事实，复用已知条件和确定性推导，只纳入被消费的已知支撑事实，不要求上游全部完成。业务事实充分但缺格式映射时由 FM 表达，不把技术槽位变成访谈问题。

案例及模拟边界按 [场景校验](scenario-validation.md)。对必要业务缺口给出对象、来源、已有事实、不能作出的判断与影响，交给访谈处理；模型仍保留未决项，不借缺口输出自动开始提问或发布。
