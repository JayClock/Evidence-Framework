# 业务分析：从合同与履约发现业务

本页维护以收入流与成本结构发现现金权责、绩效约定，再分析参与方、履约及关联边界的方法。分析形成当前业务理解，不授权编辑正式 FM；问答与控制归 Discovery，有业务依据及编辑授权即可渐进表达，范围结束与下游交付另核对完整责任。

## 分析主线

```text
理解收入流与成本结构 → 以现金权责、目标—实际对比发现业务 → 寻找实际约定，明确责任双方 → 列出主要履约，检验约定理解
                                              ↓ 对当前履约
                                     请求—确认骨架 → 履约内凭证追溯
                                              ↓
                                     异常新义务 → 重复同一循环
                                              ↓
                              单据推演、参与者与角色扮演、变化点与边界
```

沿履约和凭证增量发现其他约定及协作关系，再回到当前判断。分析不是逐项问卷，也不必先找齐全局所有合同；当前合同的已知主履约清单持续补全，有条件发生及完成后继续产生的义务一并保留。全部主履约及各层异常须在范围结束及下游交付前核对完整，不能把当前显示节点或实现切片当作合同范围。

已有现金权责或绩效约定、双方及责任明确时直接进入，不重复问合同是否存在；直接承接复用已有经营依据，不省略收入流与成本结构的分析。明确指定目标或只有一个清晰入口时直接承接；多个独立入口需要确定优先级，或用户要求查看、切换时，才由 Discovery 展示当前上下文总览。总览反映当前理解，不证明全局发现已完成；选择只决定焦点，不确认合同存在或排除其他责任。

## 1. 理解实际经营过程

从业务方的收入流与成本结构理解实际经营过程，再核对现行约定和真实单据：怎样取得业务机会、收支对应什么权责、内部工作如何约定产出、何时达成约定、如何证明完成、不完成如何处理。已知事实直接复用，不要求先填统一字段表或完成全局分类。

现金权责与目标—实际对比是发现业务的核心逻辑，不是可有可无的辅助线索：

1. **现金收入对应承担的义务**：为什么收钱、向谁承诺什么、需要什么凭证证明履约成功。
2. **现金支出对应取得的权利**：为什么付钱、谁应完成什么、如何检查对方按约履约。
3. **没有现金往来时**：从成本结构及内部绩效约定寻找目标或计划、责任双方、实际工作产出和进度检查，通过目标—实际对比组织证明。这里是设立目标并追踪结果，不是先等实际结果出现偏差；工作产出、KPI、OKR 按真实约定复用，不把任意统计数或服务期限当成绩效目标。

从上述权责追到所属约定，再列出主要履约；凭证必须围绕现金往来或 KPI，并通过关键数据项明确关联关系。这是业务凭证的组织与收敛逻辑，不要求每项履约单独收费或另设 KPI。交付、信息保护、退款、赔付等有依据的责任保留在其所属经营约定及责任链中，不因没有独立收费而消失。区分服务收入、商品价款和代收或托管的货款，第三方收取、冻结或分账不表示平台取得该笔收入；从实际收支核对真实权责，不凭常识补造条款。

经营依据未知时，先澄清收入、支出或内部目标对应的责任关系，不仅凭一句承诺认定独立业务合同，也不补造收费或绩效约定。没有对外合同则核对内部绩效协议；本次只提供领域对象或专业能力时进入领域分支，只做技术调用时核对工具范围，不强套业务合同。已知责任及其归属疑问继续保留，不能因暂时找不到经营依据就删除。

约定不清楚时，优先请业务专家或法务专家说明谁向谁承诺什么。明确口头约定也是依据，不强求纸质合同；无法取得约定说明时，从一件真实业务及其可见凭证逆推必要权责，再核实缺口。凭证存在不表示全部条款已经成立。

现行业务澄清与新业务设计分开。尚无约定就保留待决事项，建议不是现行事实，也不是法律结论；设计新约定须另获授权。范围由人类定义或明确确认，不为放行排除未知责任。

## 2. 寻找合同，明确参与方

合同回答“谁和谁，就什么，达成了什么约定”。沿现金权责或内部绩效找到实际约定与责任双方，再用主要履约检验理解，不把合约章节直接当成上下文，也不能仅凭协议名称、功能清单、注册动作或授权操作认定独立合同。一个约定可以包含多项履约，一份文档也可以包含不同的责任关系。

### 约定与责任双方

1. **找到约定。** 复用双方已经接受的订单、协议、报价或口头承诺，说明标的及主要责任；未接受的方案留在协商分支，不制造已成立合同。
2. **明确双方。** 确认谁以什么责任身份参与，实际主体已明确就复用个人或组织；角色明确而主体未知时保留缺口，不制造 Party。合同入口即明确责任双方，不以单据推演完成为前提。
3. **区分其他身份。** 合同责任主体、代表办理人和证明提供方分别核对。经办人不自动成为合同责任方，银行出具回执也不自动成为当前合同一方；代表关系只覆盖有依据的办理范围。
4. **列出主要履约。** 谁应付款、交付、提供服务、检查产出或补偿？以此检验双方对什么达成了约定；无法解释时回到当前业务核对，不仅凭名称定边界。同一方在不同履约项中可以分别成为权利方和义务方，责任方向由实际约定决定。
5. **判断归属。** 这些责任属于同一约定，还是另一组双方之间的独立承诺？附属约束保留在原合同，未明确归属的责任保留具体疑问，不补造合同供用户投票。

已明确的价格、数量、比例、周期与版本立即吸收。金额或费率尚未明确，不阻塞已有约定与责任的分析；其他参数随履约关键数据追溯补充，不预填期限、赔偿或权限。签订时间不等于创建、生效或履约开始，其业务含义按 [来源追溯](provenance.md) 核对，不索取一笔实际日期来完成类型分析。

双方与标的是对象关联；付款、交稿等是履约义务；实付金额、到货数量、交稿结果及实际确认时间属于后续结果凭证，不提前当成签约事实或合同状态字段。

**进入履约分析的条件**：能够说明本合同的现金权责或目标—实际对比依据，约定、双方及主要责任能够解释，已知事实与必要未知可区分；不要求一次补齐全部参数、主体信息和凭证，不表示法律效力裁决、责任闭合或正式建模准入。必要前提仍不明时，澄清当前收支或内部目标与谁向谁承担责任的关系，不要求用户选择合同标签。

### 沿协作发现其他合同

当前履约使用外部结果时，核对结果由谁提供、对谁承担什么责任、依据哪项约定。另一组双方的独立约定明确后，补入当前业务理解并保留与当前履约的证明关联，不要求先展开外部合同的全部内部履约。第三方出现不自动产生新合同，技术系统名称、回调或凭证提供方也不替代约定判断。

新增关联不自动切换访谈焦点；继续追当前判断所需的证明与采信条件，外部内部未决项按实际边界保留。更正推翻已有约定或边界时，核对受影响责任和人类确认，保留未受影响事实，不静默搬迁责任。

## 3. 履约：先画请求—确认骨架

从当前合同的已知主履约进入，对当前履约画出：

```text
所属约定及双方
  └─ 履约请求 ─────────→ 一份或多份履约确认
     谁向谁提出什么要求     分别记录哪些完成或部分完成结果
     请求开始及截止的含义   各确认时间、证明作用及整体完成条件
```

骨架是权责结构，不是已经找到全部单据。请求、确认本身也是凭证；可先标明完成证明待明确，再沿当前判断所需依据追溯。不能因缺证明抹去已知义务，也不能把未知确认当成可自由填写的结果。

责任人就是所属合同的一方：直接复用合同双方，按约定分别定位请求与每份确认的合同责任方及已知实际主体，不在双方之外另寻凭证责任角色。经办人、上传人和证明提供方的办理或证明作用另行说明，不替换合同责任方；外部凭证回到它所属合同的一方定位责任。一次请求可以对应不同的确认凭证，部分结果不等于整项履约完成。Confirmation 不默认人工审批或验收动作；提交、收到、验收合格、全额完成可能是不同事实，按约定区分。不把点击、导入、计算和流转都当成履约项。

使用简短的中文（英文）业务名称，细节和未知放在说明里，不用 Request／Confirmation 分类替代对象名称。箭头是从要求到结果证明的方向，不是资金方向。付款义务明确而期限未知时，只保留期限缺口，不编起算事件或固定时长。

以下为合成结构示意：

```text
所属约定：平台方（Platform Party）与作者（Author）的创作协议（Creation Agreement）
履约：交稿（Manuscript Delivery）
请求：平台方（Platform Party）→ 作者（Author），按约定交稿；期限依据待明确
请求责任人：平台方（Platform Party），为合同一方；实际主体待明确
交稿义务方：作者（Author），为合同另一方
确认责任人：按约定由作者（Author）对交稿结果负责；完成证明待明确
```

**退出条件**：当前履约的要求与结果语义可读，已知和未知分开，能够指出下一处需要追溯的依据；不是正式建模准入。

## 4. 凭证：沿骨架追溯关键数据

业务凭证围绕所属合同的现金权责或目标—实际对比组织；请求、确认及支撑凭证都须说明服务于哪项权利、义务或绩效证明，不把任意点击和流转当作业务脊梁。领域对象及独立协商按各自分支处理，不为其补造现金往来或 KPI。

以请求和确认中的关键金额、数量、比例、身份、版本及业务时间为锚点，按 [来源追溯](provenance.md) 展开：

1. 请求为什么成立：引用哪份约定、订单、方案或其他履约凭证。
2. 完成为什么成立：什么凭证证明结果，提供方、形成上下文和采信条件是什么。
3. 关键数据从哪里来：沿前序凭证追回直接记录、有效约定或有依据的派生规则，不把复制字段当独立事实。
4. 怎样判断属于本次业务：核对合同、请求、主体和标的匹配，以及计算、版本和时间约束。

一个业务判断可以涉及多个凭证，同一凭证也可有多条来源链。各链深度优先深入依据再回溯，不机械逐字段问到底，也不先扫描全部凭证再深入：

- 保留主焦点及各活跃凭证的当前位置、所属合同的合同责任方、实际主体与上层回溯关系。
- 每轮主动寻找可同时澄清的内容，核对相关请求、确认和支撑凭证，不在找到第一题后停止查找。
- 共同约定、版本或匹配关系只追一次，与其他独立缺口同轮澄清；局部依赖只约束相关分支，不将整轮变成逐问。
- 部分回答立即更新对应链并重算依赖，依据查清不表示凭证已经形成或履约已经完成。

引用不自动表示先后，请求可以引用更早的约定或同合同其他履约的凭证；不要求固定的中间单据，不为证明凭证再造无业务依据的凭证。先解释证明作用，再区分 Evidence Role 与实际 Evidence；证明插槽没有自己的责任人或形成时间。跨独立上下文的确定结果按 [语义](semantics.md) 引用，需要可替换证明约定时才使用 Evidence Role，同合同履约不为分组建立证明角色。

必需补充证明须先存在才能形成被证明凭证，分别核对责任、形成上下文、证明作用、可见性及实例匹配；上传时间不能替代业务形成时间。

**退出条件**：请求依据、完成证明及关键数据的来源、匹配和约束可解释，剩余缺口定位到原对象；字段齐全不等于来源充分。

## 5. 异常：对新义务重复同一循环

逐项、递归核对适用异常，责任终点与准入归 [追责结束](responsibility-closure.md)。已明确异常立即吸收，不为了顺序延迟记录。

异常产生新义务时，先画请求—确认，再追依据、期限与完成证明，再查各层异常。退款、赔付或外部接手不等于结束，每条分支须到达人类确认、有依据的终点。全部主履约、条件义务、兄弟分支和未决项持续参与判断，同一合同的已知部分可以先写模型，但不能将局部当成整个合同完整而交付下游；独立合同完整闭合后可分范围交付。

每轮展示聚焦当前合同、履约及一个请求或确认中的业务判断。多凭证并行不等于展开其他合同全部责任，具体形式由 Discovery 维护。

## 6. 用单据推演检验理解

主要凭证链可解释时，选正常业务与相关争议按真实角色走一遍，异常分支也须核对。优先用脱敏单据，无实例时明确为合成，不伪造已发生事件。每一步只使用当时已有的凭证，检验能否判断责任与完成。

金额、版本、时刻或责任受到质疑时，应能追回原约定；缺什么就回原对象，不临时增加审批或赔偿。记录实际结果与未决项，未执行不声称通过。对话推演不需要正式模型或 Python，不等于机器模拟，见 [场景校验](scenario-validation.md)。

## 7. 核对参与者与角色扮演关系

合同入口已明确的主体与角色继续复用。沿具体履约、单据及跨上下文协作补全同一性与代表关系，不等 API 设计再补，也不以合同或单据推演为前提处理纯领域和独立协商身份。

1. **从责任定位角色**：在哪个上下文，对什么要求或凭证承担责任，责任身份与提供方分开。
2. **寻找实际主体**：已知个人或组织立即吸收，未知不制造主体补槽位。
3. **核对跨上下文同一性**：稳定身份是否支持同一主体；同名不能证明同一，不同角色名也不证明不同主体。
4. **区分代表与责任主体**：谁代表谁办理，依据是什么，不扩展全部操作权限。
5. **形成有依据的对应关系**：核对主体、角色、同一性及代表依据的对应关系；已有对象直接引用，有编辑授权时由 FM 保存真实 `plays_role`，未知玩家不造主体。

未知实际主体不抹去已知凭证链，可以只维护明确的责任角色；责任角色未知暂不写凭证。必要未知影响范围完整性时阻塞受影响下游，不阻止其他已知表达保存。

## 8. 从实际差异发现变化点与边界

比较有依据的不同主体、渠道、证明或领域能力，判断哪些责任不变，哪些前提与采信条件变化。先有具体案例再抽模式，不征集无边界未来功能，不让业务方填写 Evidence Role 技术槽位。只有一个案例时，复用保持假设。

业务（Business）具有运营特定、领域中立的倾向，规则来自经营、交换权责或内部目标约定；领域（Domain）具有运营中立、领域特定的倾向，复杂度来自问题自身知识、约束或算法。这是分析逻辑的视角，不给整个功能模块强制二选一，也不直接决定部署方案。

边界存在疑问时，拆开具体运营责任、专业能力和工具，检验改变运营方式后哪些责任变化、替换经营对象后哪些责任仍可复用。真实差异优先；假设只作反例，不能把假设当成现行事实，也不要求业务方另设计一套运营模式。

合同按实际约定与责任关系判断；领域须说明对象、专业规则及能力范围；协商须有真实方案与拟形成的约定。没有收费或书面合同不证明属于领域，有对象和规则也不证明属于领域。混合则拆开，必要依据未知则保留问题，不把功能清单直接当上下文，不为工具另造上下文。

同一条款可以同时说明合同责任和领域规则，不因划入领域而删除合同责任。账户对象不是责任主体，成熟能力的结果不自动成为履约完成证明。更正边界时核对受影响约定、判断和确认，不静默迁移责任。

当前只消费支撑方结果时，保留其证明含义、真实责任、采信条件和消费边界；不要求展开所有供应商内部业务。内部规则影响当前判断或属于授权范围时才深入。

## 9. 领域对象与渠道协商走各自分支

### 领域对象

从已有方案与当前业务连接点进入，按 [领域建模](domain-modeling.md) 优先复用成熟知识和能力，必要时深入身份、属性、关系与规则，不要求合同或凭证。客户主体与档案、独立联系方式与普通属性须区分；身份、基数、资格、合并及授权是业务知识，不用数据库主键替代。

规则和版本须有依据，不编公式；代码只证明当前行为。FM 对操作、状态迁移、复杂算法或关系实例数量表达不足时保留能力限制，不造 Evidence／Fulfillment 来宣称已模拟。

### 渠道协商

沿真实邀请、报价、方案及回应识别双方、标的、有效时间和接受依据。RFP → Proposal → Contract 是可能主线，不是固定流水线；固定套餐不补 RFP，报价未接受不补合同，签约前协商不伪装成履约。

合同只消费形成它的最终约定与必要追溯，不搬入渠道全部过程；形成条件确实影响当前义务、期限或版本时才深入。

### 工具／胶水

只有技术调用或简单集成时，说明实际用途，不补造合同、凭证或上下文。存在独立领域规则时按该规则分析，不仅凭工具名称排除责任或领域问题。

## 10. 将发现交给正式表达

发现形成当前业务理解，不是第二份正式 FM。术语名称与含义归 [领域语言](domain-language.md) 的唯一拥有者。

有依据且获授权时，按 [渐进保存与责任范围方法](responsibility-closure.md) 让凭证、责任角色与上下文共同落地，逐批检查一致性；范围结束才核对完整责任图、终点、推演、人类确认与范围完整性。相关未澄清合同使用 Context Role，必要外部证明仍须查清，整体范围与未决项继续保留；全局结束另核对人类确认。每批按 [批次评估](batch-assessment.md) 映射已知对象、关联、规则与场景，不用技术表达或范围排除制造通过。
