# 领域语言的单一拥有者

领域语言用于日常讨论、需求和交付表达，在访谈中持续沉淀，不等待所有问题解决。同一概念只维护一份名称与含义：已建模概念归 FM 对象，未建模概念和无独立模型对象的术语归 Glossary。此方法由 FM 维护；提问与控制状态由访谈任务维护。

## 存储与权威

`.evidence/glossary.json` 是统一术语入口，位于 FM 类型根之外，使用 [glossary.schema.json](../schemas/glossary.schema.json) 定义的严格 JSON。用户指定其他 JSON 路径时沿用该位置；不创建 Markdown 词典、CONTEXT.md 或双格式副本。

两种条目互斥：

- `kind: standalone`：尚无对应 FM 对象的明确概念，或通用术语。必填 `id/name/definition`，可选 `context/aliases/distinctions`。未决解释继续澄清，不把 Agent 建议当定论。
- `kind: model`：已建模概念。必填 `id/target`，可选别名 `aliases`；不得保存 `name/definition/context/distinctions`，也不以任意附加字段补写独立含义。名称、含义与上下文从当前 FM 目标解析。

`target.objectRef` 使用 Entity、Relationship 或 Rule 的稳定 ID；Entity 属性再以 `target.attribute` 指定属性名，不使用文件路径或数组下标。对象搬家不改变引用；属性改名需按授权修复引用。规范名称取 `label`，Entity／Relationship 的业务含义取 `notes`，Rule 取 `description`，属性取 `meaning`。目标缺少业务说明时报告缺口，不用名称充当定义，也不在 Glossary 中补一份。

`term.*` 是词汇入口的稳定身份，不是 Entity ID。一个目标只有一个词汇条目，多个叫法放入 `aliases`；不为术语编造 Entity ID、角色、期限或权限。相同名字在不同业务上下文可以有不同含义，不能按名称自动合并业务身份。

## 双语规范名称

业务概念使用完整的 `中文（英文）`，采用全角括号，每次使用都保持同一个名称，不只在首次出现时附英文。中文、英文和别名指向同一个稳定 ID，不是三个概念，也不另建英文词典或独立英文字段。

- standalone 的 `name` 保存完整名称；model 的名称来自当前 FM 对象或属性的 `label`，词汇引用不复制名称与定义。现有字符串字段承载双语名称，`schemaVersion` 不变。
- 英文优先复用已有规范映射；没有映射且业务含义明确时，由 Agent 根据当前上下文直接翻译英文，不等待人类提供或确认英文名称。采用简短、准确的业务表达，同一概念保持同一译名；不从 ID、文件名或代码标识反推业务含义。
- 只有概念含义或中文叫法存在业务歧义时才澄清该歧义，不将翻译作为业务问题。英文业务名称、稳定 ID 和实现标识分别处理；直接翻译不自动修改 `term.*`、Entity ID、属性名或接口字段。已有单语 FM 标签可在对话中直接展示双语名称，源标签更新仍交定义拥有者并遵守模型编辑授权，不借术语任务改模型。
- 人名、机构的法定名称、原文引用、现有代码和外部协议名称保留实际叫法；责任角色及其他业务概念直接译为双语规范名称。

统一语言也表达责任与业务判断：定义说明概念是什么、由谁承担什么责任或证明什么，必要时区分它与其他概念的关系。共同业务依据可以解释多个数据项，但不让“凭证存在”“金额已经记录”或“用户故事已验收”替代证明边界。关系与规则的正式定义仍归 FM，不在词汇表复制责任图或记录访谈进度。

## 日常表达

提到业务概念时先核对当前上下文的叫法，让问答、需求和实现讨论指向同一个概念，不把词汇表只当作保存产物。

- 按项目指定入口同时检索完整双语名称、中文部分、英文部分、`aliases`、上下文或目标，读取命中条目；英文大小写及空白归一只用于检索，不改规范名称。已建模上下文的名称、双语部分和别名先解析为当前 Context ID，再核对身份；多命中保留歧义，不按翻译或同名自动合并。model 条目同时解析当前 FM 目标。只读相关概念，已加载且未变化的内容可以复用。没有词汇入口时沿用材料中已明确的中文叫法并直接翻译英文，不自动创建词汇表；纯技术讨论不强行引入业务术语。
- 输出使用完整的中文（英文）规范名称：standalone 取 `name`，model 取当前目标的 `label`。`aliases` 用于理解输入与检索，同一概念在叙述中不轮换同义词。首次遇到不熟悉的叫法时可以简短说明对应关系，后续直接用规范名称，不反复展开定义或附加词汇清单。
- 当前位置、追溯故事、问题、需求故事、验收条件、任务标题、诊断假设、测试名称、审查意见和交接都沿用规范名称。英文代码与字段使用项目已有映射；业务名称缺英文时按明确含义直接翻译，不以显示译名自动重命名实现标识；稳定 ID 仍按各自身份规则使用，不因显示名称调整而变化。
- 同名异义按上下文区分，需要时加简短上下文限定。输入叫法有多个可能含义，或与当前定义冲突时，指出具体差异；澄清只在当前任务允许的分支进行，不按出现频率合并，也不替用户决定新含义。含义尚未明确的新叫法作为未决术语交接；仅缺英文不构成未决业务问题。
- 原文引用、既有代码标识、API 字段及外部协议名称保留原样，解释时说明对应概念。不批量改名，不改写历史证据，也不为语言统一擅自改变接口契约。使用术语不扩大写入权限：只读请求仍不写文件，术语缺口交定义拥有者，待保存或待更正的内容明确为未保存。

输出前核对同一概念是否保持同一规范名称、已有规范映射是否复用、明确含义是否直接译为英文、上下文是否准确、必要业务未知是否保留。命名漂移、同名异义、只读或缺词边界首次出现时，按需看 [日常表达样例](../examples/domain-language.md)。语言一致性由实际表达核对，词汇结构检查不证明 Agent 已遵守这些要求。

## 每轮访谈

1. **定位定义拥有者。** 沿 [业务分析主线](business-analysis.md) 的可读视图处理受影响术语；独立术语任务只处理本次术语。按名称、别名、上下文或目标检索入口，读取匹配条目及其当前 FM 目标，核对含义由谁维护。用户明确的事实直接复用，沉默不等于同意。完成时，能区分新概念、已有定义和同名异义。
2. **澄清概念边界。** 对模糊或过载叫法核对其业务含义与区别；假设案例只用于检验理解，合成内容不作事实。已有来源冲突先指出差异，未澄清不任选其一覆盖；代码只证明实现行为。完成时，定义有明确业务依据，或必要未知与冲突具体可见。
3. **当轮沉淀明确术语。** 依据本轮已明确的业务含义，当轮维护词汇入口：未建模概念写 standalone，已建模概念写 model 引用。standalone 定义简短说明概念是什么及其边界，name 复用规范映射或按明确含义直接翻译为双语名称，其他叫法归 aliases，易混概念归 distinctions；model 仍只引用当前定义，单语目标的源标签更正交定义拥有者。完成时，受影响条目实际保存成功，或没有变化而无需写入。
4. **按归属处理更正。** 已建模概念的更正属于 FM 修改。仅有访谈授权时，说明更正、目标定位与待改影响，不建立同义 standalone 或在引用中覆盖定义；取得覆盖当前业务的人类追责结束依据及模型编辑授权后才更新目标。完成时，更正已按授权保存，或待改目标及影响已交接，来源与未受影响事实保留。
5. **核对结果后交回访谈。** 分别核对本轮条目、定义拥有者与各文件实际保存结果。保存本轮结果后再继续访谈，失败立即交接未保存内容并停止。完成时，保存结果、必要未决项及下一步边界准确，提问与等待仍归访谈任务。

当轮维护不要求每轮全文重读词汇表、全部 FM 或方法。已加载且未变化、仍在上下文的方法可以复用；写入前核对实际条目，目标变化或含义冲突时沿关联扩大读取，无法确认新鲜度时重读必要来源。没有受影响术语时不制造空更新，不因增量读取跳过新增概念的去重与定义归属核对。

“访谈并沉淀领域语言”只授权 standalone 条目和已有 FM 的引用索引，不授权修改模型 JSON、关系、规则、场景、API 或实现。只聊不落盘、仅保存资料、只记录冲突和只读校验等更窄要求优先。文本沉淀不要求安装 Python，也不能声称整个 FM 已通过校验。

## 从术语落实为模型

将术语落实为正式对象也是模型编辑：先按 [全部追责结束](responsibility-closure.md) 核对人类确认及其覆盖版本，再核对模型生成／修改授权，才可执行相应词汇条目的归位：

1. 核对 standalone 的来源、上下文和已有 FM，判断是新概念还是已有对象；不是每个词都要创建 Entity。
2. 在获授权 FM 目标中完整落实名称与业务含义，保留源依据、已有补充说明及稳定对象 ID；关系或规则仍须有独立业务依据。
3. 保留原 `term.*`，将条目替换为 model 引用并移除其名称、定义、上下文与区别正文；必要的原叫法保留为别名。名称、含义归 FM 唯一维护。
4. 检查新引用并执行适用 FM 校验。FM 目标变化后，重新解析自动得到当前名称与含义，不反向回写 Glossary。目标删除或属性改名导致悬空时明确失败，不从历史定义兜底。

多文件更新不宣称原子事务。任一保存失败就停止，分别交接词汇表及获授权 FM 文件的实际保存结果；恢复先核对内容，再补齐缺失写入，不能把部分归位当完成或继续追问。

## JSON 契约与读取

根对象为 `schemaVersion: "2.0"` 和 `terms` 数组。UTF-8、两空格缩进、末尾单个换行；拒绝注释、尾随逗号、重复键、非对象根、多文档及 NaN／Infinity。条目表达业务含义与定义归属；现有可选 `sourceRefs` 保留为内部依据引用，不写进名称或定义正文，不在日常描述中附资料出处。新增术语按明确含义维护，不将当前位置、问题、回答状态或来源链进度写入词汇表。

以下为合成格式示例，引用目标须在实际项目存在：

```json
{
  "schemaVersion": "2.0",
  "terms": [
    {
      "id": "term.receipt",
      "kind": "model",
      "target": { "objectRef": "confirmation.receipt" }
    },
    {
      "id": "term.business-day",
      "kind": "standalone",
      "name": "业务日（Business Day）",
      "definition": "双方约定的业务统计日，不等同于自然日。"
    }
  ]
}
```

通过只读检查器解析当前词汇入口：

```bash
"$PYTHON" "$FM_SKILL_DIR/scripts/check_glossary.py" "$PROJECT_ROOT/.evidence/glossary.json" --fm "$PROJECT_ROOT/.evidence/fm"
```

默认探测词汇表同级 `fm/`；纯 standalone 且尚无 FM 时可独立校验，存在 model 引用则必须提供有效 FM。检查器需要 Python 3.10+ 和本包 jsonschema 依赖，检查严格 JSON、互斥结构、重复 ID／目标、悬空对象／属性及目标说明。它还检查双语规范名称，拒绝同上下文中文或英文部分重复的名称，并将上下文名称解析为 Context ID 后检查 standalone 是否与 FM 名称、别名或属性重复。上下文名称有歧义则失败，不任选一个。旧单语名称报告缺口，不自动迁移。名称匹配不能证明全部概念已经去重，别名和跨上下文身份仍须按业务依据判断。

使用 `--query "<中文、英文、完整名称或别名>"` 可只读检索，`--context "<上下文 ID 或名称>"` 可限制范围。完整名称和语言部分均做精确匹配，不以片段或模糊翻译判定身份；返回全部 `matches`，多命中不自动选取。别名歧义保留待核对，不合并定义。

`resolvedTerms` 是本次只读解析结果，不是第二份可编辑词典；其中 `context` 为解析后的身份，`contextNames` 为当前上下文的只读检索名称，不回写业务源。失败不返回可用结果。`glossaryDigest` 和 `fmSourceDigest` 分别绑定输入，输入改变使结果失效。`referenceValidated` 表示对所读 FM 类型源的结构与引用检查，未读取 FM 时为 null；不等于整套 FM 的规则／场景通过，也不证明来源充分或业务批准。

## 交接

只列增改的 `term.*`、定义拥有者、来源、更正影响及各文件保存结果。standalone 的定义正文在词汇表，model 的定义正文在 FM；访谈展示和审核页只引用或投影，不另存可编辑副本。停止不扩大权限，历史来源与未决更正不删除。
