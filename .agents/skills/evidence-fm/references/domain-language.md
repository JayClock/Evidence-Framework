# 增量沉淀领域语言

领域语言是持续设计的一部分，不等到访谈结束或源 JSON 齐全才记录。此方法由 FM 维护，访谈任务消费它；它不规定提问轮次，也不接管问答状态。

## 单一词汇表与权限

唯一词汇表使用严格 JSON，默认位于项目根 `.evidence/glossary.json`；用户指定其他 JSON 路径时沿用该位置，但必须位于 FM 类型根之外。首次有明确术语时才创建。它是人工维护的领域语言来源，不是从模型 JSON 重建的报告，不创建 Markdown 词典、CONTEXT.md 或双格式副本。

“访谈并沉淀领域语言”授权更新发现记录与统一词汇表，不授权修改模型 JSON、关系、规则、验证场景、API 或实现。只聊不落盘、仅保存资料、只记录冲突和只读校验等更窄要求优先；不以默认目录扩大权限。仅更新术语不要求安装 Python、创建 model.json 或运行单据模拟，也不能声称整个 FM 已通过校验。

## 从回答中形成术语

1. 读取本次来源与词汇表相关条目，核对名称、含义和适用上下文。用户已经明确表达的含义直接复用，不重复索取确认；用户沉默不等于同意 Agent 的提议。
2. 对模糊词、同名异义和近义词指出具体区别。用合成的正常或边界案例检验概念身份、范围及排除项；标明案例是假设，不能作为真实业务依据。业务问题由访谈任务逐问。
3. 依据足够时当轮更新词汇表，不等待所有问题解决。保留规范名称、业务含义、适用上下文、必要的别名／易混淆概念与来源定位。仅在已有模型 ID 时引用它，不为术语编造 Entity ID、角色、期限或权限。
4. 未明确的定义、Agent 建议及冲突留在发现记录，词汇表只引用待澄清定位，不把候选解释写成定论。不同上下文可以使用不同含义，不能为统一名称强行合并概念。

## JSON 契约

格式由 [glossary.schema.json](../schemas/glossary.schema.json) 定义，与 FM Schema v3 分开：

- 根对象只含 `schemaVersion: "1.0"` 与 `terms` 数组。
- 每项必填 `id`、`name`、`definition`、`sourceRefs`。`id` 使用独立的稳定 `term.*` 标识，不是 Entity ID；改名不改 ID，不复用已撤回条目标识。
- `context` 记录有依据的业务适用范围；同名不同含义须用不同上下文区分。可选 `aliases`、`distinctions`、`modelRefs` 只写已知内容，不填空串、null 或假模型引用。
- `sourceRefs` 指向原始材料、回答定位或已保存的更正依据；来源在 Git 历史中时用完整提交标识、路径和定位引用，不能把 Agent 建议标为人工确认。
- 同一 ID 只能出现一次，同一 `context` 内的 `name` 不重复。定义只在这里维护，发现记录引用 `term.*`；未决解释仍在发现记录。
- UTF-8、两空格缩进、文件末尾单个换行；拒绝注释、尾随逗号、重复键、非对象根、多文档及 NaN／Infinity。

以下为格式用的合成示例，不是项目业务事实：

```json
{
  "schemaVersion": "1.0",
  "terms": [
    {
      "id": "term.receipt",
      "name": "收件回执",
      "definition": "证明材料已收到，不证明质量合格。",
      "context": "材料接收",
      "sourceRefs": ["材料路径#回答定位"]
    }
  ]
}
```

可使用独立只读检查器，不要求存在 model.json：

```bash
"$PYTHON" "$FM_SKILL_DIR/scripts/check_glossary.py" "$PROJECT_ROOT/.evidence/glossary.json"
```

检查器需要 Python 3.10+ 和本包 jsonschema 依赖，只校验严格 JSON、结构和重复标识／同上下文名称，返回 `glossaryDigest`、`inputChanged` 与真实错误，不写文件。结构通过不证明来源充分、引用可达或业务含义正确；缺少运行环境时可继续文本沉淀，但明确未执行机器检查。

## 更正、冲突与写入失败

来源记录先保存原话和更正依据，再更新术语。更正保留旧依据和受影响条目定位，不抹掉旧回答。已有定义与新说法冲突时，先明确双方依据及具体差异；未澄清不任选其一覆盖。含义明确更正后更新同一条目，发现记录保留更正链。

核对相关模型、需求或代码是否仍使用另一种含义。代码只证明当前实现，不裁决业务；引用具体冲突并登记影响，不为了对齐术语静默改写 JSON、规则、验收或代码。后续模型编辑必须消费最新词汇表及来源，不能从旧 JSON 反向覆盖新术语。

发现记录与词汇表是两次文件写入，不宣称原子事务。任一保存失败就停止推进，交接已保存和未保存的文件、条目及来源；恢复时先核对两边实际内容、补齐获授权的缺失写入，再继续访谈，不重复创建条目或原话。

## 每轮检查与交接

核对 JSON 是否符合独立词汇表契约、定义是否有来源、上下文是否明确、概念是否误合并、待定内容是否仍留在发现记录，以及实际差异是否只涉及获授权文件。交接只列词汇表路径、增改条目、来源、冲突与保存结果；定义正文只维护在词汇表。术语明确不等于模型完整、机器通过或具名业务批准。
