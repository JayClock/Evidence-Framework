# 业务来源追溯与凭证时间

## 从业务骨架进入追溯

合同履约按 [业务分析](business-analysis.md) 从约定与责任双方进入，用已知主要履约检验理解并画当前请求—确认，再追要求与结果中的关键数据。骨架不是完备证据链，缺口不抹去已知义务。外部凭证揭示另一组独立约定时增量补充责任与协作，保持当前焦点，不先展开支撑合同全部内部责任；当前主履约清单持续补全，正式编辑前核对完整。领域与渠道从各自对象或协商凭证进入，不强造履约。

合同的约定参数与后续实际结果分开：价格、比例或周期须追溯到有效约定，实付、实交及确认时刻须追溯到结果凭证。请求可引用早于它的合同、方案或其他履约凭证，引用不自动确定时间先后；追溯不限定在请求与确认之间，也不要求固定的中间单据。

## 业务来源追溯的统一循环

**所有关键数据都先追溯业务来源，不以“Agent 觉得需要派生”为入口。** 金额、数量、比例、六类凭证时间和领域结论都适用；类型展开、直接输入和派生计算都在同一个循环内。

```text
定位当前请求／确认或领域／协商对象中的关键数据
→ 展开必要类型含义，不先填通用字段表
→ 复用材料与最新回答，追溯业务来源
→ 区分直接记录、引用已有值、规则派生、来源待明确
→ 保存依据、候选关系、具体缺口
→ 已知则复用或推导，影响当前判断的未知形成具体缺口
→ 输入更正或案例暴露问题时，沿原对象继续追溯
```

从关键值定位原凭证或对象属性及其版本，核对是谁提供、请求或确认、证明哪个业务结果，沿引用关系或派生输入追到有效约定和规则。关联涉及的参与者或 Thing 标的，检查先后关系及当时可见性。依据不足时保存具体缺口，不为结构完整制造对象或“证明凭证的另一张凭证”。

## 一个业务焦点的多凭证深度追溯

每条来源链深度优先，多个凭证可以并行追溯。以当前业务判断为主焦点，从所需关键数据进入直接依据，再追该依据的必要数据、形成条件或适用约定；到达有业务依据的可解释来源后，回到上层判断核对该来源是否足以支撑原结论。不先扫完同一层凭证再统一深入，也不要求一条链全部结束后才能启动独立链。

同一凭证可以有多条来源链，同时承载金额、数量、版本、身份和时间等关键数据。统一循环对各项数据分别成立，但不要求逐字段问到底；相关凭证也不是互不关联的问卷。先找共同业务依据，再推进前置充分的独立分支。

分析时保留各数据项的来源、证明作用、必要输入与尚未明确的依赖。多项或多凭证共享同一约定、凭证或版本时，共同依据只追一次，再分别核对其适用关系；同一凭证不保证所有数据有相同来源。某项需要另一个未知答案才能确定时，先处理该前提；其他独立来源链可在当前授权内继续。部分回答、更正和逐项暂缓只更新受影响范围，然后重算依赖，不抹掉其他已知依据。

责任定位属于各自凭证：保留主焦点与各活跃链的凭证、所属合同／上下文、履约及端点或形成对象、关键数据、责任角色与已明确实际主体、当前深层位置和上层回溯关系。支撑凭证保留其真实形成上下文，来源深入不改变主焦点。责任身份区别于提供某个数据或证明的主体，不从上传人、受益者或上层角色推断责任；尚未明确就保留缺口，不补造主体。

来源共享以实际凭证身份、适用版本和证明范围为依据，同名或别名不证明同一节点。已解释的依据复用，输入更正后沿所有依赖它的分支核对影响。循环引用不能自证：活动路径再次遇到同一节点时指出环路及缺失的独立依据，不重复展开或制造新凭证；不同版本仍分别核对，不能把旧版本答案复用到新版本。

来源可解释只是分析终点，不是凭证已形成、履约完成或责任追究终点。没有可问前沿也可能只是等待答案、缺材料或暂缓，不能据此宣称全部追责结束。

例如，合成的退款请求（Refund Request）中，实付金额（Paid Amount）由支付凭证（Payment Evidence）证明，应退金额（Refund Amount）由退款约定（Refund Terms）决定；两项需要共同的原订单（Original Order）匹配。先核对该匹配，再沿各自来源推进，实付金额不自动等于应退金额。来源查清不说明退款已经完成，也不代替正式追责结束或编辑授权。

当前展示和提问由 Discovery 协议维护；来源链是分析关系，不写成 Glossary 的访谈状态，不新建第二份问题记录。

## 来源核对与映射结果

| 追溯结果                   | 保存与处理                                                                       |
| -------------------------- | -------------------------------------------------------------------------------- |
| 直接记录的事实或逐次约定值 | 保留提供方、记录事实及约定依据的已知部分；依据充分就复用，不强造计算公式         |
| 引用已有值                 | 保留原凭证／对象属性、适用版本和当时可见性；不能把复制后的字段当作无来源独立输入 |
| 规则派生                   | 追溯输入与规则、适用条件；完整则保存确定性推导，不问谁手工填写派生值             |
| 来源待明确                 | 保留字段已存在这一事实和未知；可说明候选关系，但不默认自由输入或先编公式         |

这些是发现说明中的业务区分，不新增 Schema 枚举、字段或状态机。记录属性、来源、形成口径、推断理由、剩余缺口及影响。按当前对象与本轮来源变化范围继续，不逐轮重扫所有已明确属性；定稿时覆盖本批次关键数据和未决缺口。

**公式可以没有，业务来源不能由字段存在代替。** 不必等材料写“计算”或用户要求自动化。将推断与已明确事实分开，不把推断写成已确认公式；关系未明先核实关系，来源性质尚未确定时，将“依据什么确定”标为待澄清点，不预设算法、固定时长或起算事件。人工明确为非派生输入后应保留该事实；仍需核实的口径交给访谈任务，不由来源核对流程自行发起问答。

没有公式不等于允许自由输入。asserted／derived 是表达分类，不是业务来源已查明的证明；类型字段、合成实例、机器 lineage 通过都不能替代缺失依据。已有问题的解决解释也不能代替业务来源：不能只引用“规定时间内付款”就宣称来源已解决。

业务规则不交 Architecture 自定，数据库表、日志、接口字段等物理记录映射留到 Architecture。追溯是 Agent 的分析责任，不是逐字段问卷：先补读和复用，按当前职责的必要依赖判定缺口影响；非阻塞未知仍如实保留，不声称追溯已完整。

跨主线复用：

- 身份、承诺、代表关系已明确就复用，不为 Party／Role 技术槽位重复问职责。
- 确认提供方、证明结果与采信口径已明确就记录，不额外发明审批人或记录人。
- 金额基数、比例与规则已明确就计算，币种、舍入、扣减等实际影响结果且未知的口径才问，不凭空制造冲突。
- 身份与唯一性已明确就复用，业务基数、授权与冲突规则仍属业务知识。
- 真实报价、版本、接受依据直接吸收，不为固定套餐补造 RFP。
- 已有异常触发、补偿及人类终点确认就复用；新增义务的各层异常仍按 [全部追责结束](responsibility-closure.md) 递归追查，不设深度上限。仅说“外部处理”不等于终点。
- 尚无真实实例时可构造标为合成的校验数据，预期来自真实规则或确定性推导，不冒充已发生事件或人工批准。

## 从首轮展开凭证类型时间

识别到凭证即展开类型含义，不等到定稿才补查：

| Evidence kind                            | 类型必备时间               |
| ---------------------------------------- | -------------------------- |
| `rfp`、`proposal`、`fulfillment_request` | `started_at`、`expired_at` |
| `contract`                               | `signed_at`                |
| `fulfillment_confirmation`               | `confirmed_at`             |
| `other_evidence`                         | `created_at`               |

**类型展开是业务来源追溯的起点，不是完成条件。** 类型属性定义、实例时间值、额外生成规则是三个层次。类型建模不要求先有实例值或生成公式；每个请求实例仍须有确定截止时间，不允许无期限或 `openEndedReason`。

| 已识别凭证               | 类型时间含义                                           | 不由类型推出的事实                                             |
| ------------------------ | ------------------------------------------------------ | -------------------------------------------------------------- |
| rfp                      | 邀请的开始时间 started_at、回应截止时间 expired_at     | 不默认开始等于编辑、发送或送达时刻                             |
| proposal                 | 方案的有效开始时间 started_at、有效截止时间 expired_at | 不默认开始等于发出，接受不自动等于签约                         |
| fulfillment_request      | 本次请求的开始时间 started_at、截止时间 expired_at     | 不默认从下单起算，不赋予任意设定期限的权限                     |
| contract                 | 该合同的签约时间 signed_at                             | 不等同于订单创建或权益生效，不认定哪种行为构成签约             |
| fulfillment_confirmation | 该凭证的履约确认时间 confirmed_at                      | 不自动改成回调到达或入库时间，不推定提供方、采信规则或全额完成 |
| other_evidence           | 该凭证的形成时间 created_at                            | 不等于其记载的原事件时间，不把形成更正凭证当作原事件重发生     |

以上六类都不为展开时间属性索取实际日期、生成公式或“哪个系统／谁记录字段”，不再造一张证明时间的凭证。类型含义与来源解释保存在发现说明，不新建发现 DSL。signed_at／confirmed_at／created_at 是时刻属性，不额外补请求区间或有效期。

保留实际签署行为、确认采信、凭证形成晚于原事件等有来源事实；没有真实歧义不发明竞争事件，也不能把一个自由 timestamp 参数当成解决依据。提供方和证明作用的缺口与“时间属性未展开”分开。

### 同一循环中的付款期限示例

以下只说明方法，不提供当前业务事实或默认72小时期限：

- 来源未知：只写“规定时间内付款”且已识别付款请求时，保留 started_at／expired_at，以及“以本次请求的 expired_at 为准；确定依据待明确”。这只表达类型含义，不证明期限来源已查明。若要判断逾期作废，就将“付款请求截止时间的确定依据”作为具体缺口交给访谈，不预设起点加固定时长。
- 直接记录或引用明确：双方逐笔协商截止，或沿用已接受方案的截止，保存原约定、提供方与适用关系的已知部分，不索取统一公式，不授予任意改期权限。
- 派生已明确：按索引补读相关明细，不重新询问已经明确的事实。凭证类型、时间业务含义及计算依据已明确时，直接复用对应属性，保存规则、原始材料和最新有效回答的来源。
- 真有起点、工作日或采信歧义时，说明具体歧义及影响，交给访谈处理。不能仅凭 kind 推断时间起点与外部事件的对应关系，不在材料之外臆造创建、发出、送达等竞争起点。

例如已有材料明确“平台发起付款就是付款请求开始；72小时后截止；以支付机构确认扣款成功时间判断，等于截止也按时”，就保存 `付款请求.expired_at = 付款请求.started_at + 72小时` 和 `支付确认.confirmed_at ≤ 付款请求.expired_at`，不再问起点来自哪条记录。

谁提供何种凭证、凭证中的时间证明哪个业务事件，在尚不明确且影响结果时仍须核实。业务含义已明确时，不再问“实际以哪条业务记录为准”或谁记录字段。

**是否阻塞取决于业务依据缺口的影响，不取决于有没有公式。** 已知类型语义不因未给时长退回 null；来源未知仍须保留，不能用类型展开关闭真实的期限确定依据问题。类型模型的非派生时间属性无需 derivedByRuleRef，实际实例缺 required 时间值仍校验失败。

最终 Entity 源 JSON 的 `attributes` 须显式定义各类型的对应名称，统一 `valueType: timestamp`、`required: true`、`keyData: true`，说明 meaning 与来源／派生规则。业务属性用 snake_case；不能仅写在说明里或让编译器补齐。Request 本身的 started_at／expired_at 构成区间；实例提供确定的 RFC 3339 时间值。类型必备属性不互换，领域对象不套 Evidence 时间表。

## 映射到正式模型

取得覆盖当前范围的人类追责结束依据与编辑授权后，正式内容按已明确的业务依据与实际 Entity ID、属性名、Rule ID 对齐，模型说明解释其业务依据及适用条件。工作理解不是已确认模型，需重新核对其所依赖的事实，而不是把整个访谈摘要复制成模型依据。

直接或引用值保留提供依据和适用关系；派生输入与规则映射到 Entity Attribute 和 CEL，依赖由 AST 提取。keyData、derivedByRuleRef、集合 binding、标量输入限制及机器 lineage 见 [追溯与模拟](traceability-and-simulation.md)，JSON 类型要求见 [格式](format.md)。来源说明不新增 Schema 枚举，也不手写第二份依赖清单。

## 核对业务依据

解释每项结论依赖的约定、凭证、规则及适用版本，区分事实、推导、候选与未知。关键数据的来源指业务形成依据与证明作用；核对已有材料及本轮明确回答即可。

更正后沿依赖重新核对受影响结论、问题解决依据及场景预期。正式表达按本轮授权更新，必要依据缺失时交接具体判断缺口。
