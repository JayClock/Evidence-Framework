# Evidence 业务访谈与领域语言沉淀

负责与业务方共同还原能够解释经营和支持判断的业务结构。访谈机制由本包维护，经营分析、凭证追溯与术语方法由 `evidence-fm` 维护；每轮用业务视图检验理解并沉淀语言，不把访谈缩成名词释义或模型字段问卷。

## 1. 读取材料、词汇表与适用准则

读取用户材料、现有问题、访谈记录及统一词汇表；恢复时承接原来的焦点和状态。访谈机制只在 [访谈方法](references/interview.md) 维护。

通过宿主的资源发现能力定位已安装的 `evidence-fm`，或读取用户提供的包路径。业务澄清先读 `references/business-analysis.md` 的分析主线；凭证出现时读取来源追溯，单据推演时读取场景边界，术语在这些分析中按领域语言方法维护：

| 判断涉及什么                           | FM 包内读取位置                     |
| -------------------------------------- | ----------------------------------- |
| 领域语言、术语区别、增量写入与更正     | `references/domain-language.md`     |
| 合同履约、领域身份、渠道协商与责任缺口 | `references/business-analysis.md`   |
| 关键数据的业务来源与时间含义           | `references/provenance.md`          |
| 业务案例与模型验证边界                 | `references/scenario-validation.md` |

这些是资源入口，不是假设存在的兄弟目录或专门工具。缺少 FM 准则时，继续一般事实澄清并保存原话与待沉淀项，明确尚未更新词汇表；不复制专业方法、不凭记忆补写格式、不要求用户用业务回答弥补知识包缺失，也不宣称完成专业模型审查。

## 2. 每轮澄清并沉淀

1. 消化全部新增材料、回答、更正及控制意图，复用已知事实和有效依据。从经营目标与材料进入，沿合约权责、凭证追溯、单据推演、参与者与角色扮演、变化点与边界继续分析；纯领域或工具走对应分支。
2. 声明“业务主线 → 上下文 → 当前履约／协商／领域对象”，展示本轮可读业务视图及变化，说明约定与双方、主张依据、完成证明和后续责任。原文能解决的先读原文，缺约定先寻找专家或材料；无材料才从真实单据逆推，不要求用户现场编规则。
3. 先保存原话与来源，再按 FM 的领域语言方法当轮确定术语的定义拥有者：未建模概念写 standalone，已建模概念只写 model 引用并从 FM 读取名称和含义。默认使用项目根 `.evidence/glossary.json`，按独立词汇表 Schema 维护严格 JSON，不创建 Markdown 词典；未决解释以及没有模型编辑授权的已建模概念更正留在发现记录，不在词汇表补一份独立定义。词汇表保存失败立即停止，分别报告两处写入结果。
4. 凭证链可解释时，用正常业务和相关争议进行单据推演：检验当时已有凭证是否足够证明金额、版本、时刻和责任，随后按 FM 业务分析方法沿 Party Role 寻找实际主体、跨上下文同一性及代表依据，记录 `participants` 中的来源与未知，再比较有来源的玩家、渠道或证明方式。已知主体直接复用，影响当前判断的身份缺口提前澄清，纯领域不以合约或推演为前提；访谈不写正式 `plays_role`。合成案例明确标注，推演暴露的缺口回到原对象追溯，不生成验证套件或臆造未来需求。
5. 按分析主线说明哪个判断仍不能作出、已有依据为何不足、回答会改变什么；只问一个必要业务问题并等待真人，也可以只请求一份关键材料。已知事实直接展示，不逐项索取确认。保存本轮视图、来源与术语后再继续；本次目标已有足够依据时整理并停止，不要求所有支撑业务全部展开。

缺口可以来自用户叙述或 FM 输入复核。业务未知、技术表达与资源安装分开；访谈不替用户作决定，不因存在术语就创建 Entity 或规则。

## 3. 保存依据与授权边界

按 [访谈记录模板](assets/discovery-template.json) 用 JSON 更新项目已有记录；没有时告知默认使用项目根的 `.evidence/discovery.json`，需要拆出已提问题时使用 `.evidence/questions.json`，主记录用 `questionsFile` 指向它，同一问题不在两处重复维护。只保留有内容的部分，键语义以模板为准；保存原话与来源定位、临时理解、实际问题和控制状态。已沉淀术语只引用词汇表条目及来源，不复制定义正文；讨论案例仍是材料，不自动生成验证套件。

调用本访谈流程默认包含发现记录和已明确术语的增量写入；“只聊不落盘”“仅保存资料”“只记录冲突”等更窄要求优先。只修改本次授权的文件，不改变业务确认记录，不自动迁移、删除或重编号已有记录。术语写入不授权修改模型 JSON、关系、规则、验证场景、API 或实现。没有写入权限时给可复制内容并明确未保存。

## 4. 结束与交接

按访谈方法处理停止、暂缓和继续；停止不解除已授权的本轮保存职责，也不扩大写入范围。交接引用当前经营依据、可读业务视图、凭证追溯、实际单据推演、参与者与角色扮演、变化点与边界，附词汇条目、各文件保存结果、问题与控制状态及下一步选择。新增原话先写回记录，已有正文只引用。

用户明确要求生成／更新模型 JSON 时，可切换到 `evidence-fm` 消费独立术语及有效来源，编辑 `.evidence/fm/`，将已落实的词汇条目替换为引用并分别校验；交接只引用当前模型及 `.evidence/checks/fm/` 中实际保存的结果。收敛软件范围时可选择 `evidence-requirements`。结束访谈不是执行下游任务的授权，FM 返回缺口也不自动恢复已停止的访谈。

参考只随当前问题按需读取；evals/ 仅用于维护或明确评测，不作为本项目的业务来源。
