# 单点一轮：依据、记录、展示

以下都是合成样例。实际业务按当前记录与 FM 方法分析，不照抄业务约定。

## 1. 退款约定未知：只问当前判断所需的依据

### 输入

当前焦点是订阅协议 A-1 的退款履约 R-1、请求端点。退款申请关联原支付凭证，后者记录实付金额；退款金额计算约定尚未提供。问题 Q-010 正在追溯该约定，用户要求继续。

### 记录增量

先保存本轮原话，再维护 R-1 及其追溯 T-1；已知支付凭证说明的是实付金额，不推出应退金额。Q-010 沿用原 ID 与缺口标识。术语按 FM 方法检查拥有者，未受影响条目不重写。handoff 只引用 R-1、request、T-1 和 Q-010，不复制故事，不修改正式 FM/API。

### 期望展示

```text
当前位置：订阅协议 → 退款 → 退款申请〔履约请求〕

我们正在追溯退款申请中的金额。已经找到原支付凭证，它能说明当时付了多少钱，但还不能说明应该退多少；这一步需要回到适用的退款约定。

退款金额是依据什么约定确定的？
```

### 反例与检查

- 问“谁填写金额”：把业务依据换成操作来源；问题不是数据库表或接口字段的来源。
- 同时问退款金额、期限和审批人：捆绑多个判断，还可能补造审批义务。
- 写“按实付金额全额退款”：把未提供的规则写成事实。
- 标题写“退款申请请求”：用技术分类改写业务名称。

检查端点仍是退款申请，问题只涉及计算约定，没有其他合同、金额实例、全局进度或机械缺口栏。

## 2. 回答足以确定金额，同时要求停止

### 输入

沿用上一轮记录。用户回答：“退款金额按该笔实付金额全额退还，这就是适用约定。请只保存并交接，不继续问。”

### 记录增量

先保存回答 S-003，再把 T-1 更新为按适用约定引用原实付金额；Q-010 通过该来源解决，不创建同义问题。已有访谈与术语授权下，核对词汇条目并记录各文件结果，随后保存停止意图。只涉及已建模定义时记录更正影响，不覆盖 FM。

对应的[发现记录](refund-record.json)与[词汇入口](glossary.json)展示保存后的期望结构。它们没有故事副本或全部追责结束依据；其他责任的完整记录仍保留在真实项目中，样例省略不表示删除。

### 期望展示

仅在两处实际保存均成功后使用下列交接；失败时转入控制与恢复样例。

```text
当前位置：订阅协议 → 退款 → 退款申请〔履约请求〕

退款金额的依据已经追到适用约定：按该笔实付金额全额退还。原支付凭证提供金额，约定说明为什么应退同一金额。

发现记录和词汇表均已保存。本轮停止，不再提问。
```

### 反例与检查

- 再问“具体退款多少钱”：已有依据能够确定，不应为了续问凑题。
- 保存 completionSourceRefs：停止不是全部追责结束。
- 在 handoff 保存整段故事：把展示变成第二份业务记录。

检查保存顺序、原问题解决依据、各文件真实结果和停止位置；不因局部来源已清楚自动生成模型。

## 3. 纯领域身份：不补造合同

### 输入

用户只讨论客户档案身份。已知共用手机号不能证明同一客户，足够的身份判断依据尚未明确；本轮允许澄清与记录，没有合同履约材料。

### 记录增量

原话先保存，工作理解归 domainObjects；术语归属按 FM 方法核对。焦点使用领域对象记录，省略 focusPoint，不为了显示路径制造合同、请求或凭证。

### 期望展示

```text
当前位置：客户档案 → 身份判断

我们已经知道手机号可能被共用，因此两份档案有相同手机号还不能证明它们属于同一客户。接下来需要找到业务上足以判断同一身份的依据。

实际业务依据什么判断两份档案属于同一个客户？
```

### 反例与检查

- 询问数据库主键：用技术身份替代业务判断。
- 建立“客户档案合同”：为格式补造业务。
- 默认使用证件号：把建议当成现行规则。

检查只问一个身份依据问题，不扩展销售合同、权限或全企业字典。
