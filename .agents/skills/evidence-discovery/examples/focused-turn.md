# 单点一轮：理解、追溯、展示

以下都是合成样例。实际业务按当前记录与 FM 方法分析，不照抄业务约定。业务名称及英文映射均为本样例已明确的叫法。

## 1. 退款约定未知：只问当前判断所需的依据

### 输入

当前焦点是订阅协议（Subscription Agreement）A-1 的退款（Refund）R-1、请求端点。退款申请（Refund Application）关联原支付凭证（Payment Evidence），后者记录实付金额（Paid Amount）；退款约定（Refund Terms）尚未提供。凭证责任角色是读者（Reader），实际主体未明确。问题 Q-010 正在追溯该约定，用户要求继续。

### 理解与推进

复用支付凭证（Payment Evidence）说明实付金额（Paid Amount）这一事实，继续追溯应退金额（Refund Amount）的约定。Q-010 沿用原标识；按 FM 方法核对受影响术语的定义拥有者。

### 期望展示

```text
当前位置：订阅协议（Subscription Agreement）→ 退款（Refund）→ 退款申请（Refund Application）〔履约请求〕
责任人：读者（Reader）；实际主体待明确。

业务目标：作为读者（Reader），我希望提出退款申请（Refund Application），以便按适用约定取得应退金额（Refund Amount）。

我们正在追溯退款申请（Refund Application）中的应退金额（Refund Amount）。已经找到原支付凭证（Payment Evidence），它能说明实付金额（Paid Amount），但还不能说明应该退多少；这一步需要回到适用的退款约定（Refund Terms）。

应退金额（Refund Amount）是依据什么约定确定的？
```

### 反例与检查

- 问“谁填写金额”：把业务依据换成操作来源；问题不是数据库表或接口字段的来源。
- 未核对依赖就同时问金额、期限和审批人：把未知前提捆绑成问卷，还可能补造审批义务；仅当前节点内前置充分、彼此独立的必要问题才能成组。
- 写“按实付金额（Paid Amount）全额退款”：把未提供的规则写成事实。
- 让支付机构成为当前凭证责任人：把证明提供方误当作提出退款要求的责任角色。
- 用技术分类改写业务名称，或只在首段附英文、后面轮换叫法。

检查端点仍是退款申请（Refund Application），问题只涉及计算约定，没有金额实例、全局进度或机械缺口栏。

## 2. 回答足以确定金额，同时要求停止

### 输入

沿用上一轮记录。用户回答：“按该笔实付金额全额退还，这就是适用约定。请只保存并交接，不继续问。”

### 理解与推进

回答明确全额退还约定，应退金额（Refund Amount）因此引用实付金额（Paid Amount），Q-010 对应的判断已经明确。按授权核对受影响术语，再遵守停止意图。

[词汇入口](glossary.json)展示合成术语产物；术语实际保存结果按工具反馈交接。

### 期望展示

术语实际保存成功后使用下列交接；失败时说明未保存内容并停止。目标未变化，不重复用户故事。

```text
当前位置：订阅协议（Subscription Agreement）→ 退款（Refund）→ 退款申请（Refund Application）〔履约请求〕
责任人：读者（Reader）；实际主体待明确。

应退金额（Refund Amount）的依据已经追到适用约定：按该笔实付金额（Paid Amount）全额退还。支付凭证（Payment Evidence）提供金额，退款约定（Refund Terms）说明为什么应退同一金额；这不表示退款（Refund）已经完成。

词汇表已保存。本轮停止。
```

### 反例与检查

- 再问具体金额：已有依据能够确定，不应为了续问凑题。
- 将本轮停止视为全局结束：局部判断与全部责任闭合须分别核对。

检查已知约定能否解决原问题、术语实际结果与停止位置。

## 3. 纯领域身份：不补造合同

### 输入

用户只讨论客户档案（Customer Profile）的身份。已知共用手机号（Phone Number）不能证明同一客户（Customer），足够的身份判断依据尚未明确；本轮允许澄清与记录，没有合同履约材料。

### 理解与推进

承接客户档案（Customer Profile）的身份判断，复用手机号（Phone Number）可能被共用这一事实。按 FM 方法核对术语，选择影响身份判断的一个必要依据问题。

### 期望展示

```text
当前位置：客户领域（Customer Domain）→ 客户档案（Customer Profile）

我们已经知道手机号（Phone Number）可能被共用，因此两份客户档案（Customer Profile）有相同手机号（Phone Number），还不能证明它们属于同一客户（Customer）。接下来需要找到业务上足以判断同一身份的依据。

实际业务依据什么判断两份客户档案（Customer Profile）属于同一个客户（Customer）？
```

### 反例与检查

- 询问数据库主键：用技术身份替代业务判断。
- 为格式建立合同或给非凭证对象补责任人。
- 默认使用证件号：把建议当成现行规则。

检查只问一个身份依据问题，不扩展销售合同、权限或全企业字典。
