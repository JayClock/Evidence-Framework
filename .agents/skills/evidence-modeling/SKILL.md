# Evidence 建模入口

一次触发、分阶段执行、同页联合审核。只负责编排、权限与交接：专业业务分析、领域语言和模型表达归 `evidence-fm`；访谈机制归 `evidence-discovery`；整体接口设计归 `evidence-api-design`；模型与接口的离线审核页归 `evidence-visualization`。FM 和 API 保持独立事实源，不复制专业方法或建立入口私有状态。

## 1. 定位目标与实际文件

读取项目指令、本次目标、已有来源、记录和 Git 差异，按 [文件交接](references/workflow.md) 恢复。默认根为 `.evidence/`，只修改本次授权的文件，保留无关改动；不自动迁移、转换或删除既有记录。

通过宿主资源发现定位所需 Skill 的实际目录，读取其 SKILL.md，不假设兄弟路径。一体生成在编辑前确认 FM、API Design、Visualization 及运行依赖均可用；缺必需资源先停止，不先改 FM 后才发现无法联合交付，不以业务提问弥补工具缺失。

## 2. 选择一个分支

| 本次意图             | 执行者及读取条件                                                                                    | 写入范围与退出条件                                                                          |
| -------------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 讨论方法／只聊不落盘 | FM 的 `references/business-analysis.md`；术语问题按需读 `references/domain-language.md`             | 只解释与展示，不保存、不自动进入访谈                                                        |
| 访谈、继续澄清       | Discovery；经营依据、合同边界、骨架、追溯、单据推演、参与者与角色扮演及变化点按 FM 方法             | 只保存发现记录与词汇表；一个必要问题后等待真人或交接                                        |
| 生成／修改模型与 API | FM → API Design → Visualization；先核对 `references/responsibility-closure.md` 的人类全局依据和授权 | 门槛满足后，先业务分析，再按当前 Schema 映射与校验；接续整体 API 设计与校验，生成联合审核页 |
| 只校验               | FM 与已有 API 的校验分支；明确只查 FM 时仅运行 FM                                                   | 只读报告，不写任何项目文件，不生成审核页；API 缺失明确报告联合检查未完成                    |
| 生成联合审核页       | Visualization，必需当前 FM 与 API Design                                                            | 重新校验两源后生成同一只读页面，不修改设计源；缺 API 不降级为 FM 单独审核                   |
| 暂缓／停止／仅补资料 | Discovery 的控制分支                                                                                | 按更窄授权保存新增来源或影响后停止，不自动恢复问答                                          |

在本入口请求生成／修改模型，默认授权本轮 FM、整体 API 与联合审核页的完整链路，无需第二次触发 API 或审核页。明确“只修改 FM”“不要设计 API”“不生成审核页”等更窄要求优先，只执行获授权部分；调用独立 FM Skill 不扩大其权限。访谈按 FM 方法当轮维护明确术语，不编辑模型 JSON、规则、场景或 API；普通回答、追责结束确认或只读请求本身都不触发生成。

编辑授权不替代人类追责结束确认，也不是业务批准。直接调用 FM、充分外部说明或已有模型同样核对门槛；未闭合只交接缺口，不局部放行、不自动改为访谈。

## 3. 核对分支交付，不重做专业分析

业务逻辑、领域逻辑和工具／胶水按实际依据选择路线，不强迫所有输入通过合同流程。访谈按 FM 方法的分析依赖推进；正式 JSON 映射是准入后的独立动作。

- **访谈**：按 FM 方法核对各约定的经营依据、来源与边界理由，从记录引用生成可读视图，全部主履约、当前骨架、追溯、异常与未知均可定位；人类终点和全局结束依据分别检查。原话与术语分别报告保存结果，任一失败即停止，未执行单据推演不声称通过。
- **模型与 API 生成**：人类结束确认仍覆盖当前范围和版本；核对定义拥有者及稳定引用。落实 standalone 后保留 term ID，将条目替换为 FM 引用；目录、命名与结构以当前 FM Schema 为准。按 [联合交付](references/workflow.md#fm--api--联合审核) 接续 API 和页面，分别核对实际增改删、真实检查及限制，不在 FM 子步骤结束时终止完整授权链路。
- **只读校验**：没有项目写入；没有实际场景执行时 `simulationPassed` 为 null。两源结果分别报告，FM 通过不能冒充 API 通过。
- **联合审核页**：同页展示模型、规则、场景、接口契约、消费者流程及双向引用；输入新鲜度和实际检查在交接中说明，不嵌入业务页面。页面不是业务批准或状态来源。

## 4. 交接后停止

列出当前分支、文件引用、实际保存结果、检查和未决影响。界面只收集交互，不保存业务记录；不可用转普通对话，不伪造回答。

保存、机器检查、追责结束和业务批准分别说明，不自动批准。失败保留真实错误及已改文件，不自动回滚。完成本次获授权链路或遇到阻塞后停止，不自动进入需求、规划、实现或 Git 操作；模型缺口不自动解除访谈停止状态。
