# 建模入口与行为评测

## 两类输入

- [routing.json](routing.json)：四个建模 Skills 同时可用时的选择、权限与近似请求。不能预先指定待测 Skill，否则测不到触发能力。
- [evals.json](evals.json)：明确进入 Modeling 后的编排行为；专业行为继续使用各包自己的 evals。

评测文件只用于维护，不作为真实业务来源。静态测试检查目录、引用、路由用例结构与执行协议，不证明 Agent 实际选择正确。

## 隔离执行

1. 使用独立临时项目和新会话，不读取真实 `.evidence/`。为题述路径准备最小合成资料；需要准入或多轮回答时由真人提供可定位的依据，不让待评 Agent 自答。
2. 新旧版本使用同一模型、宿主、工具、项目指令和输入；同一组全部安装 `availableSkills`，保留其他实际竞争 Skills 的一致可见性。显式入口的调用控制由宿主执行，不通过删除元数据模拟。
3. 只向待评 Agent 提供 prompt 和题述来源，不提供 primarySkill、expectations 或 forbiddenActions。非显式案例不得附加“请使用某 Skill”的提示。
4. 记录实际读取的 Skills 与参考、执行顺序、文件前后摘要、命令、提问和停止位置。模型先读错误 Skill 再纠正也记录，不只观察最终答复。
5. 每例至少独立运行三次；旧版与新版相互隔离，不共享对话、答案或已生成文件。多轮案例跨会话恢复只交接实际保存文件。

`primarySkill: null` 表示不应进入本组专业流程，不代表禁止使用其他合适工具。FM 方法作为 Discovery 的知识依赖不算第二次主流程触发；一体生成由 FM 包完成模型与 API，再接续 Visualization，也不是误触发；API 阶段不应重新执行 FM 检查。含方法词汇的 Skill 维护请求不等于业务建模请求。

## 判定与证据

逐条 expectations 标注通过／失败／未评，并引用原始轨迹或文件差异。检查：

- 应触发是否触发，是否误触发相邻 Skill；明确入口与自动选择分别统计。
- 是否遵守只读、仅 FM、仅页面等写入边界，是否绕过人类准入。
- 是否先保存来源再沉淀术语、保存失败后停止、每轮最多一个必要问题。
- 是否省略必要步骤、反复索取已有事实、自动恢复暂缓或越权进入下游。
- 是否按分支加载资料；记录实际 token 与时长（可取得时），不可用填未取得，不用字符数冒充 token。

保存结果到隔离工作目录，不回写案例为“已通过”，不修改业务批准或计划状态。总体通过率之外列出每例方差、关键越权失败和环境阻塞；触发准确不抵消越权写入。没有真实 Agent 运行时保持未执行，不以用例存在、文档测试或人工阅读填通过率。
