# 访谈、领域语言沉淀与模型编辑工作流程

## 文件布局与恢复

默认路径均相对项目根，按需创建；沿用已有文件与用户显式指定路径，不自动迁移：

- `.evidence/discovery.json`：来源、回答、工作理解、简化业务视图、问题、暂缓／停止状态与交接；需拆分时用 `.evidence/questions.json`。
- `.evidence/glossary.json`：唯一领域词汇表，使用独立 Schema 的严格 JSON，位于 FM 类型根之外；standalone 当轮沉淀未建模术语，model 只引用 FM 对象／属性，不复制定义，不维护 Markdown 词典。
- `.evidence/fm/`：源 JSON、说明、validation 与 generated；已建模概念的名称和含义由对象唯一维护；落实独立术语后，词汇条目改为引用。
- `.evidence/checks/fm/`：获授权保存的紧凑运行清单，绑定模型内容摘要。
- `.evidence/api/api.json`：另行使用 `evidence-api-design` 时维护的 API 设计源。
- `.evidence/api/generated/`：完整校验后更新的当前 API 投影。
- `.evidence/checks/api/`：获授权保存的 API 紧凑运行清单。
- `.evidence/views/index.html`：用户要求时生成的自包含离线只读审核页，方法与工具归属可定位的 `evidence-visualization` Skill。修改 JSON 后重新生成，不以页面存在代表当前校验通过。

恢复时读取项目文件，不猜测旧会话。发现记录只保存当前焦点、来源、实际问题、简化理解、状态、模型和检查指针，不复制正式模型正文。模型可能处于编辑中或校验失败状态；下游消费前必须重新校验，不能仅凭文件或旧报告存在判定可用。

## 分析路线

### 业务、领域与工具

先解释当前问题的核心复杂度：

| 路线 | 判断线索                               | 分析起点                              |
| ---- | -------------------------------------- | ------------------------------------- |
| 业务 | 收入、成本、KPI、合规、风险或运营约定  | 协议／合同、双方责任及履约证据        |
| 领域 | 算法、计划、统计、优化、领域身份与结构 | Domain Context、Thing、关系与领域规则 |
| 工具 | 仅连接已有能力，没有独立业务或领域判断 | 记录不适用依据，不补造模型            |
| 混合 | 同时包含运营责任与问题域能力           | 先分离两种逻辑，再以有来源的关系组合  |

业务与领域是知识边界，也是候选弹性边界。合同 Context 聚合双方业务责任，但不同 Fulfillment 可能具有不同弹性诉求；不要把一个合同自动当作单一部署或容量边界。

### 合同与履约分析

对合同／协议型业务，按以下顺序取得闭合切片：

1. **找协议上下文**：确认是哪项现实约定，以及承担权责的双方业务身份。内部绩效约定也可适用，但不能只因存在管理关系就假定条款。
2. **找主要履约**：逐项表达“谁要求谁在什么业务期限内完成什么”。不要先画系统步骤或审批流。
3. **找请求与证明**：明确发起主张的 Evidence、期限依据、实际由谁形成什么确认凭证，以及该凭证证明的结果。
4. **找未履约后果**：分别检查未请求、过期、拒绝、部分完成和错误完成。区分“原履约仍未完成”与“触发新的退款、补交、重做、终止、补偿或赔偿责任”。
5. **递归追踪责任**：对新责任重复请求—确认分析，直到已有终极处理、明确的本次范围边界，或需要业务方澄清。不得为结束递归而编造“无后续责任”。
6. **划分领域输入**：识别稳定参与主体、履约标的和提供判断的领域能力；Thing 进入 Domain Context，不能因为合同引用它就把它变成合同内部状态。

只纳入当前来源闭合的职责切片。未明的下游责任不自动阻塞独立主履约，但不得拆掉当前职责成立所必需的期限、证明或违约规则。

### 合同前渠道

合同形成前按实际材料识别 RFP → Proposal → Contract 生命周期：

- 合同前协商与合同履约具有不同的法律、知识和弹性边界；保持独立 Context 和时间线。
- 合同只追溯形成它的最终依据，不依赖渠道内部全部过程。
- 固定套餐、询价、招标和反复报价可以有不同结构，不强迫归并成单一路径。
- 同一合同可由多个独立渠道形成时，把渠道视为变化点，而不是把所有渠道步骤塞进核心合同。
- 只分析合同前范围时允许没有未来 Contract，不为模型完整性虚构签约结果。

### 异步、违约和业务一致性

每个 Request—Confirmation 都是一段业务时间线：

- Request 形成后、合格 Confirmation 形成前，结果未知或待履约；这来自业务现实，不是技术异步的投影。
- `started_at`／`expired_at` 表达请求区间；`confirmed_at` 表达确认的业务时刻。字段存在不等于期限或时刻的业务来源已明确。
- API 返回、消息到达、记录入库、签署、生效、批准和确认必须按真实来源区分。
- 异常修正通常产生新的不可变 Evidence 或新的 Fulfillment，并保留对原事实的追溯。
- 合同上下文的一致性来自主要履约与违约后续共同形成的责任链，不依靠覆盖旧状态维持。

### 变化点与业务模式

基本履约成立后再检查：

1. 核心履约是否直接依赖多个支撑合同或多种证明来源；
2. 消费方真正依赖的是哪类合格证明，而不是哪个当前供应商；
3. 是否应由外部时刻 Evidence 扮演 Evidence Role，以隔离可替换来源；
4. 是否存在不同渠道、Third-party Role、Domain Role、Context Role 或独立 Fulfillment 边界；
5. 替换领域输入后，权责、完成证明和违约责任是否仍成立。

一个案例只能提出业务模式候选。复用支持和具名确认的门槛由 `evidence-fm` 当前规则决定。支付 SDK、消息 Topic、数据库表或微服务名称不是业务变化点证据。

## 简化理解与正式模型

讨论／工作坊可以先形成简化业务视图，帮助快速交流：

```text
业务目标
→ 候选协议与双方
→ 主要履约：谁要求谁完成什么
→ 请求区间 → 确认证明
→ 未履约触发的新责任
→ 渠道、领域输入与候选变化点
```

简化视图必须附来源、推断和缺口，并写入发现记录；它不是第二套长期模型，不与 JSON 双轨维护。访谈中的明确术语按领域语言方法写入统一词汇表，简化视图只引用条目。该授权不包括模型 JSON、关系、规则和验证场景。

模型 JSON 编辑时才依据 `evidence-fm` 映射为稳定 ID、Context、Role、Participant、Evidence 类型时间、Relationship、CEL Rule、实例 `basedOn` 和 validation。源目录和命名遵循 FM 格式方法；术语无需先绑定 Entity ID，不从词汇表条目自动生成模型对象。归属、基数和跨上下文约束以当前 `evidence-fm` 为准。

## 访谈并沉淀领域语言

每轮同时使用 `evidence-discovery` 的访谈机制和 `evidence-fm` 的 `references/domain-language.md`，不把访谈结束作为术语写入的前置条件：

1. 读取当前词汇表、所引 FM 目标、来源和控制状态；先解析定义拥有者，再指出模糊词、同名异义及概念边界。
2. 消化本轮全部事实和更正，先保存原话与来源。
3. 将未建模术语作为 standalone 当轮写入 `.evidence/glossary.json`；已建模概念使用 model 条目引用当前 FM 目标，不能另存名称与含义。未决解释和没有模型编辑授权的更正留在发现记录，不增加实现设计。
4. 核对术语与现有 JSON、需求和代码的冲突，登记影响；不静默改写模型或验收，不让代码裁决业务含义。
5. 展示本轮增改条目及保存结果，再选择一个必要问题等待真人。可以用标明为假设的具体案例检验边界，不将合成案例当事实。

本模式授权发现记录与词汇表的增量写入，不包括模型 JSON、关系、规则、验证场景、API 或代码。只聊不落盘、仅保存资料或只记录冲突等更窄要求优先。两处文件不是原子事务，任一写入失败就停止，明确已保存和未保存内容；恢复时核对实际内容再补齐，不重复写入。

缺少 FM 领域语言方法时仅继续一般事实澄清，记录待沉淀项，明确词汇表尚未更新；缺少 Python 不阻塞文本术语沉淀。未形成模型 JSON 也可以先问影响业务判断的必要问题。

问题优先顺序跟随当前责任链：

1. 当前责任是否存在以及双方是谁；
2. 谁要求谁完成什么；
3. 什么证明结果、由谁形成；
4. 请求期限和各 Evidence 时间如何由业务确定；
5. 哪个未履约后果实际影响当前判断；
6. 哪个渠道或跨上下文依赖需要作为变化点。

不为填满模板一次性询问全部实例日期、物理字段或可选规则。停止不会因后续材料自动解除；暂缓问题沿用原 Q-ID 与 gapKey。材料足够时保存交接后停止，不为凑流程提问。

## 生成或修改

用户要求生成或修改即授权编辑本次范围内的当前模型。先读取现有文件和 Git 差异，区分已有改动与本轮变更，不覆盖无关工作。

遵循 `evidence-fm`，按事实依赖评估 ready、support、pending。直接编辑 `.evidence/fm/`，保留未受影响的有效内容和稳定 ID。落实独立术语后将同一 term 条目替换为引用，移除独立定义；撤回对象时同步处理词汇表及模型引用，真实未知留在评估中；没有可纳入职责时只记录依据与缺口。

正式映射前执行以下核对：

- 业务职责是否能由来源解释，而不只是“有一个流程”；
- 每项 Fulfillment 是否形成有方向的请求与确认结构；
- 责任双方、确认提供方和经办主体是否被错误合并；
- 请求期限、签署、确认及其他凭证时间是否完成业务来源核对；
- 违约后续是否错误塞入原履约状态；
- 合同前、合同、履约与领域边界是否混合；
- 跨上下文证明是否通过当前 Schema 允许的 Evidence Role 等结构表达；
- 技术组件是否被误建成 Participant、Role、Evidence 或业务 Context。

运行 `check_fm.py`。失败时只修复获授权的表达错误，不削弱业务预期；无法解决则明确当前模型未通过、哪些文件已经修改及下一步选择。用户中断后不自动回滚，下次从当前文件继续。

最后展示：

1. 模型路径与本次实际增改删，提供差异及新文件内容；Git diff 不包含未跟踪文件，须单独检查。
2. 变更来源、业务目标、事实依赖、责任链、变化点和未纳入职责。
3. Schema、CEL、lineage、simulation 与 timeline 的真实结果，声明实际执行场景数。
4. `modelDigest`、`inputChanged`、Evidence 时间线及未决顺序。
5. 仍影响业务判断的缺口与当前审核状态。

差异展示不是额外写入确认。写入与机器通过都不是具名业务批准，模型保持有依据的审核状态。Git 仅用于查看和用户明确要求的版本操作，不自动暂存、提交或回滚。

## 只读校验与检查记录

只校验时运行 FM 包内 `check_fm.py`，报告真实退出状态；不写任何项目文件。没有实际执行场景时 `simulationPassed` 为 null，不宣称模拟通过。

用户要求留存结果时，将紧凑运行清单保存到 `.evidence/checks/fm/<运行标识>.json`，并按 FM 校验方法保留命令、环境、来源摘要与日志指针；不复制完整输出。不覆盖已引用的检查记录，不将报告放进模型目录。来源、模型、场景或校验器变化后重跑；旧结果只证明旧版本。

## 结束与界面降级

提问界面只收集回答、暂缓或停止选择，业务标识与记录仍由 Agent 维护。无界面时用普通对话等待输入；取消或停止不伪造答案、不主动发下一题。

交接只给当前焦点、分析路线、词汇表增改条目与保存结果、模型路径、实际检查记录、责任链和未决项；未保存内容明确列出。术语更新不等于模型已校验。完成后停止，不自动启动 API、需求、架构、开发或业务审核。
