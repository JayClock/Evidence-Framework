# FM Modeling 组合入口

这是用户显式调用的编排入口。它负责把业务理解、澄清、正式建模和校验串成一次可恢复的工作，不另造一套 FM 语义：访谈方法归属 `evidence-discovery`，正式模型与当前 Schema 的判断归属 `evidence-fm`。

## 开始

读取用户目标、项目约定、发现记录、当前模型、检查记录及已有 Git 差异。新产物默认放在项目根的 `.evidence/`，具体布局和恢复方式见 [工作流程](references/workflow.md)。沿用已有文件与用户显式指定路径，不自动迁移。产物目录不授予宿主状态写权限，不改 `state.json`、审批或运行记录。

通过宿主资源发现定位已安装 Skill，不假设兄弟目录或固定安装路径。识别本次意图：

- **讨论／澄清**：整理来源、简化业务视图、回答、问题与交接；不修改正式模型。
- **生成／修改模型**：用户请求即为本次范围内的编辑授权；先完成必要业务分析，再直接编辑 `.evidence/fm/`，校验并展示差异。
- **只校验**：运行只读检查，不修改模型、场景、发现记录或报告文件。
- **生成可视化审核页**：定位 `evidence-visualization` 并读取其 `SKILL.md`，从重新校验的 FM／已有 API 生成离线只读 HTML；不重复维护展示方法，不修改业务模型或自动创建 API。
- **暂停／结束**：保存已取得且获准记录的依据与控制状态后停止，不启动建模。

资源缺失是执行限制，不是业务问题。缺少 `evidence-discovery` 时可以消费充分材料，但不自创访谈机制；缺少 `evidence-fm` 时不能声称完成专业建模或校验。只读环境给出可复制交接并明确未保存。

## 先选分析路径

在提出问题或映射 Schema 前，先判断当前复杂度来自哪里：

- **业务逻辑**：围绕收入、成本、绩效、合规或风险，优先沿协议、双方权责和履约证据分析。
- **领域逻辑**：围绕算法、计划、统计、优化、身份和领域结构，直接分析 Domain Context，不补造合同。
- **工具／胶水**：仅连接已有能力且没有独立业务或领域语义时，可以判断 FM 不适用；信息不足不是不适用。
- **混合问题**：先分离运营相关的业务逻辑与问题域自身的领域逻辑，再通过有来源的 Evidence 与 Thing／Role 关系组合。

这一步选择分析路线，不替代 `evidence-fm` 的适用性与 ready／support／pending 判断。

## 组合流程

1. **消化输入**：处理全部新增材料、回答和更正。需要澄清时遵循 `evidence-discovery`；回答必须先保存，再判断下一个必要缺口，保存失败即停止。
2. **建立业务理解**：按工作流程形成最小但闭合的分析切片。合同型业务从双方责任、主要履约、违约后续和终极边界展开；合同形成前业务保留独立渠道；领域型业务从身份、结构和规则展开。
3. **识别业务变化**：检查可替换的确认凭证、不同签约渠道、不同履约弹性，以及被业务消费的领域输入。变化点必须来自业务结构，不从 API、队列、数据库或当前服务拆分反推。
4. **正式映射**：用户要求生成或修改时遵循 `evidence-fm`，评估 ready、support、pending，直接维护一个当前模型目录。Entity 文件名使用 `<category>-<kind>--<id-suffix>.yaml`，其余命名与结构以当前 FM Schema 和 `evidence-fm` 规则为准；旧图例或简化分析不能覆盖现行约束。
5. **真实校验**：运行 Schema、CEL、lineage、simulation 与 timeline 检查。只修正授权范围内的表达错误，不削弱业务预期；失败时如实保留当前文件和错误，不自动回滚。
6. **展示结果**：列出实际增改删、来源、检查摘要、`modelDigest`、Evidence 时间线、变化点、未决顺序和业务缺口。文件变化后旧检查不能证明当前模型有效。
7. **保存交接并停止**：仅保存获授权的最小交接。Git 用于查看差异和版本恢复，不自动提交、暂存或回滚；不自动进入 API、需求、架构或开发。

## 不可混淆的业务语义

- Request 表示权利方向义务方提出的、具有业务时限的履约主张；Confirmation 表示由实际提供方形成、证明具体履约结果的凭证。
- Request 已形成而合格 Confirmation 尚未形成时，业务上处于待履约／未知结果，不把它压缩成同步技术调用。
- 回调到达、记录创建、人工审批和履约确认不是天然同一事件；必须按来源分别判断。
- 失败、取消、退款、冲正、补偿或赔偿可能触发新的 Evidence／Fulfillment；不修改原凭证来伪装业务修正，也不把未知后果写成无责任。
- 现实当事人可作为发现入口；正式模型仍按当前 Schema 区分 Participant、Party Role、Evidence Role 及责任归属。

界面工具仅用于提问；不可用时转普通对话。差异和检查结果通过普通对话展示，不能把界面回答当作文件已经保存。写入、机器检查与业务批准始终相互独立。
