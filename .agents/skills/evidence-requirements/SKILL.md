# Evidence 软件需求收敛

决定“业务中哪些事情由本次软件负责”，而不是把全部业务活动搬成系统功能。可以直接接受外部业务说明，不强制先有 FM 或特定发现日志。

## 输入与边界

1. 遵守项目的任务范围、文件权限与审核要求；没有写入授权时只做分析。
2. 读取用户指定材料、已有需求、业务术语、相关规则与案例；有 FM 时读取源 YAML，不只依赖生成报告。检查来源变更与矛盾，不用过期模型遮盖新事实。
3. 采用项目已有目录；没有时告知默认使用 `docs/requirements/`。没有写权限或只讨论时提供可复制内容，并明确未保存。
4. 先核对用户是否真的要求软件需求；纯业务访谈或只校验 FM 不触发自动需求生成。evals/ 只用于维护或明确评测，不作为本次需求的业务输入。

## 工作步骤

### 1. 对齐问题与证据

识别真实参与者的任务、痛点、目标和成功条件。角色来自业务依据，不因为模板需要而凑画像。区分当前代码行为与期望业务规则，冲突须指出而非自行择一。

使用 [来源与缺口检查](references/source-check.md)。同一回答中的事实全部吸收，已有事实直接复用；只对影响当前需求结果的核心缺口逐问，不要求用户先填写完整清单。

### 2. 明确软件责任

对相关业务活动明确本次软件是：执行、计算／判断、接收外部结果、辅助人工，还是本次不做。业务责任方和运行软件的系统不是同一概念。

例如外部机构提供付款确认，不等于本次软件要实现资金划转；人工争议处理不是默认建设诉讼系统。没有来源不默认为人工审批、自动退款或任意权限。

列出候选 MVP 与取舍依据。未有明确选择时标成建议，不把 Agent 推荐写成人工已决定。范围排除须有依据，保留外部依赖；不能为了完成文档删除关键业务未知。

### 3. 组织可交付的薄切片

围绕可观察价值组织用户旅程及必要故事，不按页面、数据库表或固定数量凑 Epic。每个故事说明：作为谁，希望什么，以便获得什么价值；同时说明软件职责、依赖和人工／外部边界。

分配稳定 `US-001`、`AC-001-01` 等标识，优先保留已有项目规则。修订不重编号、不复用废弃 ID，不因标签改变而换故事身份。

### 4. 写验收与追溯

每个可实施故事具有 Given／When／Then、具体输入、可观察预期、业务来源或模型规则／案例引用；覆盖适用的正常、边界、异常场景。不从实现输出倒推预期。

金额、期限、权限、舍入、安全与性能指标均须有依据；未知不能用常见默认值补齐。合成测试数据明确标记，不能伪造真实业务或验收通过。

关键规则仍未知的故事标成待澄清，列出实际影响，不包装成可实施故事。若只有技术选择未知，可交给后续设计，但业务规则本身不能下放给编码自行决定。

## 产物与停止

使用 [需求模板](assets/requirements-template.md) 按需生成：

- `scope.md`：参与者与痛点、问题陈述、软件职责矩阵、MVP 建议／决定、不做事项及依据。
- `stories.md`：故事、稳定验收标识、具体场景及预期、追溯和未决项。

优先沿用项目已有需求文档与验收格式，避免维护两套不一致的需求。不要在需求中另造业务规则或反向修改业务事实来匹配故事。

用户要求停止时先把新增事实与未决项写回对应记录，再以路径和稳定 ID 交接当前焦点、待选范围、问题与暂停状态、下一步选择；已有需求、模型和来源不在交接中再抄一份。停止后补充材料只吸收，不自动追问。已暂缓问题不换 ID 重问，恢复该题需要明确意图。

完成时列出实际保存文件、已确定／建议的软件范围、可实施和被阻塞的故事及下一步选择。不自动进入架构、排 Sprint、编码或提交 Git。需求文档不是批准记录或测试执行证据。
