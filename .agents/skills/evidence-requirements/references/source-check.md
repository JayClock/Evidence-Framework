# 软件需求的来源与缺口检查

每个软件职责、业务规则与验收预期都要能追溯到原始业务材料、用户原话或有来源的模型／案例。可直接从外部说明开始，不要求使用另一个 Skill 的编号或文档布局。

1. 找到相关原文与版本，区分事实、用户决定、Agent 推导和建议。代码证明当前行为，不自动证明期望正确。
2. 核对术语、对象身份、责任与外部边界。同名不代表同一对象，业务 Role 不自动等于账户权限或系统组件。
3. 金额、数量、比例、时间和业务结论均检查形成依据：直接记录、引用已有值、规则派生，或来源待明确。没有公式不等于自由输入，字段存在不等于业务口径已知。
4. 凭证与时刻含义分开：签约不默认等于生效、确认不默认等于回调、凭证形成不默认等于原事件。履约确认不是默认人工审批。
5. 对照正常、边界与异常案例。预期可由明确规则确定性推导；合成数据须标注，不冒充真实事件或用户答案。
6. 已有事实充分覆盖的问题直接链接依据解决，避免要求用户再答一次。来源或回答更正后保留旧原文和更正关系，复核所有实际受影响的故事及预期。
7. 技术映射未知单列为设计事项；真实业务未知定位到受影响故事／验收，不假装全局阻塞，也不绕过局部必需规则。

有必要澄清时先保存当前理解、展示来源与具体缺口，然后只问一个核心问题并等待。问题沿用稳定标识，不预排问卷、不捆绑子问题、不对已明确事实重复确认；跳过或停止不会解除业务阻塞。

普通 Markdown 是可审阅的协作记录，不提供不可变日志或身份认证。真实批准须有明确的人工依据，不能从账号、材料充分或机器通过推断。
