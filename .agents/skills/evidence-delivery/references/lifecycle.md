# 双层循环状态协议

## 1. 两层职责

主 Agent 承担外层 PDCA，管理任务选择、依赖、进度、重规划和唯一归档。每次任务派发新的 worker 进程执行，再派发另一个新的 reviewer 进程只读审查；不共享或续接子会话。子 Agent 只返回临时交接，主 Agent 核验后更新唯一机器计划：

```text
项目宪法 → Guides 导航 → 项目基线与工程指南
          ↓
软件范围 + .evidence/fm + .evidence/api
          ↓
docs/plans/smart-domain/plan.yaml
          ├─ compiled.tasks / executionOrder：计算 DAG
          └─ tasks[taskKey]：Guides、设计、状态、CHECK、证据
          ↓
docs/plans/smart-domain/review.html：只读审核投影
```

扩展和审核页不拥有业务状态。扩展只调度进程、返回可定位的临时交接；工具权限直接取自 subagent 定义：worker 可读写实现文件，reviewer 仅可读取和搜索。确定性脚本只观察、编译或投影；任务前馈未就绪时不得从结构候选直接进入 Action。共享工作树不是沙箱，worker 的 shell 仍有主进程的操作系统权限；唯一归档是角色协议，不宣称路径级强隔离。

## 2. 外层状态转换

允许状态为 `planned`、`blocked`、`in-progress`、`done`。

```text
planned ──前置完成且无局部阻塞──> in-progress
   │                                  │
   └──缺少来源/环境/前置────────────> blocked
                                      │
blocked ──缺口有依据地解决──────────> planned
                                      │
in-progress ──检查失败可局部修复────> in-progress
in-progress ──CHECK、质量检查与双维度审查满足────> done
in-progress ──发现上游变化──────────> blocked → 重新 Plan
```

所有状态转换由主 Agent 执行。不得因文件存在、审核页显示、子进程正常退出或命令曾经通过设置 `done`。依赖任务不是 `done` 时，当前任务不能进入 `in-progress` 或 `done`。

## 3. 计算型与推断型控制

### 交给程序

- taskKey、依赖引用、DAG 和 API 覆盖；
- `compiled.tasks` 与 `tasks` 一一对应；
- CHECK 和 gap 标识唯一；
- blocked、空命令和 gap 的结构关联；
- done 的 `acceptanceCriteria` 均为引用本任务 CHECK 的结构化断言，且真实证据非空；
- 当前可执行任务集合；
- 从同一 `plan.yaml` 重建离线审核页。

### 交给 Agent

- FM 到业务模块的映射；
- 哪种切片形成最小可验收结果；
- CHECK 是否真正证明业务结果；
- 失败属于实现、任务设计、切片还是业务来源；
- 当前任务的授权、来源、设计、环境和 CHECK 是否足够开工；
- 哪些业务源、架构、规范、howto、代码或环境变化使旧证据失效。

计算通过只证明声明结构自洽，不能证明业务设计合理、测试充分或业务批准。

## 4. 转向矩阵

| 观察                            | 内层动作                                  | 外层动作                                              |
| ------------------------------- | ----------------------------------------- | ----------------------------------------------------- |
| 编译、测试或静态检查失败        | worker 定位失败信号，按诊断协议修复并重跑 | 不换任务，修复后另启 reviewer 重审                    |
| CHECK 不能证明 FM 预期          | 修订测试设计                              | 保持 taskKey；必要时修订同一任务记录                  |
| 任务拥有重复或缺失工作单元      | 停止实施                                  | 修订 slicing 并重新 compile                           |
| FM/API 来源改变                 | 停止使用旧证据                            | 返回 Plan，重算投影和影响范围                         |
| 缺少业务事实                    | 不猜测实现                                | 记录 gap，交回 FM 澄清                                |
| 必要前馈不足或相互冲突          | 不进入 Action，定位来源拥有者             | 修订局部设计/关联 gap；不建私有前馈状态               |
| 环境或命令不可用                | 记录环境阻塞                              | blocked，只影响相关任务                               |
| CHECK、质量检查及双维度审查满足 | worker 与 reviewer 分别返回有来源的交接   | 核验产物新鲜度，唯一归档证据与 done，重建审核页并停止 |

## 5. 知识交接与归位

内层任务的 worker 与独立 reviewer 在向外层主 Agent 交付结果、结束会话或因缺口停止前，分别清点本轮**新增**且可能影响后续行动的内容；没有新增内容不制造空记录。即时反馈在下一步行动前就要处理，不能等到收尾。按来源区分：

- **用户统筹**：用户表达的偏好、优先级或暂时取舍，保留原意、来源与适用场景；它不是正式业务事实或已批准的任务范围。
- **执行发现**：对照当前文件、命令或运行结果发现的差异与限制，注明证据定位、观察时间或运行标识、受影响范围及尚未核实之处；不得将推测写成事实，也不得把历史结果当本次观察。
- **决定**：注明作出者（用户或执行者）、结论、理由、适用范围、所依据的授权与仍受影响的检查。执行者只能决定本任务范围内的做法，不能替业务方或架构拥有者批准上游变更。

内层不写持久任务记录，只向主 Agent 返回**来源定位、建议归属、影响和未决条件**。worker 交接产物、实际检查与局部设计建议；reviewer 独立交接 Standards / Spec、未验证项及发现。两者均不写 `guides`/`design`、`observedEvidence`、`gaps`/`gapRefs` 或 `status`，不自行改写 FM、API、需求或项目规则。临时运行目录、工具结果与会话摘要不能充当持久知识。没有归档授权或归档失败时，主 Agent 报告可复制的交接信息并明示“未保存”，不能声称下一会话会自动看到。

外层在验收本轮交付和派发下一任务前，由主 Agent 逐项核对两份交接内容与现有来源、原始日志和当前产物，按项目 Guides 的权威位置和实际授权唯一归位：业务回答交发现记录，由相应拥有者决定是否更新 FM/API/需求；项目范围内的工程约定经确认写入对应架构或工程指南；本任务局部设计留在任务记录，检查结果与待决 gap 各归其位。需要改变切片或依赖时返回 Plan 重编译，不能用对话摘要、`review.html` 或新建的知识队列作为第二份事实源。用户只读讨论时不写业务记录或计划状态。归档只保存核验后的事实、来源、范围与必要证据指针，不复制执行推理；临时材料须在整合成功、必要日志已按授权保存后才能清理，不自动删除失败证据。

若新说法与旧说法冲突，保留两者的来源、时间和各自适用范围，标明受影响任务，交由有权者裁决；不能凭“后说的覆盖先说的”推定全局替换。比如“不要用某库”后又说“仅本地测试可用”，先确认后者是否只对本地测试构成例外，其他范围仍按原约束处理。归位后下一次会话再按来源与新鲜度重新核对，不把已保存等同于已批准或已验证。

## 6. 恢复会话

1. 读取项目宪法、Guides 导航和 Git 差异，确认模式与授权；
2. 核对 FM/API 与计划输入，必要时返回 Plan 重编译；
3. 运行 `plan_state.py verify`，只有通过后才读取 `next` 的结构候选；
4. 选择一个 taskKey，只读取其任务记录、直接前置，并加载 `sourceRefs` 与 `procedureRefs` 指向的真实来源；核对已归位的用户反馈、发现和决定对本任务是否适用，未保存的交接不能当成文件证据；
5. 检查授权/目标、来源/审核、前置新鲜度、设计边界、环境及验证/退出；架构/指南/代码/环境变化须评估重验；
6. 确认工作树与状态一致，通过后才开始新的 worker 委派；reviewer 必须另开会话。子 Agent 能力不可用就报告环境阻塞，不回退为主 Agent 自做自审。中断的临时交接必须重新核验，不能按子进程成功标 done。

若 `plan.yaml` 不存在、compiled 为空、源摘要过期或结构无效，停止在 Plan，不根据聊天或 `review.html` 猜测下一任务。
