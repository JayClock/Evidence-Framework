# 双维度审查

worker 完成实际检查后，主 Agent 启动新的只读 reviewer 会话，独立审查工程规范与需求忠实性。两者各有结论，不能合并成一个总分；工具通过也不能替代这两项判断。reviewer 不继承 worker 的会话或推理，不兼任执行者。

## 固定审查范围

用本轮开工时的 Git 差异与当前文件确定本任务增量，包含未提交、已暂存和未跟踪文件；保留用户已有改动的边界。用户指定提交范围时先解析固定点并核对实际 diff。不要只看 HEAD 而漏掉工作树，也不要把他人的已有修改归因于本轮。

读取任务授权、outcome、非目标、acceptanceCriteria 及所引需求、FM/API、工程规范；事实冲突交对应拥有者，不能以当前实现裁决。无法取得必要来源时相应维度报告未验证，不给通过结论。

## Standards：工程规范

逐项检查变更是否遵守当前适用的架构、模块公开契约、行为和数据归属、测试边界与工程约定。每条发现引用规范位置及具体文件/片段，说明影响。

区分硬性违规与设计建议。命名含混、重复逻辑、职责分散或多余抽象需要结合本任务判断，不能凭通用偏好否定项目明确约定。自动工具已经报告的问题引用实际结果，不用重复手工描述制造额外发现数量。

**退出条件**：适用规范各有判断依据，违规、建议及未验证项分别列出。

## Spec：需求忠实性

从已授权软件范围逐条追到本任务实现与 CHECK，而不是只看代码是否自洽：

- 要求的行为是否缺失或只实现一部分；
- 实现是否错误解释规则、时刻、身份或失败后果；
- 是否新增未授权行为、权限、默认值、数据库或集成方案；
- 测试预期是否来自独立依据，是否能捕捉需求被破坏，而非仅证明实现与自身一致。

每条发现引用需求/规则/验收位置、实现位置及证据或缺口。FM 中存在的活动不自动属于软件范围，代码存在不证明获得授权。

**退出条件**：每条本任务验收及非目标已对照，缺失、错误和范围扩张明确可见。

## 输出与转向

独立 reviewer 分别输出 `Standards`、`Spec`，每项包含结论、发现、依据、未验证项与所需行动。只读工具权限直接由 subagent 定义控制，不提供 bash/edit/write。需要重跑命令时报告精确命令与目的，交主 Agent 安排；缺少独立 reviewer 时停止，不由主 Agent 或 worker 自审代替。

实现问题留在当前任务修复，改动后重跑受影响 CHECK 并重审；边界/依赖问题返回规划，业务冲突返回来源拥有者。两个维度均满足要求且质量检查实际通过，才具备任务完成依据；设计建议不自动变成新需求。

reviewer 只返回交接。主 Agent 核对受审产物未变化后，将获授权且已核实的审查结果唯一写入当前任务 observedEvidence，引用其 CHECK 与来源；只读审查仅报告。保持现有 schema 和状态归属，不增加独立批准字段，不把 Agent 审查当业务批准。
