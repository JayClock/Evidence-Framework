# Evidence PoC

**用双层循环驾驭 AI 软件开发，让交付依据从“Agent 声称完成”变为可检查的工件、执行结果与人工决策。**

Evidence 是一个运行在本地 Pi TUI 中的 AI 软件工程工作流原型：外层以 PDCA 组织任务分解、执行追踪与验收，内层以操控循环（Steering Loop）引导和纠正 Agent 的具体行动。

人类负责目标、业务事实与关键决策；Agent 在当前任务的约束内生成工件、修改代码并执行验证；Evidence 扩展负责流程约束、确定性检查和证据记录。仓库同时提供 Nx + React + Spring Boot 全栈脚手架，作为工程实践的运行基础。

## 为什么需要 Evidence

把一个完整项目交给 Agent，仅靠“请继续”和“再改一下”，容易遇到三类问题：

- **任务失控**：上下文增长后，遗漏需求、偏离范围，无法确定进展。
- **执行失准**：缺少业务依据、操作规则和验收标准，拆得再细也可能做错。
- **完成失真**：生成了文档或代码，却没有实际验证，或者把自我评价当成通过证据。

Evidence 通过双层循环组织工程交付：**外层管理“做什么、做到哪”，内层控制“当前这一步如何做、如何纠偏”。** 方法论、工件和执行证据共同支撑任务推进与质量检查。

## 核心模型：双层循环

双层循环不是两条独立流水线，也不只是“大任务套小任务”。外层把整体目标分解为可追踪、可验收的工作；每项工作的执行，再由内层提供前馈和反馈。

```text
外层：PDCA —— 任务分解、追踪与验收

Plan：明确目标、阶段产物、任务及验收标准
  ↓
Do：执行当前工件或当前故事
  │
  └── 内层：Steering Loop —— 具体任务的执行与纠偏
      前馈 Guides → 行动 Action → 反馈 Sensors → 调整 Steer
           ↑                                         │
           └────────── 未达标且可在当前范围修正 ───────┘
      达到退出条件 → 提交工件与执行证据
      缺少依据或超出边界 → 暴露阻塞，交由人类处理
  ↓
Check：检查工件、计划覆盖与实际执行结果
  ↓
Act：依据检查与 Gate 决策推进、修订或回退
  └── 将反馈带入下一轮 Plan
```

### 外层 PDCA：不让项目失去方向

外层关注整个工程的流程分解和追踪，而不是要求 Agent 自行规划所有步骤。

| 环节  | 在 Evidence 中的落点                                                                   |
| :---- | :------------------------------------------------------------------------------------- |
| Plan  | 固定工程阶段与交付物；通过需求、架构和 Sprint 计划明确故事、场景、任务、依赖与通过标准 |
| Do    | 一次处理当前工件或当前用户故事，不越过批准范围自行进入下一阶段                         |
| Check | 阶段工件校验；故事完成时重跑全部适用计划检查及质量命令；最终独立审查                   |
| Act   | 按 Gate 策略推进；人工可要求修订或回退上游，相关下游证据需重新取得                     |

流程状态由扩展保存在 `.evidence/state.json`，阶段间以 `artifacts/` 交接，而不是依赖聊天记忆。默认每个工程阶段、每个编码故事使用独立 Session。

**外层循环不意味着全自动重试。** 当前阶段 Gate 默认需要人工审核；质量失败后按状态等待继续执行或人工反馈，并受修订轮次限制。

### 内层 Steering Loop：让当前任务有依据、有反馈

对于边界已明确的任务，继续拆分并不能替代必要的知识和质量标准。内层通过四个环节驾驭 Agent 的自我纠正过程：

| 环节            | 要回答的问题                           | 在 Evidence 中的落点                                                             |
| :-------------- | :------------------------------------- | :------------------------------------------------------------------------------- |
| 前馈（Guides）  | 行动前，需要知道哪些事实、规则和边界？ | `AGENTS.md`、阶段 Skill、上游工件、提示词与模板、API 契约、测试策略和工序        |
| 行动（Action）  | 当前允许做什么？                       | 读取依据、提交当前工件，或修改当前故事的真实代码与测试；工具按阶段限制           |
| 反馈（Sensors） | 如何发现偏差，而不是只听 Agent 自评？  | 工件结构检查、FM 校验与适用单据模拟、真实测试输出、lint/build、审查意见          |
| 调整（Steer）   | 偏差该如何修正，何时必须停下？         | 在当前任务范围内修正并重新验证；缺少业务依据、需改变契约或超出范围时交由人工处理 |

**只有前馈，Agent 容易草率结束；只有反馈，Agent 可能反复犯同一种错误。** 检查结果和修订意见需要成为下一次行动的上下文，循环才真正闭合。

内层不等于 TDD：需求文档、统一模型、架构和计划同样需要操控循环。TDD 是编码阶段的一种具体执行工序，而不是所有任务的统一模板。

### 工序与证据：连接两层循环

架构阶段定义可复用测试工序（`TP-*`），计划阶段将其落实到“故事 → 验收场景 → TASK → CHECK”；编码阶段按批准的工序执行，并把结果交回外层验收。

例如，一个需要新增行为的编码任务：

1. **前馈**：读取对应 AC 场景、API 契约、适用工序和批准的测试命令。
2. **行动与反馈**：先增加行为测试，通过 `evidence_tdd_red` 记录真实行为失败；环境错误、语法错误不算 Red。
3. **调整与再验证**：实现最小行为，通过 `evidence_tdd_green` 重跑同一命令，不能删除或削弱 Red 测试取得 Green；重构后由 `evidence_complete_tdd_cycle` 复验。
4. **回到外层**：全部任务完成后提交故事，扩展重跑全部适用 CHECK 和质量命令，满足条件后才进入 Gate。

复用已有行为和验收任务通过 `evidence_verify_task` 验证，不制造虚假 Red。一个故事可以包含多个正常 TDD 循环，**循环次数不等于外层修订轮次**。

## Harness 如何落地

双层循环是设计框架，指令、工具与技能、环境、状态则是它的工程载体。

| 子系统     | 项目中的载体                                                    | 作用                                         |
| :--------- | :-------------------------------------------------------------- | :------------------------------------------- |
| 指令       | `AGENTS.md`、阶段提示词、工件模板                               | 提供目标、上下文、边界和退出标准             |
| 工具与技能 | `.pi/skills/`、`evidence_*` 工具与检查器                        | 封装方法论和工序，执行提交、校验及真实验证   |
| 环境       | Pi TUI、Nx、Node.js、JDK、Gradle Wrapper、隔离的 FM Python 环境 | 为行动和反馈提供明确的运行条件               |
| 状态       | `.evidence/state.json`、`artifacts/`、`reports/`                | 保存进展、工件、反馈及决策，让下一轮有据可循 |

**计算型检查交给工具，需要语义理解的分析交给 Agent，关键业务判断交给人类。** Schema、文件摘要、任务依赖和命令结果可以由代码核对；业务是否完整、设计是否合理、测试断言是否充分，不能仅靠结构检查得出结论。

## 工程工作流

```text
需求分析 → 统一建模 → 架构设计 → Sprint 计划
        → 逐故事编码与测试 → 独立审查 → 完成
```

| 阶段        | 方法与职责                                  | 主要产出                                           |
| :---------- | :------------------------------------------ | :------------------------------------------------- |
| 需求分析    | Design Thinking，明确角色、问题与范围       | 用户画像、问题陈述/MVP、故事地图与验收场景         |
| 统一建模    | 统一语言 + FM Schema v3                     | 领域对象、关系、规则及适用的渠道、合同履约与凭证链 |
| 架构设计    | 按需 DDD 映射与技术设计                     | 上下文映射、模块、API、数据模型、测试策略与工序    |
| Sprint 计划 | Scrum / INVEST，场景驱动任务分解            | Backlog、依赖、可执行测试计划、DoD                 |
| 编码与测试  | 真实 Red → Green → Refactor，复用与验收验证 | 可运行代码、测试和逐任务执行记录                   |
| 独立审查    | 只读核对需求追溯、设计约束和交付证据        | 审查报告、缺口与剩余风险                           |

Modeling 是唯一建模入口。纯领域、纯渠道同样使用统一 FM，不因没有合同而跳过；DDD 边界与战术设计按需进入架构工件，不把业务模型直接等同于事务聚合或微服务。

## 建模的价值：从问题出发，沿业务依据收敛

**系统是为了解决某一类问题而存在的，而不是为了堆积功能。建模首先要回答：解决什么问题，以什么判断它得到了解决？**

Evidence 区分两类关注点：

- **领域问题**：如何正确处理问题本身，例如内容组织、搜索、排程与计算。围绕领域知识、对象、关系、规则及适用算法展开。
- **业务问题**：如何利用这些能力赚钱、省钱、支撑运营。对外关注收入、支出及其对应的权利与义务；对内关注成本、效率，以及目标—实际之间的绩效承诺。

两类关注点可以在同一系统中共存，但需要分别理解。业务部分按 8X Flow 的权责与凭证主线展开，不从“系统还能有哪些功能”无限发散，而从明确的业务依据切入：

| 分析起点      | 需要解释的问题                                           |
| :------------ | :------------------------------------------------------- |
| 收入          | 收到钱意味着承担什么义务？凭什么证明已经完成？           |
| 支出          | 付出钱意味着取得什么权利？如何确认对方已经履行？         |
| 目标—实际/KPI | 目标是什么，由谁负责，如何计算实际结果，凭什么核对差异？ |

从这些起点继续追溯权责、凭证、关键数据来源和异常处理，就能形成支撑当前业务运转的主线，再识别相关角色、参与者与领域能力。

**提问由主线上的缺口驱动，而不是由所有可能的功能分支驱动。** 一个金额需要追溯计算依据，一个完成状态需要找到确认凭证，一个异常需要明确责任与处理边界。每次澄清都应补足当前模型，而不是开启无关的话题。

通过正常、边界与异常场景，检查模型能否解释实际业务。当当前范围内的关键依据明确、适用场景经过核对、阻塞项得到解决或通过人工调整范围处理后，就可以提交模型进入审核。范围外的问题保留边界，不必继续深挖背后的全部运营体系；纯领域和签约前渠道，也不强行补造合同与履约。

**更容易收敛，来自明确的分析起点、追溯主线和完成边界，而不是承诺更少的提问次数。** 信息不足时仍需补充或缩小范围，未知项如实保留，不能用假设换取表面上的完成。

这也是双层循环在建模阶段的具体体现：**外层确定要解决的问题与范围，内层沿业务依据发现缺口、获取反馈并修正模型。**

## 什么算交付证据

- **工件依据**：原始需求、统一语言、模型和批准的架构与计划。
- **执行记录**：FM 校验及实际执行的适用模拟、任务检查、完整 TDD 循环和质量命令输出。
- **决策记录**：Gate 关联工件和报告的 SHA-256 摘要；审核前证据改变时需要重新检查。

这些证据支持追溯，但不等于自动证明质量：

- 模型结构通过、单据模拟通过、业务方认可和 Gate 批准是不同结论；未执行的模拟不能记为通过。
- 命令成功不证明每个业务场景都被断言覆盖，也不代表人工验收或全部质量评价已经完成。
- 工具限制与命令检查不是安全沙箱；项目脚本和扩展仍需信任。

当前是**本地工作流 PoC**，不依赖 CI、自动 Push 或固定模型厂商。可按阶段配置模型；Git 检查点可选且仅在本地执行。自动检查辅助决策，不替代人工审核。

## 快速开始

### 环境准备

- Node.js 24 LTS（推荐）与 npm 10 或更高版本。
- JDK 17；后端已包含 Gradle Wrapper，无需单独安装 Gradle。
- Python 3.10 或更高版本：统一 FM 建模及扩展自测需要，可通过 `EVIDENCE_PYTHON` 指定解释器。
- 使用 Evidence 工作流时，需要在 Pi 中配置可用模型及其认证。

```bash
npm install
```

### 体验 Evidence 工作流

在仓库根目录启动项目依赖中的 Pi：

```bash
npx pi
```

信任项目扩展与 Skills 并重启 Pi 后执行：

```text
/evidence-init
```

填写原始需求后开始生成工件。后续根据状态操作：

| 命令                      | 用途                                |
| :------------------------ | :---------------------------------- |
| `/evidence-status`        | 查看当前阶段、进度、报告和 Gate     |
| `/evidence-run`           | 继续就绪的工件或故事                |
| `/evidence-review`        | 打开人工 Gate，审核、批准或要求修改 |
| `/evidence-revise <反馈>` | 根据反馈发起修订                    |
| `/evidence-back`          | 回退上游阶段                        |

不要手改 `.evidence/state.json`，也不要绕过提交工具或 Gate 编辑器修改生成工件。完整操作、配置和旧运行升级说明见 [Evidence 工作流指南](docs/evidence.md)。

### 运行全栈示例

无需初始化 Evidence 工作流，也可以直接启动前后端：

```bash
npm run dev
```

- 前端：<http://localhost:4200>
- 后端示例：<http://localhost:8080/api/hello>
- 健康检查：<http://localhost:8080/actuator/health>

开发环境的 `/api` 请求由 Vite 代理至后端。可分别运行 `npm run dev:frontend` 和 `npm run dev:backend`。

## 项目结构与技术栈

```text
.pi/
├── extensions/evidence/  # 状态机、提示词、工具、校验与 Gate
├── skills/               # 阶段方法论与执行工序
└── evidence.json         # 模型、Gate、轮次和质量命令配置
apps/
├── frontend/             # React + TypeScript + Vite
└── backend/              # Java + Spring Boot + Gradle
.evidence/                # 运行状态，由扩展管理
artifacts/                # 阶段交付物与 Gate 记录
reports/                  # 校验及实际命令报告
AGENTS.md                 # 项目级 Agent 约束
docs/evidence.md          # 完整工作流指南
```

技术基础：Nx 23、React 19、TypeScript、Vite、Java 17、Spring Boot 4、Gradle；测试使用 Vitest 与 JUnit。

## 开发与验证命令

```bash
npm test                  # 应用测试 + Evidence 扩展测试
npm run lint              # 前端代码检查
npm run build             # 应用构建 + Evidence 扩展类型检查
npm run graph             # Nx 项目依赖图
npm run evidence:verify   # 扩展类型检查、测试及格式检查
```

扩展自测不调用语言模型；首次执行可能下载 FM Python 依赖。自动回归验证确定性机制，不等同于真实人工端到端验收或模型生成质量评测。
