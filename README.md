# Evidence（证据工程）

把**软件工程方法论**引入 LLM 驱动的开发流程，让"人类如何用 AI 构建项目"这一过程本身系统化、自动化、可重演。

元工程的目标覆盖完整的软件工程 PDCA：需求、建模、契约、架构、规划、实施、回顾各阶段在同一循环里推进，每一阶段以对应方法论为语境、以可判定产物为出口。当前落地的是领域建模与它直接衍生的技术契约、联合审核。

## 核心理念

**元工程（Meta-Project）** 是把**软件工程方法论**引入 LLM 驱动的开发流程中，把"人类如何用 AI 构建项目"这一过程本身系统化、自动化、可重演。

它解决的根问题是：**常规 LLM 编程（一次性对话 + 上下文窗口）缺乏结构化、缺乏方法论语境、缺乏多轮改进，导致上下文丢失、任务完成度不可控、质量不稳定。**

元工程不是"用 Agent 写代码"的工具，而是一套**元层（Meta-Layer）** 的工程体系：

```
┌───────────────────────────────────────────────────┐
│ 每个开发阶段导入对应的方法论，在方法论指导下：    │
│   1. 产出该阶段的可判定产物                       │
│   2. 用确定性脚本给出计算证据，用清单给出语义判定 │
│   3. 携带范围与摘要交接下一阶段                   │
│   4. 由人在关键节点做出业务决定                   │
│   5. 提示词改动以评测分数取舍                     │
│                                                   │
│ —— 元层由协议固定，目标层由 Agent 在约束内发挥 —— │
└───────────────────────────────────────────────────┘
```

### 元层与目标层

| 层次 | 内容 | 归属 |
| :--- | :--- | :--- |
| **元层** | 阶段顺序与接续条件、方法论文档、产物位置与唯一源、检查字段与语义、门禁条件、评测基线 | 由协议固定，不随对话变化 |
| **目标层** | 本次业务的模型、契约、代码 | 由 Agent 在当前阶段的约束内产出 |

元工程自动化的是判定：检查、派生产物、投影、评测。阶段能否交接、业务是否成立，由门禁与人工确认回答。

### 宏观确定性，微观灵活性

| | 常规 LLM 编程 | 放手式 Agent | 元工程 |
| :--- | :--- | :--- | :--- |
| 宏观（做什么、按什么顺序、用什么方法论） | 由 LLM 自己决定，随上下文漂移 | 由 Agent 自己规划，不可控 | **由协议预先定义，确定不变** |
| 微观（具体怎么表达、怎么写） | 完全由 LLM 决定 | 完全由 Agent 决定 | **由 Agent 在约束范围内发挥** |
| 产物可判定性 | 无 | 无 | **每类产物都有对应检查** |
| 阶段交接 | 靠对话记忆 | 靠 Agent 自述 | **靠携带范围与摘要的有效结果** |

由协议**预先确定**：

- 阶段顺序，以及阶段之间的接续条件
- 每阶段的产物类型与位置：模型、追溯日志、契约、页面、代码各归其位
- 每阶段的判定项与结果字段：一致性、完整性、有效性、输入是否已变
- 交接所必需的证据，以及不可推断的部分
- 人类结束确认，由人显式给出

留给 Agent **自主发挥**：

- 需求阶段：如何从业务材料推导软件职责与验收条件
- 建模阶段：如何沿凭证找到责任双方、请求与确认，如何表达未知
- 架构阶段：如何划分模块边界与依赖方向
- 实施阶段：如何实现一个工作单元、如何选择验证路径
- 局部错误与缺口的修正方式

## 方法论驱动的开发流程

按开发阶段安排对应的方法论，每个阶段在该方法论的指导下产出可判定的产物：

| 阶段 | 导入的方法论 | 关键产物 | 判定 | 状态 |
| :--- | :--- | :--- | :--- | :--- |
| 需求与软件职责 | Design Thinking 裁剪版 | 软件职责结论、非目标、验收条件 | 职责覆盖，验收条件可被引用 | ⏳ |
| 领域建模 | 履约建模 + DDD 战略设计（现金权责 → 责任双方 → 请求—确认 → 履约包裹） | 唯一模型源、可校验追溯日志 | 一致性、范围完整性、场景模拟 + 六个语义问题 | ✅ |
| 技术契约 | 资源与能力设计 + HTTP 契约设计 | 接口能力、HTTP 契约、消费者旅程 | 契约覆盖已检查范围，HTTP 契约自洽 | ✅ |
| 联合审核 | 只读投影 | 单页审核工作台 | 浏览器回归与两源新鲜度 | ✅ |
| 架构设计 | DDD 战术设计 + 分层架构 | 上下文映射、模块边界、领域映射 | 分层规则以可执行断言表达 | ⏳ |
| 实施计划 | 敏捷拆解 + 切片策略 | 可校验的任务切分、局部设计、检查项 | 归属唯一、依赖无环、验收条件可解析 | ⏳ |
| 实施与回放 | 小步测试循环 + 旅程回放 | 代码、分层证据、场景映射 | 四层证据齐备，场景指向真实执行 | ⏳ |
| 持续改进 | 回顾 + 评测基线 | 改进措施、分数变化 | 分数比较，退化先回退 | ⏳ |

### 领域建模（已实现）

领域建模沿一条证据链把业务判断固定下来：

```
业务材料
  │
  ▼
访谈：履约判断 ──► 关键数据 ──► 凭证来源 ──► 深入追溯 ──► 返回判断
  │
  ▼
追溯日志（结构与引用可校验）
  │
  ▼
唯一模型源：合同 → 履约 → 请求／确认 → 规则／场景
  ├──► 一致性检查（每批修改）
  ▼
范围结束确认（人类显式给出）
  │
  ▼
范围完整性检查 + 场景模拟 ──► 门禁 ──► 技术契约 ──► 联合审核投影
```

**五个入口，各自只做一件事**：

| 入口 | 职责 | 不做什么 |
| :--- | :--- | :--- |
| 业务访谈 | 沿凭证追溯，成组提问，写可校验的追溯日志 | 不编辑模型，不执行技术校验 |
| 业务建模（FM） | 维护唯一模型源，报告一致性与完整性 | 不主持访谈，不设计接口 |
| 技术契约（API） | 就绪范围内设计资源、能力与 HTTP 契约 | 不改业务模型，不重复模型检查 |
| 只读投影 | 把模型与契约投影成单页审核工作台 | 不设计业务界面，不改任何源 |
| 端到端编排 | 选择分支、传递授权、核对交付、接续阶段 | 不重做专业分析，不建私有状态 |

**产物位置固定，各自有唯一拥有者**：

```text
.evidence/
├── fm/                       唯一模型源：Context、实体、关系、规则、验证场景
├── traces/interview-trace.json  访谈问答与来源日志（可结构校验）
├── api/api.json              技术契约唯一设计源
├── api/generated/            契约派生产物（只可再生成，不可手改）
└── views/index.html          只读审核工作台（快照，不是批准或计划状态）
```

**六个语义问题**，脚本通过不替代它们：

- 现金权责锚定：本批合同是否挂到具体收入义务、支出权利或内部绩效目标？
- 主要履约成对：合同双方是否各自已成为至少一项主要履约项的权利方？
- 请求—确认对偶：每个履约项是否都有明确请求端与结果确认端？
- 违约阶梯闭环：异常下是否有补偿或升级路径，并推到可指名的责任终点？
- 易变策略隔离：计价、分佣、分发是否已拆为规则或能力提供者？
- 定义归属：新增名称与定义是否归对象或属性拥有者，并与既有术语一致？

任一为否即为未完成。

### 技术契约与联合审核（已实现）

技术契约只读消费建模阶段同一次范围检查结果，把就绪范围表达为资源、角色能力、HTTP 契约与消费者旅程；联合审核把两源投影成单页只读工作台。二者并入建模批次，独立成阶段会产生两份互相不知道对方是否有效的结论。

契约检查通过后才生成投影；缺契约时联合审核不降级，失败的重新生成保留旧页。

## 判定与传感器

每个阶段的判定由三部分构成，缺任一部分都不算完成：

| 构成 | 内容 | 当前手段 |
| :--- | :--- | :--- |
| **计算证据** | 可复算的结构与覆盖结论 | 校验脚本 |
| **语义判定** | 结构通过仍不能替代的业务判断 | 逐项清单 |
| **新鲜度** | 结论与输入是否仍然对应 | 输入摘要绑定 |

结果字段各自独立：

- `consistent`：本次一致性结论。
- `complete`：指定范围的责任完整性；未检查时为 `null`。
- `valid`：结构合法性。
- `inputChanged`：检查后输入是否变化，变化使结论失效。
- `modelDigest`：结论绑定的输入摘要。
- `runtimeValidated`：契约检查恒为 `false`，静态检查不启动服务。

严重程度三级，只有阻塞级停止接续：

| 级别 | 典型情形 | 处置 |
| :--- | :--- | :--- |
| 阻塞 | 保存失败、空履约／空上下文、Schema 或表达式语法失败、依赖环路、范围完整性未过、适用场景失败 | 立即停止，不接续下游 |
| 警告 | 待澄清的上下文角色、模拟器无法执行的规则、定义已更正但依赖未重算 | 记录并报告，不阻断 |
| 信息 | 一致性通过、摘要更新、未改动无关文件 | 随结论报告 |

各阶段当前的传感器：

| 阶段 | 传感器 | 产出结论 |
| :--- | :--- | :--- |
| 需求与软件职责 | ⏳ 待办 | — |
| 领域建模 | `check_interview_trace.py` | 追溯日志的结构、问答标识与对象引用可被下游读取 |
| 领域建模 | `check_fm.py` | 未发现一致性错误 |
| 领域建模 | `check_fm.py --scope` | 指定独立范围的责任已闭合 |
| 领域建模 | 场景模拟 | 已声明场景在该模型下可回放 |
| 阶段门禁 | `check_stage_gate.py` | 结束确认、检查结果与范围三者匹配 |
| 技术契约 | `fm_api.py check` | 契约覆盖已检查范围，HTTP 契约自洽 |
| 技术契约 | `fm_api.py project` | 派生产物与设计源一致 |
| 联合审核 | `review-browser.mjs` | 页面可加载、引用完整、无外部请求 |
| 架构设计 | ⏳ 待办 | — |
| 实施计划 | ⏳ 待办 | — |

## 阶段门禁

每个阶段以人工确认结束：范围、证据与输入摘要同时匹配，才允许进入下一阶段。门禁回答能否交接，业务是否成立由人判断。

建模阶段的门禁区分三种覆盖范围：

| 确认类型 | 覆盖 | 不覆盖 |
| :--- | :--- | :--- |
| 合同级结束 | 该合同的责任与凭证已澄清 | 其他合同、全局追责是否结束 |
| 领域／协商结束 | 该分支的方案与连接点已澄清 | 未获授权的内部建模 |
| 全局追责结束 | 当前完整范围 | 机器检查是否通过、业务是否批准 |

## PDCA 循环

元工程在完整的软件工程范围内驱动 PDCA：需求、建模、契约、架构、规划、实施、回顾各阶段都在同一循环里推进，每个阶段以对应方法论为语境。

```
Plan   根据方法论与该阶段已有产物制定执行计划
  │
  ▼
Do     在方法论语境与产物约束下产出该阶段工件
  │
  ▼
Check  取确定性检查的取值，再做语义判定
  │
  ▼
门禁   范围结束确认；证据齐备才允许交接
  │
  ▼
Act    达标进入下一阶段；未达标携带未通过项进入下一轮
  │
  └──────────► 回到 Plan
```

每一轮携带上一轮的完整产出、未通过的检查项与轮次编号；退出标准是检查结果。

### 双层循环

外层管阶段与轮次，内层管单次交付：

```
外层：阶段与轮次
┌───────────────────────────────────────────────────────┐
│ Plan   确定目标、授权、来源、允许文件与停止条件       │
│ Do     在方法论语境下产出该阶段工件                   │
│ Check  确定性检查取值与语义判定分别报告               │
│ Act    达标接续下一阶段；未达标进入下一轮             │
└──────────────────────┬────────────────────────────────┘
                       │
                       ▼
内层：单次交付
┌───────────────────────────────────────────────────────┐
│ Guides   只加载当前判断需要的方法与来源               │
│ Action   在当前授权内完成本分支动作                   │
│ Sensors  先取检查值，再判定；证据先于结论             │
│ Steer    按失败类型措辞：修正、交接、停止、或报告完成 │
└───────────────────────────────────────────────────────┘
```

内层每轮只完成当前分支的一次交付；外层在轮次退出、目标或授权改变、或有效结束信号到达时接续。连续问答保持原焦点，不重走分派，不重复已加载且未变化的方法。

```
                       │  证据齐备
                       ▼
┌──────────────────────────────────────────┐
│ 持续改进   待办                          │
│ 产出：改进措施、分数变化                 │

└──────────────────────────────────────────┘
```

## 执行手段

| 手段 | 当前用法 | 选型理由 |
| :--- | :--- | :--- |
| **普通对话** | 访谈、讨论与阶段推进 | 判断质量取决于问答质量；追问、更正与否定在对话里最直接 |
| **确定性脚本** | 一致性、完整性、门禁、契约、页面回归 | 只有脚本能给出可复算的结论 |
| **固定环境** | 一条命令创建／校验运行环境，脚本只用该解释器 | 同一输入在不同机器上得出同一结论 |
| **技能分派与接续** | 端到端入口选择分支、传递授权、核对交付 | 专业判断归各自拥有者，入口只做编排 |

元工程不引入状态文件，也不由流水线推进阶段。状态从产物与最近一次检查结果派生，结论绑定输入摘要。可重演性落在一条本地命令加上仓库内已提交的证据。

## 元层的载体：技能包

```text
.agents/skills/
├── evidence-modeling/        端到端编排：分支、授权、接续
├── evidence-discovery/       访谈问答、控制与追溯日志
├── evidence-fm/              唯一模型源、语义判定与结构校验
├── evidence-api/             技术契约与派生产物
└── evidence-visualization/   只读审核工作台

每个包自持：SKILL.md、references/（方法论）、scripts/（传感器）、
          schemas 或 tests/、evals/（提示词取舍的分数依据）
```

约定：

- 技能是唯一方法来源，每个阶段对应一个技能包；下游阶段的包列入待办。
- 合成样例只在测试中消费，测试夹具不进入提示词。
- 提示词改动以用例分数取舍：改动前后各跑一次，退化先回退。
- 结论绑定输入：模型、场景或校验器变化后重新检查。

## 实践总结

### 1. 判定落到取值

每类产物都配一个可复算的检查。格式正确与业务成立是两件事，语义问题用清单逐项判定。

### 2. 一个源，多份投影

模型与契约各只有一份源；页面与派生产物是可重建投影。投影承载展示，不承载批准或计划状态。

### 3. 状态从产物派生

阶段与轮次不写入独立状态文件。结论绑定输入摘要，输入变化使旧结论失效。

### 4. 门禁与批准分开

门禁回答证据是否齐备、能否交接；业务是否成立由人给出结束确认，并区分合同级、分支级与全局覆盖。

### 5. 判断先于提问

每轮重算依赖前沿，把全部互不依赖的必要未知同轮提出。已答项立即承接，未答项不计为同意。

### 6. 合成样例不进提示词

样例只在测试中消费，提示词只写方法、约束与判定标准。样例进入提示词后，模型复制的是表层结构。

### 7. 阶段以可判定为准入

只有具备判定标准的阶段进入交付范围，其余以待办列出并写明完成判据。
