# 8X Flow 上下文识别与引导式发现

这是发现交互的统一方法：独立使用 Skill 时读取；Evidence 的 discovering 提示词直接加载本文件。工具与定稿契约见 `../SKILL.md`，FM 语义与格式见 `README.md` 中的按需索引。这里不定义第二套 Schema，也不设置独立发现 Gate。

## 1. Agent 先识别，再围绕事实引导

从用户的业务叙述、痛点和真实材料开始，不要求用户先学习建模术语或列齐合同、履约和功能。Agent 主动抽取有依据的候选上下文，给出简短依据及不确定点，然后追问当前最关键的事实。信息太少时先问一件实际发生的事，不凭空给出完整模型让用户挑选。

- 不让用户先选择建模模式；不按产品名称或关键词硬分类。“客户”不自动意味着销售合同，“绩效”不自动意味着主管是权利方，没有“合同”字样也不等于没有约定。
- 合同、领域与渠道可以并存。沿实际责任或对象关系组合，不要求整个产品只能属于一种模式。
- 有来源支持的候选可以先提出供核实；推断标为 inferred，信息不足标为 unknown，不因用户没有纠正就升级为明确事实。材料已明确的事实直接引用，不逐条索取重复确认。
- 先说明“我从哪段材料看到了什么”，再问业务问题。不要把自己生成的候选清单当成独立业务来源。

### 从首轮就使用凭证类型的时间知识

识别到凭证候选时，按其类型核对以下必备时间，不等到定稿才补查：

| Evidence kind                            | 必备时间属性             |
| ---------------------------------------- | ------------------------ |
| `rfp`、`proposal`、`fulfillment_request` | `start_at`、`expired_at` |
| `contract`                               | `signed_at`              |
| `fulfillment_confirmation`               | `confirmed_at`           |
| `other_evidence`                         | `created_at`             |

这些是类型级约束，不是当前业务的既定日期。面向业务核实“从哪一刻开始／何时截止／何时签署或确认、谁记录、依据是什么”；不要让人填写技术字段，也不要为了补齐类型而虚构凭证。RFP、Proposal、Request 必须有确定的截止时间，不允许无期限或 `openEndedReason`。周期性请求也须逐次能确定截止时刻。

时间可以来自明确输入或有来源的确定性计算规则；涉及账期、时区、自然日／工作日等影响结果的歧义，按缺口逐题核实。**未知时间依据保持阻塞**，记录在 candidates／notes／问题中，不能猜默认期限、当前时间或最大日期。请求／期限等发现文本仍可暂为 null，这不是正式 FM 的无期限例外。

最终 `entities/*.yaml` 的 `attributes` 必须显式定义对应名称，统一 `valueType: timestamp`、`required: true`、`keyData: true`，并说明 meaning 与来源／派生规则；不能只写在 notes、README 或界面摘要中，也不能依赖编译器自动补齐。`requestInterval` 固定引用 `start_at` 和 `expired_at`。类型模型保存属性定义，实例保存具体 RFC 3339 时间值；尚未发生不代表可以删除类型属性或制造未来实例。

### 范围是发现成果，不是前置问卷

Agent 随发现整理“已展开、暂不展开、仍有边界歧义”的内容，而不是先问“请定义完整业务范围和排除项”。只有边界会影响当前结果时才问具体选择，例如“你提到作者合作和广告主投放两份协议；当前争议来自哪一份的结算？”

不自行扩大或缩小用户目标。材料未提到不等于用户已决定排除；暂未展开与已确认排除要分开记录。影响当前正确性的外部依赖仍要了解，例如不负责执行银行转账，也可能需要知道什么证明已付款。局部发现不补齐整个企业；软件负责哪些活动留到 Modeling 末尾收敛。

## 2. 合同主线：先找合同上下文，再找履约项

```text
候选合同上下文 → 双方角色与约定 → 履约项
             → 请求、期限、完成与确认凭证 → 异常与新责任
```

从收入、支出或目标—实际中的交换与承诺找合同／协议关系。合同上下文是业务约定，不要求已有名为“合同”的电子文件；是否存在约定、约定内容及依据均需核实。

1. **合同与双方**：哪两方以什么身份合作？约定依据是协议、订单、绩效约定还是其他材料？多个合同分别是谁与谁的关系？系统、API、调度器不是业务 Party。
2. **双方义务**：分别承诺什么？谁有权要求谁完成哪件事？按材料抽取候选履约项，缺少义务内容就围绕双方实际承诺追问，而不是要求用户自行列“Fulfillment”。
3. **履约边界**：不把每个流程步骤都当成履约项。点击、导入、定时计算和内部流转不因出现在流程图中就成为独立履约；检查是否有独立约定义务、请求与确认语义。也不把用户目标直接编成合同。
4. **逐项展开**：谁何时依据什么发起请求？要求交付什么、多少、何时完成？怎样算完成、谁有权确认、什么凭证证明？完成标准与确认行为分开核实。材料没写期限就是未知，不擅自设定默认期限或无期限。
5. **异常**：部分完成、拒绝、逾期、异议、更正、退款或补偿如何处理？是否形成新责任、由谁请求和确认？没有依据不套行业惯例编造罚金、权限或赔偿。

内部绩效同样核对谁提目标、谁必须回应、谁可同意／拒绝／要求修改，以及执行中能否变更。不预设主管永远是权利方，不自动创建“目标设定履约”。

**示例仅演示提问，不提供当前项目事实：**

用户说“找作者写文章，按阅读收入分成”，可以说：“这里可能有平台与作者的内容合作协议。双方分别承诺哪些事情？”收到回答后先更新候选，再按缺口决定是否询问约定材料。若材料已明确交稿与分成支付，则直接引用，并追问当前缺失的验收或结算依据。不凭示例自动确定付款周期、分成比例或编辑权限。

## 3. 领域主线：先找对象，再找身份与规则

```text
候选领域上下文与对象 → 身份 → 属性与关系
                   → 变化条件、资格、不变条件与计算 → 正常与反例
```

从具体痛点切入，不要求合同或凭证才能讨论领域知识。详细映射按需读 `domain-modeling.md`。

| 当前缺口   | 面向业务的追问                                                           |
| ---------- | ------------------------------------------------------------------------ |
| 对象含义   | 这里的客户是个人、公司还是档案？联系人和客户有什么区别？                 |
| 身份       | 如何判断两份资料是同一对象？同名、手机号相同、标识改变时怎样处理？       |
| 属性       | 哪些资料必须有、谁提供、允许怎样更正？字段是否真的有独立身份和生命周期？ |
| 关系       | 一个公司能有多个联系人吗？同一联系人能否属于多个公司？关系何时有效？     |
| 变化       | 什么情况下可以合并、归档或删除？冲突怎样处理？错误变化能否恢复？         |
| 约束与计算 | 什么条件必须始终成立？资格或等级依据什么计算？规则变化如何影响历史结果？ |
| 反例       | 两家不同公司共用财务联系人手机号，是否应合并？依据是什么？               |

这些是问题方向，不是一次性问卷。优先解决用户当前痛点需要的规则；档案去重先问身份，而不是先收集所有字段。区分客户本人、档案、联系动作和联系凭证；领域对象不全是 Thing，属性也不逐个造实体。业务上的修改／删除规则可以发现，但不提前决定数据库或 API。

v3 对操作、状态迁移、关系基数及复杂算法的表达缺口如实记录，由 Architecture 和后续 Q1/Q2 接续验证；不造假 Evidence 或假 Fulfillment 来声称已模拟领域操作。

## 4. 渠道主线：沿真实协商凭证展开

```text
真实邀请、报价或方案 → 请求与回应 → 协商规则 → 按需连接签约来源
```

问谁向谁发出邀请或方案、回应什么、版本如何变化、有效期和接受／拒绝依据是什么。可用 RFP → Proposal → Contract → Fulfillment 检视已有时间线，但这不是所有模型必须走完的流水线。

只展开真实存在的区域。固定套餐不补造 RFP；报价尚未接受不补造已签合同；RFP／Proposal 是签约前异步请求—响应凭证，不是履约项。协商中发现独立领域规则或真实协议时再连接相应上下文。

## 5. 共用循环：凭证、数据、回放与具体缺口

### 四色凭证与关键数据追溯

在各履约内向前寻找约定和请求依据，向后寻找完成与确认凭证，同时核对角色、参与者／地点／标的及描述。四色是发现方法，不是四个新 FM 实体类型。

对金额、数量、比例和时间追问：谁输入、来自哪张单据或对象属性、采用什么公式、哪个规则版本、当时是否可见？更正、退款、冲正和补偿追加凭证并保留原依据，不覆盖原凭证；这不意味着所有领域对象都不可修改。签约前也沿真实协商凭证追溯，但不套履约约束。

### 正常、边界、异常回放

请业务方讲具体实例，记录情节、预期、来源及 gap。单据回放仅在当前可见凭证下判断能否请求、确认、计算和解释争议，自动场景固定 `asOf`。领域则回放对象规则的正常、边界与反例，不声称已执行单据模拟。

预期来自材料或人工回答，不从实现结果倒推，不为通过校验削弱预期。不适用须有具体理由；没有资料不能写成不适用。回放暴露缺口时回到对应合同、对象、凭证或规则，不重启整套范围问卷。

### 每轮如何推进

1. 读取当前快照、最新回答和材料，指出本轮有来源支持的进展与尚存的不确定点。
2. 围绕当前最关键的缺口只提出一个核心问题，带稳定 Q-ID、来源、焦点、影响、是否阻塞和 target。target 指向已保存的合同／履约，尚未定位为 null。不预排整套问卷，也不在一题中捆绑多个子问题；前文列举的是分析方向，不是每轮必须填完的表。
3. Agent 通过 `evidence_ask_questions` 保存后停止；扩展在 Agent 完全空闲后自动显示当前问题的“回答／结束本轮”菜单，选择回答直接进入编辑器。Esc 只关闭界面；`/evidence-answer` 可重开，带 Q-ID 可标注未知、排除、跳过或更正历史回答。等待期间不代答、不重复提问。未知不能解除业务阻塞，已排除项仍需有依据处理其依赖。
4. 问答开启时，保存人工输入后扩展自动启动一次消化：按最新 A-ID 修订候选及案例，更新 focus 和 contractView。用户一次给出多项事实时全部吸收，不对已经说明的内容重复问。跳过仅保留缺口，不冒充事实、不换 Q-ID 追问同一缺口；人工结束后不得自动追问。
5. 先用 `evidence_save_discovery` 保存消化后的完整快照，再决定下一问。向用户简述“本次明确了什么、候选模型如何变化、还缺什么”，在 notes 中保留依据和变化。更正的旧原文保留，但不能继续支撑明确事实。没有必要的新问题可在保存后合法停止；资料充分才做隔离检查或声明定稿，不要求每轮交付正式 FM。

例如追溯分成金额：先问“按什么计算？”，若答“实收金额，按月结算”，则同时记录计算依据和账期，再根据材料决定是否追问退款扣减，而不是继续问已经回答的结算周期。此例不提供当前项目的业务事实。

历史问题列表用于主动切换讨论对象、补充或更正，不是必做题队列。每次答完一题就先消化，其余保留为未解决缺口，不自动暂缓、删除或排除。仍有必要讨论时可按原 Q-ID 原文重用一条未答且未暂缓的问题；已答题仅由人工更正。过时的阻塞项仍需人工有依据地解决或排除。

## 6. 记录与定稿边界

使用现有发现结构，不新增合同／领域 profile 或另一套候选 DSL：

- `scope / excludedScope`：Agent 整理当前展开部分、明确排除项及依据；待确认边界在 notes／问题中显式保留，不把 Agent 的猜测写成人工决定。
- `focus`：当前工作位置，不是阶段顺序；scope 仅用于具体边界歧义，不是默认前置任务。
- 必填 `contractView`：只读问答视图所需的发现候选关系投影，不是另一套正式模型。`contracts` 中每个合同用 `contextRef` 引用候选 C-ID，`roleRefs` 有两个位置（未知位置为 null），附真实 `sourceRefs`。角色候选限于当前合同，不把跨合同的同一参与者误当成同一角色。`fulfillments` 各项引用 `candidateRef`，记录 `rightHolderRef`、`obligorRef`（来自合同双方且不同；未知为 null）、`request`（请求依据）、`deadline`、`confirmation`（确认依据）和来源；未核实的文本为 null，不默认无期限或已完成。异常引出的新项同时记录 `parentFulfillmentRef` 和 `trigger`，前序须在同一合同且无循环；主要履约两者都为 null。`current` 为 `{contractRef, fulfillmentRef}`，只展开合同而未选履约时 fulfillmentRef 为 null；尚未定位时 current 为 null，无合同依据时 contracts 为空。缺失字段不兼容，发现快照为 v3。
- 主界面只展示合同双方、履约权责、当前展开项及当前问题。箭头表示权利方要求义务方履约，不是付款方向，更不是 Agent 的问答；同一方在不同履约中可以互换权责。推断标候选、未知标待明确，不把回答完成当作已经履约。问题的 `target` 决定正在讨论的关系，不根据名称猜测。详细来源与工程状态按需用 `/evidence-status` 查看。
- `notes`：当前展开的上下文、各候选间关系、履约清单或领域规则、凭证及数据来源、暂未展开项、异常与表达 gap；只写适用内容。
- `candidates`：稳定 C-ID、描述、`explicit/inferred/unknown`、`INPUT`／`SRC-*`／最新 `A-*` 来源。描述可承载候选合同、双方、义务或对象；未明确候选不绑定正式 modelRefs。
- `cases`：正常、边界、异常的场景、预期、来源和 gap。材料明确不等于专家已批准。

发现记录由扩展追加到 revision-N.json，不直接写 discovery 文档。正式 FM 可附引用快照的 discovery 摘要，但它不是第二份事实源。只有无独立业务／领域语义的简单胶水才可声明 FM 不适用，仍按本地发现、定稿和共同 Gate 完成；缺少合同不是不适用理由。

就绪时调用 `evidence_finalize_discovery` 检查声明，再依次提交统一语言、FM 和软件需求，共用 Modeling Gate。模型默认 draft／pending，具名专家审核、机器校验、实际模拟、人工 Gate 各自独立，不因候选已整理或机器通过就提升审核状态。
