# 8X Flow 上下文识别与引导式发现

这是发现交互的统一方法：独立使用 Skill 时读取；Evidence 的 discovering 固定系统上下文完整加载本文件，不逐轮复制进任务消息。工具与定稿契约见 `../SKILL.md`，FM 语义与格式见 `README.md` 中的按需索引。这里不定义第二套 Schema，也不设置独立发现 Gate。

## 手动模型更新边界

问答期间只追加发现记录，模型更新由人工选择触发。`finish` 仅整理并停止，`resume` 继续问答；`update-model` 才授权把积累的发现更新进统一语言和 FM。没有人工更新请求时，不调用 `evidence_finalize_discovery`，不因材料充分便自动定稿。

人工选择更新模型后，先消化全部新增输入，再按 `incremental-assessment.md` 提交全历史 Context assessment v1：各 Context 声明本批次职责、已知／未知 facts、requiredFactRefs、具体 structure/provenance/decision 依赖、回放与剩余职责；逐道未解决阻塞题定位 affectedFactRefs。Domain、Channel、Contract、Fulfillment 按自身语义评估，不依赖关联 Context 的全部知识。扩展分别输出 ready、support、pending；已知支撑投影可以被引用，未知部分仍保留。没有可纳入职责也提交实际结果，不仅因当前 Q-ID 未解决便停止评估，更不能把未知改成无后续责任或排除项。

更新统一语言和 FM 时复用已有模型及稳定 ID，说明本批次纳入的事实、变更和仍未纳入原因；正式模型不包含未明确的业务规则。提交 discovery-coverage v1：全部 Context 的状态、模型引用、retainedFactRefs、remainingScope，以及全部纳入事实到实际模型 ID 的映射；支撑投影不得宣称整体完成。FM 更新成功后停回发现，不生成 Gate、不自动收敛软件需求；用户另选 `converge` 才开始需求收敛，新增发现须先更新模型。

## 1. Agent 先识别，再围绕事实引导

从用户的业务叙述、痛点和真实材料开始，不要求用户先学习建模术语或列齐合同、履约和功能。Agent 主动抽取有依据的候选上下文，给出简短依据及不确定点，然后追问当前最关键的事实。信息太少时先问一件实际发生的事，不凭空给出完整模型让用户挑选。

- 不让用户先选择建模模式；不按产品名称或关键词硬分类。“客户”不自动意味着销售合同，“绩效”不自动意味着主管是权利方，没有“合同”字样也不等于没有约定。
- 合同、领域与渠道可以并存。沿实际责任或对象关系组合，不要求整个产品只能属于一种模式。
- 有来源支持的候选可以先提出供核实；推断标为 inferred，信息不足标为 unknown，不因用户没有纠正就升级为明确事实。材料已明确的事实直接引用，不逐条索取重复确认。
- 先说明“我从哪段材料看到了什么”，展示有依据的候选结构与不确定点，再问业务问题。不要把自己生成的候选清单当成独立业务来源。有约定依据时优先展示“履约请求 → 确认凭证”，不是先要求人填齐抽象权责表；无依据时先问一件真实发生的事，不为展示完整而造模型。

### 所有主线共用的提问决策

类型必备属性、发现方向和校验清单首先是 Agent 的分析责任，不是用户必答题。每轮消化全部新增输入后，先对相关候选、原始材料、最新有效回答及历史问题做事实覆盖检查；卡片、摘要或字段暂为空不代表没有依据。按索引补读相关明细，不逐轮重读整个模型。

| 当前情况                                     | 本轮动作                                                                         |
| -------------------------------------------- | -------------------------------------------------------------------------------- |
| 已有明确事实                                 | 引用并复用，保存本轮变化，不索取重复确认                                         |
| 已识别凭证，只有类型属性尚未展开             | 直接展开其类型语义；属性定义不要求先有实例值或生成公式，不因此提问               |
| 已有输入和规则足以确定结果                   | 保存确定性推导、来源及适用条件，不请人重新提供计算结果                           |
| 关键数据的业务来源或形成口径未明             | 沿四色追溯保存已知来源、候选关系和缺口；影响当前判断时向人澄清，不默认输入或派生 |
| 仅缺技术映射                                 | 记录给 Architecture 的实现事项，不作为业务发现阻塞或新业务问题                   |
| 业务已明确但 FM 尚未表达或无法表达           | Agent 补属性、引用或规则；能力不足记录表达 gap，交下游验证，不倒逼人重新定义业务 |
| 缺少影响业务结果的事实、约定，或存在真实冲突 | 展示具体未知、现有依据为何不足及影响，只问一个核心业务问题                       |

提问前应能解释：**什么业务判断仍无法作出，已有依据为什么不能解决，回答将改变什么结果**。不能回答这三点就不凑题；有必要问题才调用提问工具，否则保存后停止或执行满足条件的校验。技术缺口、模型表达缺口和业务知识缺口分别记录，不能全部标为“待用户确认”。业务未知不能靠字段齐全、名称匹配或类型知识消除；确定性推导也不能增加新约定、把候选当事实或覆盖人工冲突／范围决定。

### 四色追溯的统一循环

**所有关键数据都先追溯业务来源，不以“Agent 觉得需要派生”为入口。** 这适用于金额、数量、比例、六类凭证的时间以及领域结论；类型展开、直接输入和派生计算都在同一个循环内，不另设时间例外或派生发现流程。

```text
识别对象／凭证并展开类型属性
→ 复用材料和最新回答，按四色追溯关键数据的业务来源
→ 区分直接记录、引用已有值、规则派生、来源待明确
→ 保存依据／候选关系／具体缺口
→ 已知则复用或推导；影响当前判断的未知则逐问
→ 消化回答与案例回放，沿原对象继续追溯
```

四色是发现视角，不是四个新 FM 实体类型：粉色关注产生与承载数据的凭证、先后及当时可见性；黄色核对提供、请求或确认数据的业务角色；绿色关联参与者、地点、标的或领域对象；蓝色追溯描述、约定、规则及适用版本。按实际存在的关系检查，不为凑齐四色补造对象或另一张“证明凭证的凭证”，不从权责方默认推定数据提供方。

| 追溯结果                   | Agent 的处理                                                                                           |
| -------------------------- | ------------------------------------------------------------------------------------------------------ |
| 直接记录的事实或逐次约定值 | 保留谁提供／形成、记录什么事实及其业务依据的已知部分；依据充分就复用，不强造计算公式或另问谁手工填字段 |
| 引用已有值                 | 保留原凭证／对象属性、适用版本和当时可见性；不能把复制后的字段当作无来源独立输入，也不强造算术公式     |
| 由规则派生                 | 追溯输入属性及规则依据；完整则保存确定性推导，不问已知计算结果；缺规则则向人澄清当前必要口径           |
| 来源或形成方式待明确       | 保留字段已存在这一事实和未知；可提出有业务理由的候选关系，但不能默认自由输入或先编公式                 |

这些是发现说明中的业务区分，不新增 Schema 枚举、字段或状态机。用相关 candidate.description／notes 记录属性、已知来源、形成口径、推断理由、剩余缺口和业务影响，引用 `INPUT`／`SRC-*`／最新有效 `A-*`；只有来源支持的关系才成为明确事实。已有属性和义务不因局部来源未知整体降为未知，未变内容不重复保存。每轮按当前对象及本轮来源变化影响范围接续检查，不重扫全部已明确属性；定稿时覆盖当前范围的关键数据及未决缺口。

**公式可以没有，业务来源不能由字段存在代替。** 不必等材料写“计算”或用户要求自动化：四色追溯发现疑似派生关系时，将推断与已明确事实分开，不把推断写成已确认公式；关系本身尚不确定就先核实关系，明确后只问一个缺失口径。来源性质尚未确定时问“依据什么确定”，不预设固定时长、起算事件或算法，也不让人写 CEL。人工明确为非派生输入后应保留该事实；人工停止／暂缓时只记录待澄清内容，沿用原 gapKey／Q-ID，不绕过控制追问。

材料没有公式，不等于业务允许自由输入。FM 的 asserted／derived 是表达分类，不是业务来源已查明的证明；类型字段、合成实例、机器 lineage 通过或 resolution 都不能替代缺失依据。业务规则不交 Architecture 自定，数据库表、日志、接口字段等物理记录映射留到 Architecture。追溯是 Agent 的分析责任，不是逐字段问卷：先补读和复用，只问影响当前业务判断的真实缺口；非阻塞未知仍如实保留，不声称追溯已完整。

跨场景应用（仅是方法示例，不是当前项目事实）：

- **合同与角色**：材料已明确双方身份、承诺与代表关系就复用；不为填 Party／Role 槽位再次问相同职责或具体操作员。代表权限或责任对象有真实歧义时仍须问。
- **确认与其他凭证**：提供方、证明的事件／结果及采信口径已明确就记录，不额外发明审批人、记录人或“证明凭证的另一张凭证”。只有凭证名称则不能推定提供方和证明作用；更正记录也不自动等同于原业务发生。
- **金额、数量与计算**：基数、比例及计算规则已明确就推导，不问谁手工填写派生值；币种、舍入、退款扣减等影响结果且未明确的口径才是业务问题，不凭空制造冲突。
- **身份与关系**：已明确业务标识及唯一性范围就复用，不要求用户决定数据库主键、索引或外键。身份冲突、业务上的基数、跨对象授权等仍是业务语义，不能一律推给架构。
- **渠道协商**：已有报价、版本和接受依据直接吸收；不逐一补问邀请、报价和回应，不为固定套餐补造 RFP；接受是否签约有真实歧义才问。
- **异常责任**：逐项检查不是逐项索取答案；已明确触发、新义务或无后续义务终点就复用，不无限递归。仅说“外部处理”不等于无责任，缺约定不猜罚金或法律终点。
- **案例回放**：材料已有案例就复用；规则足以决定的边界结果可明确标为推导。尚无真实实例时可构造标为合成的校验数据，预期须来自业务依据／确定性推导，不伪造人工回答或真实已发生事件；规则有歧义才请业务方澄清。机器数据生成和结构校验不是业务批准。

### 从首轮就使用凭证类型的时间知识

识别到凭证候选时，按其类型核对以下必备时间，不等到定稿才补查：

| Evidence kind                            | 必备时间属性             |
| ---------------------------------------- | ------------------------ |
| `rfp`、`proposal`、`fulfillment_request` | `start_at`、`expired_at` |
| `contract`                               | `signed_at`              |
| `fulfillment_confirmation`               | `confirmed_at`           |
| `other_evidence`                         | `created_at`             |

**类型展开是四色追溯的起点，不是完成条件。** 已识别请求，就直接定义该请求的开始时间 `start_at` 和截止时间 `expired_at`；已识别其他凭证也直接展开表中的类型时间。类型属性定义、实例时间值、额外生成规则是三个层次。类型建模不要求先有实例值或生成公式；RFP、Proposal、Request 的每个实例仍必须有确定截止时间，不允许无期限或 `openEndedReason`。周期性请求也逐次提供起止时间，不为补齐类型虚构凭证或真实实例。

逐类型展开示例（是类型含义，不是当前业务的实例事实）：

| 已识别的凭证                            | 直接记录的类型时间                                   | 不能由类型推出的额外事实                                             |
| --------------------------------------- | ---------------------------------------------------- | -------------------------------------------------------------------- |
| `rfp` 询价邀请                          | 邀请的开始时间 start_at、回应截止时间 expired_at     | 不默认开始等于编辑、发送或送达时刻，不补默认有效天数                 |
| `proposal` 报价方案                     | 方案的有效开始时间 start_at、有效截止时间 expired_at | 不默认开始等于发出，接受不自动等于签约，不补默认有效时长             |
| `fulfillment_request` 履约请求          | 本次请求的开始时间 start_at、截止时间 expired_at     | 不默认从下单起算，不赋予任意设定期限的权限                           |
| `contract` 合同                         | 该合同的签约时间 signed_at                           | 不自动等同于订单创建、最后点击或权益生效时间，不认定哪种行为构成签约 |
| `fulfillment_confirmation` 履约确认凭证 | 该凭证的履约确认时间 confirmed_at                    | 不自动改成回调到达或入库时间，不推定提供方、采信规则或已经全额完成   |
| `other_evidence` 其他凭证               | 该凭证的形成时间 created_at                          | 不自动等同于它记载的原业务事件时间，不把形成更正凭证当作原事件重发生 |

以上六类都不为展开时间属性索取实际日期、生成公式或“哪个系统／谁记录字段”；也不为了刻意补全追溯再造一张证明该时间的凭证。先将类型展开记入相应 candidate.description／notes，沿用支持凭证识别的原始来源，不为发现增加另一套时间字段结构；只有请求期限写进已有 deadline，合同／确认／其他凭证不借用 deadline 承载时刻字段。signed_at／confirmed_at／created_at 是时刻属性，不额外补请求区间或有效期，也不因它们无需截止时间而删除字段。

六类时间都按上面的四色循环继续追溯业务来源。有材料明确最后一方签署构成签约、银行回执的扣款成功时间被采信、补录凭证形成晚于原事件发生等事实就保留；缺乏依据时记录缺口，不臆造竞争事件来追问，也不能把一个自由 timestamp 参数当成解决依据。提供方和证明作用的缺口与“时间属性未展开”分开，识别到确认凭证的类型不等于已确认它足以证明完成。

时间不是独立的提问分支。以付款截止时间示例应用同一个循环：

- **来源待明确**：只写“规定时间内付款”且已识别付款请求时，先保留 start_at／expired_at；deadline 可写“以本次付款请求的截止时间（expired_at）为准；确定依据待明确”。这只表达类型含义，不证明期限来源已查明。若当前要判断逾期作废，来源缺口影响结果，就问“这类付款请求的截止时间依据什么约定确定？”，不预设必须给起算事件加固定时长的公式。
- **直接记录或引用已明确**：例如双方逐笔协商最终截止，或请求沿用已接受方案中的截止时间，保存原约定、提供方及适用关系的已知部分，不强索统一公式，也不赋予任意一方修改期限的权限。
- **派生规则已明确或有缺口**：按索引补读相关明细，不重新询问已经明确的事实。凭证类型、时间业务含义及计算依据已明确时，直接复用对应属性，保存规则和 `INPUT`／`SRC-*`／最新 `A-*` 来源。固定窗口起点、工作日口径或确认采信确有缺口时，说明具体歧义及影响，再只问一个核心问题。不能仅凭 kind 推断时间起点与外部事件的对应关系，不在材料之外臆造创建、发出、送达等竞争起点。

谁提供何种凭证、凭证中的时间证明哪个业务事件，在尚不明确且影响结果时仍须核实；这不同于询问数据库字段。业务含义已明确时，不再问“实际以哪条业务记录为准”或“谁记录这个字段”。

例如，材料已明确“平台发起付款就是付款请求的开始；72小时后截止；以支付机构确认扣款成功时间判断，等于截止也按时”，就记录 `付款请求.expired_at = 付款请求.start_at + 72小时` 以及 `支付确认.confirmed_at ≤ 付款请求.expired_at`，不再追问起点来自哪条记录。若材料确实同时给出订单创建和付款请求发出两个不同起点，才问“72小时从订单创建还是付款请求发出开始计算？”。这些例子只说明方法，不提供当前业务事实或默认72小时期限。

**是否阻塞取决于业务依据缺口的影响，不取决于有没有公式。** deadline 的已知类型语义不因未给时长退回 null，但来源待明确必须在 deadline／candidate／notes 中保留；确实全未知才为 null。类型模型的非派生时间属性无需 derivedByRuleRef，不表示其业务来源已充分；仅有真实派生规则才添加 CEL 和规则引用。实际实例缺 required 时间值仍校验失败，各 kind 的必备属性不能互相替代；合成回放可提供明确标为测试数据的时间值，不由此推断业务固定时长或消除来源缺口。

最终 `entities/*.yaml` 的 `attributes` 必须显式定义对应名称，统一 `valueType: timestamp`、`required: true`、`keyData: true`，并说明 meaning 与来源／派生规则；不能只写在 notes、README 或界面摘要中，也不能依赖编译器自动补齐。`requestInterval` 固定引用 `start_at` 和 `expired_at`。类型模型保存属性定义，实例保存具体 RFC 3339 时间值；尚未发生不代表可以删除类型属性或制造未来实例。

### 范围是发现成果，不是前置问卷

Agent 随发现整理“已展开、暂不展开、仍有边界歧义”的内容，而不是先问“请定义完整业务范围和排除项”。只有边界会影响当前结果时才问具体选择，例如“你提到作者合作和广告主投放两份协议；当前争议来自哪一份的结算？”

不自行扩大或缩小用户目标。材料未提到不等于用户已决定排除；暂未展开与已确认排除要分开记录。影响当前正确性的外部依赖仍要了解，例如不负责执行银行转账，也可能需要知道什么证明已付款。局部发现不补齐整个企业；软件负责哪些活动留到 Modeling 末尾收敛。

## 2. 合同主线：先找合同上下文，再找履约项

```text
候选合同上下文 → 双方角色与约定 → 履约项
             → 展示“履约请求 → 确认凭证”候选 → 核实关键缺口
             ↔ 更新候选、依据与期限 ↔ 异常与新责任、案例回放
```

从收入、支出或目标—实际中的交换与承诺找合同／协议关系。合同上下文是业务约定，不要求已有名为“合同”的电子文件；先从材料核对约定是否存在、内容及依据，仅对尚不明确且影响结果的部分提问。

1. **合同与双方**：哪两方以什么身份合作？约定依据是协议、订单、绩效约定还是其他材料？多个合同分别是谁与谁的关系？系统、API、调度器不是业务 Party。
2. **双方义务**：分别承诺什么？谁有权要求谁完成哪件事？按材料抽取候选履约项，缺少义务内容就围绕双方实际承诺追问，而不是要求用户自行列“Fulfillment”。
3. **履约边界**：不把每个流程步骤都当成履约项。点击、导入、定时计算和内部流转不因出现在流程图中就成为独立履约；检查是否有独立约定义务、请求与确认语义。也不把用户目标直接编成合同。
4. **逐项展开**：先展示请求端（谁向谁提出什么要求及依据）和确认端（谁提供或形成什么凭证、证明什么结果），附期限和不确定点，再只问当前一个关键缺口。Confirmation 是履约证明，不默认等于人工审批；不从权利方或义务方推导确认人，也不自动添加“执行 → 验收”阶段。实际存在独立验收时才核实验收方、标准及凭证；履约执行过程按需展开。已识别请求就展开其 start_at／expired_at；材料未给固定时长不等于期限结构未知，不擅自设定默认期限或无期限。
5. **违约与后续责任**：逐项检查主要履约的违约情况，主动发现部分完成、拒绝、逾期或结果不符时的处理约定；有新责任则提出候选履约并寻找凭证，对新增的补偿履约重复检查，有依据时记录责任链的终点；不将整个责任链闭合作为独立主履约产出的条件。按下面的责任链方法展开，不只笼统询问“有没有异常”。

内部绩效同样核对谁提目标、谁必须回应、谁可同意／拒绝／要求修改，以及执行中能否变更。不预设主管永远是权利方，不自动创建“目标设定履约”。

### 逐项、递归发现违约责任

正常履约与违约后的责任共同构成合同的业务逻辑。Agent 需要检查每项履约，而不是等用户主动列出异常；不因已有一项赔付就认为整个合同的异常已覆盖。

```text
主要履约 → 未完成／逾期／结果不符 → 按约产生的新履约
                                      ↓
                              新履约仍未完成怎么办
                                      ↓
                              继续检查至有依据的终点
```

- **从已知义务寻找具体缺口**：先核对材料和已有回答中的处理约定。缺少责任约定时，提出具体违约情景和责任缺口，例如已明确付款义务却未说明逾期处理，就指出这一缺口，核实实际如何处理；不要求用户自己列全异常履约项。情景只是用于核实的反例，不表示已经发生违约，也不是新责任的依据。
- **有依据才建议新履约**：先展示“前序履约 → 违约触发条件 → 新履约候选”，然后用“履约请求 → 确认凭证”说明谁有权要求谁完成什么、依据与期限、谁提供什么证明。材料支持的部分直接记录，推断说明理由并标为 inferred；没有约定依据的新责任只保留为缺口，不默认存在罚息、退款、赔偿或直接诉讼。确认凭证仍不等于人工审批，不从权责方推定确认人。
- **对补偿继续检查**：退款、补交、返工或赔付本身也是义务；发现后继续检查其不履行时的约定，而不是添加一层补偿便结束。已有的异常履约复用原 C-ID，新项通过同一合同内的 parentFulfillmentRef 与 trigger 连接直接前序，沿各分支展开且不循环。请求与确认可引用前序凭证说明追责依据，追加补偿凭证而不覆盖原凭证。
- **区分新义务与自动后果**：如果有依据表明未付款使合同自动作废且不产生额外义务，也无需另一次履约确认，则记录终止规则及依据，不造独立履约项。不能仅因由系统自动执行就排除真实的退款或赔付义务。
- **明确终点而非臆定终点**：沿新责任递增检查，有依据时确认只能诉诸法律，或按约终止且没有后续义务；尚未明确时保留缺口，不要求本轮全部找到终点。法律处理作为责任链的外部边界记录，不自动扩展为诉讼管理功能。材料未提后续责任不代表不存在；未知、跳过、暂缓和范围外都不等于责任链已经闭合。范围外记录依赖与排除依据，不将其写成无后续责任。
- **记录覆盖与节制交互**：在 notes 中按履约 C-ID 简述未检查、待核实、已明确新责任、已明确终点及其来源；用 candidates、contractView 和 cases 保存对应候选、关系与回放，不新建结构化检查表或第二套状态字段。逐项检查是 Agent 的分析责任，不是预排问卷；根据最新理解选择一个关键缺口，一次只问一个核心问题。已明确事实不重复问，暂缓缺口不换 Q-ID 追问，人工停止后只保存已知结论与缺口，不以递归检查为由继续问答。

例如，材料已明确供货方交货、采购方付款，并约定交货不合格需补交：先保留这三项义务及来源，再分别识别付款逾期、补交仍失败的责任缺口。如果当前焦点是补交，就先展示补交候选及已知凭证，再只问“如果补交仍未按期完成，双方约定如何处理？”。收到回答后先保存更新，再决定是否继续该分支或转向付款；不猜赔偿比例，也不把两个缺口合成一题。此例只说明分析方法，不提供当前业务事实。

### 候选建议的固定展示

每个候选包含所属约定、履约事项、请求端、要求／依据、期限、确认凭证及不确定点。使用业务语言，不让用户填写技术字段。材料明确的直接引用；推断理由和未知点写在详细说明中，不放进名称。部分信息已知时保留已知部分，不能用一个已知凭证名称推导未知的提供方或审批人。

**名称与分析分离：** 新保存的每个 candidate 必须提供 `label` 和 `description`。`label` 是简短业务名称（最多40字符、单行、无首尾空白），如“专栏订阅合同”“平台”“读者”“支付订阅费”；只承担识别，不包含职责、依据、缺口、“候选”等状态标记或建模纪律。完整业务说明、已知事实、推断理由和剩余缺口写 `description`；跨候选的关系分析写 notes，来源仍用 sourceRefs，不制造第二份业务事实源。confidence 独立记录，界面负责添加候选标记，不在名称中重复写“候选推断”。

请求、确认字段各用一句简短业务说明，保留必要依据和局部未知；详细论证写对应 candidate.description／notes，不在字段中堆叠“系统不是合同一方”“不指定经办人”等通用建模纪律。不能为简洁删除真实业务条件或确认方式；长文本的展示截短不改变原文，完整依据按需查看。

**局部未知不抹去已知：** 例如材料已明确读者付款、平台提供权益、接收外部付款确认，就直接记录这些事实。支付期限和凭证提供方未知只记为对应缺口，不把整项支付义务重新当作未知，也不重复确认已明确事实。模型的候选／审核状态与这些事实是否有依据是两回事。

**以下是展示形式示例，不提供当前项目事实：** 假设材料已明确签署创作协议、平台要求作者持续交稿，且编辑代表平台按约催稿：

```text
所属约定：平台与作者的创作协议
候选履约：交稿
履约请求：平台（编辑代表）→ 作者
要求／依据：按创作协议持续交稿
履约期限：以本次交稿请求的截止时间（expired_at）为准；确定依据待明确
履约确认凭证：待明确——谁提供什么凭证证明本次交稿完成
```

AI 先说明对应材料位置及已知／未知，再问：“实际业务中，以什么记录证明这次交稿已经完成？”不直接补成“编辑验收通过”，也不因作者提交就认定履约成功。签约前的选题、试写和样稿协商留在渠道主线，不混入签约后的交稿履约。

如果用户只说“找作者写文章，按阅读收入分成”，尚不能确定双方约定，可以先提出候选合作关系并问“双方分别承诺哪些事情？”。不凭这个简短叙述自动确定请求人、付款周期、分成比例或编辑权限。

## 3. 领域主线：先找对象，再找身份与规则

```text
候选领域上下文与对象 → 身份 → 属性与关系
                   → 变化条件、资格、不变条件与计算 → 正常与反例
```

从具体痛点切入，不要求合同或凭证才能讨论领域知识。详细映射按需读 `domain-modeling.md`。

| 当前缺口   | 面向业务的追问                                                           |
| ---------- | ------------------------------------------------------------------------ |
| 对象含义   | 这里的客户是个人、公司还是档案？联系人和客户有什么区别？                 |
| 身份       | 如何判断两份资料是同一对象？同名、手机号相同、标识改变时怎样处理？       |
| 属性       | 哪些资料必须有、谁提供、允许怎样更正？字段是否真的有独立身份和生命周期？ |
| 关系       | 一个公司能有多个联系人吗？同一联系人能否属于多个公司？关系何时有效？     |
| 变化       | 什么情况下可以合并、归档或删除？冲突怎样处理？错误变化能否恢复？         |
| 约束与计算 | 什么条件必须始终成立？资格或等级依据什么计算？规则变化如何影响历史结果？ |
| 反例       | 两家不同公司共用财务联系人手机号，是否应合并？依据是什么？               |

这些是问题方向，不是一次性问卷。优先解决用户当前痛点需要的规则；档案去重先问身份，而不是先收集所有字段。区分客户本人、档案、联系动作和联系凭证；领域对象不全是 Thing，属性也不逐个造实体。业务上的修改／删除规则可以发现，但不提前决定数据库或 API。

v3 对操作、状态迁移、关系基数及复杂算法的表达缺口如实记录，由 Architecture 和后续 Q1/Q2 接续验证；不造假 Evidence 或假 Fulfillment 来声称已模拟领域操作。

## 4. 渠道主线：沿真实协商凭证展开

```text
真实邀请、报价或方案 → 请求与回应 → 协商规则 → 按需连接签约来源
```

先核对已有邀请或方案的发出方与接收方、回应、版本、有效期和接受／拒绝依据，按共用提问决策处理；不是逐项询问这些要素。可用 RFP → Proposal → Contract → Fulfillment 检视已有时间线，但这不是所有模型必须走完的流水线。

只展开真实存在的区域。固定套餐不补造 RFP；报价尚未接受不补造已签合同；RFP／Proposal 是签约前异步请求—响应凭证，不是履约项。协商中发现独立领域规则或真实协议时再连接相应上下文。

## 5. 共用循环：凭证、数据、回放与具体缺口

### 沿四色追溯继续回放

各主线共用第1节的“四色追溯的统一循环”，不重开另一套时间或派生问卷。在履约内向前寻找约定和请求依据，向后寻找完成与确认凭证；纯领域沿对象及规则、签约前沿真实协商凭证追溯，不补造合同。更正、退款、冲正和补偿追加凭证并保留原依据，不覆盖原凭证；这不意味着所有领域对象都不可修改。

### 正常、边界、异常回放

先复用材料中的实例与预期，或依据已明确规则推导合成正常、边界与异常回放，记录情节、预期、来源及 gap，区分真实案例与合成数据。仅在预期不能由已有业务依据确定时，请业务方说明具体争议或规则，不强索生产数据填测试字段。单据回放仅在当前可见凭证下判断能否请求、确认、计算和解释争议，自动场景固定 `asOf`。领域则回放对象规则的正常、边界与反例，不声称已执行单据模拟。

预期来自材料或人工回答，不从实现结果倒推，不为通过校验削弱预期。不适用须有具体理由；没有资料不能写成不适用。回放暴露缺口时回到对应合同、对象、凭证或规则，不重启整套范围问卷。

### 每轮如何推进

1. 承接扩展提供的当前完整视图、最新回答和材料，需要细节时用已有 read 分页读取视图文件，先消化全部新增事实，展示“本次明确 → 候选更新 → 仍待明确”及来源。合同履约用“请求 → 确认凭证”候选结构，不从操作清单或人工审批流程倒推业务。
2. 提问前先通过 evidence_save_discovery 追加本轮发现记录（包括首轮已有候选），再围绕其中一个关键缺口提出核心问题，带稳定 Q-ID、来源、焦点、影响、是否阻塞和 target。target 指向已保存的合同／履约，尚未定位为 null。若现有快照已完整反映当前理解，无需无变化地重复保存。不预排整套问卷，也不在一题中捆绑多个子问题；前文列举的是分析方向，不是每轮必须填完的表。
3. Agent 通过 `evidence_ask_questions` 保存后停止；扩展在 Agent 完全空闲后自动显示当前问题的“回答／结束本轮”菜单，选择回答直接进入编辑器。Esc 只关闭界面；`/evidence-answer` 可重开，带 Q-ID 可标注未知、排除、跳过或更正历史回答。等待期间不代答、不重复提问。未知不能解除业务阻塞，已排除项仍需有依据处理其依赖。
4. 问答开启时，保存人工输入后扩展自动启动一次消化：按最新 A-ID 修订候选及案例，更新 focus 和 contractView。用户一次给出多项事实时全部吸收，不对已经说明的内容重复问。跳过仅保留缺口，不冒充事实、不换 Q-ID 追问同一缺口；人工结束后不得自动追问。
5. 先用 `evidence_save_discovery` 追加消化后的发现记录，再决定下一问。不重写全部已知内容；更正与撤回引用此前记录，旧原文不可改写或删除。向用户简述“本次明确了什么、候选模型如何变化、还缺什么”，在 notes 中保留依据和变化。更正的旧原文保留，但不能继续支撑明确事实。没有必要的新问题可在保存后合法停止；资料充分可做隔离检查；只有人工选择更新模型才执行全历史评估并按结果定稿，不要求每轮交付正式 FM。

例如追溯分成金额：先问“按什么计算？”，若答“实收金额，按月结算”，则同时记录计算依据和账期，再根据材料决定是否追问退款扣减，而不是继续问已经回答的结算周期。此例不提供当前项目的业务事实。

### 稳定缺口与问题解决依据

历史问题是事实缺口索引，不是必做题队列。新问题须提供稳定 `gapKey`，由对象与事实维度组成，如 `c-004.payment-deadline`、`input.agreement`；纯领域／渠道也用对象或上下文标识，不因 target 为 null 混淆不同对象。同一缺口沿用原 gapKey 与 Q-ID，措辞变化、焦点切换、未知或暂缓都不是新缺口。提问前检查历史索引与相关事实；运行时拦截同标识重题和部分文本重复，不具备任意语义改写识别能力，不以换 gapKey 绕过。v5 问题必须有 gapKey；不兼容或转换旧日志，也不补写历史字段。

每次答完一题先消化全部事实；一次回答覆盖其他未答／未知问题时，通过 `resolution` 追加已有事实与原问题的关联，无需用户按 Q-ID 再答一遍。每条包含 `questionId`、`conclusion`、`reasoning`、`sourceRefs`、`citations`（各项 `sourceRef` 与逐字 `quote`）。说明这些原文如何完整覆盖该问题，推导写出依据和适用条件；每个来源都须有摘录。只允许 `INPUT`、有效 `SRC-*` 或最新状态为 answered 的 `A-*` 作解决依据，`D-*` 仅用于 supersedes。摘录存在的机器检查不证明推理成立，不得挑选片段掩盖冲突。

resolution 是可撤回的 Agent 解释，不是人工回答、业务批准、自动范围排除或另一套 FM。不得替代已有人工事实或排除决定；未知／跳过本身不是依据，不以“已停止”“范围外”“技术问题”为借口无来源地消除真实业务缺口。业务语义已经明确而旧问题仅追问物理映射时，可引用明确语义并说明技术映射交 Architecture，但不能借此改变业务规则。仅凭请求已识别或 start_at／expired_at 已展开，不得用 resolution 关闭期限确定依据问题。只有已有业务事实充分覆盖原题才关联解决：例如原文已明确双方逐笔约定截止且不采用统一公式，可以据此解释不需要固定时长；不能只引用“规定时间内付款”就宣称来源已解决。对其他凭证的时间、金额、数量同样如此。纯字段表示问题可由有依据的类型解释处理，但来源、签约行为、采信规则或计算口径仍未知时不得借此关闭；类型定义和业务来源缺口须分开保留。历史题目、人工回答与停止控制仍保持不变。

有效关联使该题不再待答或阻塞，历史题目和 A-\* 原文不变，界面标为“已关联依据”；来源版本、引用回答或该题后续人工回答变化会使旧关联失效。外部文件改动尚未追加来源时也不能将关联显示为有效；不能用无关 note 刷新来源。恢复或重选涉及这种关联的问题前，先用 `/evidence-run` 显式整理来源或撤回旧关联，避免磁盘状态与日志重放选题不一致；人工仍可按 Q-ID 补答。失效或撤回后按最新事实重新检查缺口，不自动弹题或恢复人工停止／暂缓。修订和撤回引用 `recordHeads` 的 `resolution:Q-ID` 当前 D-ID；重新建立须引用撤回记录。不适用的旧解释可撤回，但撤回本身不能解除该题阻塞。

仍缺事实时保持原问题；仅原文未答、未关联有效依据且未暂缓的问题可原 Q-ID 再选。已有回答由人工更正，真实冲突／缺少约定／范围决定由人工处理；Agent 不能删除问题、伪造 A-\* 或通过自我引用关闭缺口。

## 6. 记录与定稿边界

使用现有发现结构，不新增合同／领域 profile 或另一套候选 DSL：

- `scope / excludedScope`：Agent 整理当前展开部分、明确排除项及依据；待确认边界在 notes／问题中显式保留，不把 Agent 的猜测写成人工决定。
- `focus`：当前工作位置，不是阶段顺序；scope 仅用于具体边界歧义，不是默认前置任务。
- 派生 `contractView`：只读问答视图所需的发现候选关系投影，不是另一套正式模型，也不是 Agent 每轮提交的字段。contract 记录上下文、双方角色与来源；fulfillment 记录单个履约及 contractRef；position 记录 focus 与 current。`contracts` 中每个合同用 `contextRef` 引用候选 C-ID，`roleRefs` 有两个位置（未知位置为 null），附真实 `sourceRefs`。角色候选限于当前合同，不把跨合同的同一参与者误当成同一角色。`fulfillments` 各项引用 `candidateRef`，记录 `rightHolderRef`、`obligorRef`（来自合同双方且不同；未知为 null）、`request`（谁向谁提出什么要求及依据，有来源才写代表／经办人）、`deadline`（期限依据）、`confirmation`（谁提供或形成什么凭证、证明什么结果）和来源；全未知的文本为 null，部分已知保留原依据并标明剩余待明确。不默认确认人为任何一方，不默认人工验收、无期限或已完成。异常引出的新项同时记录 `parentFulfillmentRef` 和 `trigger`，前序须在同一合同且无循环；主要履约两者都为 null。`current` 为 `{contractRef, fulfillmentRef}`，只展开合同而未选履约时 fulfillmentRef 为 null；尚未定位时 current 为 null，无合同依据时 contracts 为空。记录类型字段严格校验，发现日志仅支持 v5；不兼容、不转换或迁移旧日志。
- 主界面标题和请求箭头两端只使用 label，不使用完整 description；展示合同双方、当前候选履约的请求端（谁向谁提出要求）、要求／依据、期限、确认凭证及当前问题。当前项详细说明和来源通过 F2 查看；完整履约结构与各候选描述通过 /evidence-status 查看，TUI 工具结果不重复输出。请求端箭头表示权利方要求义务方履约，不是付款方向，更不是 Agent 的问答；同一方在不同履约中可以互换权责。确认端保留有来源的凭证说明，不推导审批人，也不强制增加独立执行或验收阶段。推断标候选、未知标待明确，不把回答完成当作已经履约。问题的 `target` 决定正在讨论的关系，不根据名称猜测。详细来源与工程状态按需用 `/evidence-status` 查看。
- `notes`：当前展开的上下文、各候选间关系、履约清单或领域规则、凭证及数据来源、暂未展开项、异常与表达 gap；只写适用内容。
- `candidates`：稳定 C-ID、必填短名称 `label`、完整说明 `description`、`explicit/inferred/unknown`、`INPUT`／`SRC-*`／最新 `A-*` 来源。合同、角色、履约及领域候选均使用同样的名称／说明分工；candidate.modelRefs 仅为导航，不能代替事实级发布覆盖；部分未知的候选只映射实际纳入的已知事实，不把整体候选当作完成。名称必须有来源，不让人填写技术字段，不从长描述自动猜名称；名称更正同样追加记录并引用前次 D-ID。
- `cases`：正常、边界、异常的场景、预期、来源和 gap。材料明确不等于专家已批准。

### 只追加的建模记录

`evidence_save_discovery` 接受 `expectedRevision`、`summary`、`sourceRefs`、`records`。summary 说明本轮明确内容、解释变化和剩余缺口；来源仍是 `INPUT`、`SRC-*` 或最新 `A-*`。records 只提交本轮新内容：

| kind        | value                                                     |
| ----------- | --------------------------------------------------------- |
| scope       | scope、excludedScope                                      |
| position    | focus、current（未定位为 null）                           |
| note        | 本轮分析文本；有效 note 组合为视图 notes                  |
| source      | id、path、locator                                         |
| candidate   | id、label、description、confidence、sourceRefs、modelRefs |
| case        | id、kind、mode、scenario、expected、sourceRefs、gap       |
| contract    | contextRef、roleRefs、sourceRefs                          |
| fulfillment | contractRef 及单项履约字段                                |
| resolution  | questionId、conclusion、reasoning、sourceRefs、citations  |
| withdraw    | 无 value；supersedes 引用待撤回的当前 D-ID                |

每个普通记录均提供 supersedes：首次建立对象为 null，更正为该对象当前 D-ID；已有对象不能以 null 覆盖。D-ID 由扩展分配，形如 D-003-001（版本号、本轮序号）。从当前视图的 recordHeads 取引用，不猜 ID。更正保留稳定 C-ID／SRC-ID／CASE-ID；撤回后如重新提出，须引用撤回记录。缺省、漏交、空数组均不代表删除已有内容。撤回合同须同时撤回其履约并调整 position；其他悬空关系也必须在同轮明确处理。历史问题不支持 Agent 撤回；可追加有来源的 resolution 关联已知事实，未解决的业务缺口仍保留。

历史记录不可改写或删除。人工回答通过 UI 单独追加，回答更正引用前次 A-ID；Agent 不能提交或伪造人工回答。D-ID 表明某轮 Agent 曾作何解释，不把该解释当作独立业务事实。未知或跳过可以只追加说明缺口的 note，不必制造候选变化；仍必须先消化再追问。源材料只在显式追加其版本时捕获摘要，相关解释绑定该 SRC 版本；更正源材料必须显式更正依赖解释，不得靠无关 note 让旧来源变新。

不增加独立查询工具或固定查询工序。启动／续轮／恢复时先用有界上下文包中的待消化人工输入、当前对象及相关缺口；未内嵌的新输入必须按提示全部补读后再保存消化结果，不重新读一遍所有历史回答。已有 read 根据 offset/limit 读取 `.evidence/cache/discovery/<runId>/context-details.md` 中的逐对象原文、D-ID、失效标记及完整缺口索引。current.json 仍保留全部现状、recordHeads、withdrawnRecordKeys、staleRecordKeys，但不是每轮必读。核对 revision，新版本不沿用旧行号；摘要截短或省略不表示不存在、已解决或排除。切换讨论对象时按索引取相关明细，不重读全部方法或整份模型；更新评估仍覆盖全历史，阻塞、来源和回放按本批次职责及具体事实依赖判定，不要求关联 Context 整体完成。历史记录用 read 按 D-ID 中的版本号读取对应 revision 文件。两个缓存均可覆盖重建，不是不可变凭证、独立业务来源或 Gate 输入；损坏或丢失不影响从记录链恢复，校验不信任缓存。文件 revision-N.json 只含本轮事件，不能把链尾当作完整快照。

发现记录由扩展追加到 revision-N.json，校验整条摘要链后重建当前视图，不直接写 discovery 文档，不支持旧数据迁移。正式 FM 可附引用记录链的 discovery 摘要，但它不是第二份事实源。只有无独立业务／领域语义的简单胶水才可声明 FM 不适用，仍按本地发现、定稿和共同 Gate 完成；缺少合同不是不适用理由。

人工选择更新模型时调用 `evidence_finalize_discovery` 评估全部已积累成果，依次更新统一语言和 FM 后停回发现；人工另选 converge 才开始软件需求收敛，最后共用 Modeling Gate。模型默认 draft／pending，具名专家审核、机器校验、实际模拟、人工 Gate 各自独立，不因候选已整理或机器通过就提升审核状态。
