# 8X Flow 范围识别与事实发现

输入是业务叙述、领域问题、Epic、访谈或事实尚不完整时读取。本阶段先识别当前问题与上下文，再按范围提问；不把所有材料送进合同发现流水线。

## 发现 Gate

- 用户明确本次要解释的问题、边界，并给出足够的业务／领域事实时，可直接建模并保留来源定位。
- 材料有歧义时，先记录显式事实、候选、推断和问题；不靠技术常识补齐合同、身份、权限、公式或期限。
- 合同、渠道与领域是可组合的上下文，不是按产品名称互斥选择的模式。同一 CRM 中，绩效、客户档案、签约渠道与拨号工具可以属于不同范围。
- 纯领域缺合同不是 blocker；纯渠道尚未签约也不是 blocker。简单集成不含独立领域规则时，可输出不需建模的范围说明并结束，不反复索要权责材料。

## 1. 先由人提供问题与事实

业务方／领域专家先给出当前问题、真实材料、自己的对象解释或时间线。Agent 可以抽取候选并核对，但不先交付完整答案让人挑选。

先记录：

```text
当前问题：
已知事实与来源：
本次展开的范围：
明确不展开的范围：
待确认的边界：
```

不确定是否存在协议时，询问价值、责任与留痕；不因材料未出现“合同”就判定系统无价值，也不因出现“客户”就自动归入销售履约。

## 2. 按上下文发现

### 合同与履约

从收入、支出或目标—实际/KPI 找业务脊梁，询问双方 Role、谁有权要求谁做什么、完成凭证、期限与违约。对外交易与绩效协议共用同一机制。

绩效目标还要确认：目标是在签约前谈妥，还是执行中允许变更？由谁提目标，谁必须回应，谁可同意／拒绝／要求修改？不要预设主管永远是权利方，不自动创建“目标设定履约”。

### 签约前渠道

有业务时间线时，可用四阶段工作板：

```text
邀请投标 RFP → 投标 Proposal → 合同 Contract → 履约 Fulfillment
```

它是凭证发现的工作板，不是所有模型必须完成的四阶段流水线。纯渠道只展开已知区域；固定套餐也不必补造 RFP。RFP／Proposal 是异步请求—响应凭证，不是履约项。

候选凭证示例：

```yaml
id: candidate.payment-request
phase: fulfillment
label: 付款请求
producedByRoleCandidate: 销售方
addressedToRoleCandidate: 购买方
basedOn:
  - candidate.sales-contract
proves: 销售方已主张购买方在约定期限内付款
sourceLocator: 合同第 5.2 条
confidence: explicit
openQuestions: []
```

### 领域

按 `domain-modeling.md` 发现领域对象、身份、属性、关系、行为条件、状态约束和计算。先让专家解释对象如何区分、如何关联、什么情况下可变化；不要求把领域事实翻译成合同单据。

```yaml
id: candidate.customer-profile
label: 客户档案
proposedCategory: participant
proposedKind: thing
contextCandidate: 客户信息领域
identityQuestion: 同一客户的多份档案如何区分或合并？
sourceLocator: 客户资料管理访谈第 2 段
confidence: explicit
openQuestions:
  - 档案与客户本人是否一一对应？
```

所有发现记录的 `confidence` 使用 `explicit`、`inferred`、`unknown`。它们是 discovery 格式，不是新的 FM Entity 字段。

## 3. 按实际关系组合并回放

- 领域对象是业务输入或标的时建立明确引用；不要把名称相同当成同一对象。
- 领域对象、执行动作、履约确认和工具调用分别是什么，要逐一说明。
- 合同间用允许的确定性凭证连接；不因流程相邻就直接连接合同。
- 请业务方回放权责与时间线，请领域专家回放对象规则的正常／边界／反例；仅确认当前范围。

## 4. 产物与进入正式模型

按范围选择发现产物，不机械生成全部文件：

```text
discovery/
├── scope.md
├── evidence-inventory.yaml     # 有凭证发现时
├── domain-inventory.yaml       # 有领域发现时
├── timeline.md                 # 有时间线时
└── open-questions.md
```

显式事实进入同一 FM YAML；推断和未知项留在 discovery。部分模型可以保持 `draft`，但不通过伪造确认、期限或合同来满足 Schema。

- `draft`：当前范围仍待确认；review 为 pending 或实际 rejected。
- `reviewed`：具名业务／领域专家已检查，仍可有已知 gap。
- `confirmed`：具名审核者明确确认当前范围，不代表整个系统均已建模。

## 完成检查

- 是否先界定当前问题，而不是强制先找合同？
- 是否在同一格式内区分并按需展开合同履约、渠道与领域？
- 问题是否针对实际未知项，而不是要求补齐缺席的上下文？
- 是否区分客户本人、客户档案、联系行为及联系凭证？
- 候选是否有来源和确认状态，未确认内容是否仍诚实保留？
- 不需建模、局部模型和待确认发现材料是否都有明确完成边界？
