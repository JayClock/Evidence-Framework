# 软件需求收敛

需求不是建模的前置完整答案。先通过交互建模理解业务，再选择本次由软件实现、只接收结果或保留人工处理的部分。

## 输入与执行

1. 读取原始输入、当前发现快照、统一语言、FM 源文件/状态及场景。正式模型不得反向依赖这里才生成的故事。
2. Empathize：从实际参与者与工作场景识别痛点、目标、成功条件，不为满足配额补造角色。
3. Define：说明问题、现状与目标，选择 MVP 并明确不做事项；模型中所有业务活动不自动成为软件功能。
4. Ideate：按可观察价值组织用户旅程、必要 Epic 和薄切片。数量按范围，不强制三种画像或六个故事。
5. 保留来源链：问题/回答/材料 → 模型 ID、规则、回放案例 → 软件能力 → US/AC。区分已知事实、假设与未决项；未知金额、期限、权限等不得自行补齐。
6. 发现核心矛盾时调用发现工具重开 Modeling，不在需求文档中维护另一份业务规则。下游反馈也回退 Modeling，共用一个 Gate。

## 验收契约

- 故事说明“作为谁，希望什么，以便获得什么价值”，界定软件职责及外部/人工边界。
- 每个故事覆盖正常、异常和适用边界的可测试验收场景；预期结果来自已核对模型和回放，不从实现倒推。
- 分配稳定 US-xxx 和 AC-<故事编号>-<序号>，给出 Given/When/Then、示例数据及预期；修订不重编号、不复用废弃 ID。
- story-map.md 输出且只输出一个 acceptance-catalog JSON，声明全部故事及场景，与叙述一致。它是下游测试计划的契约，不是测试已通过的证明。
- 性能、安全和可用性约束须有依据；未知指标标注影响，不预选技术框架或测试替身。
- 未解决的核心规则必须继续发现或移出本次范围，不直接交给编码。

## 工件

按当前任务依次提交 `personas.md`、`problem-statement.md`、`story-map.md`，路径仍为 `artifacts/01-requirements/`。这是 Modeling 的需求投影，不是独立 Requirements 阶段或 Gate。

每个定稿任务以 `evidence_submit_artifact` 提交完整当前文档；不直接写工件。最后一个故事目录提交后，由扩展重检发现、模型和需求并创建 Modeling Gate。
