# Evidence requirements

使用 Design Thinking 将项目描述转化为可审核、可追溯、可测试的需求工件。

## 工件驱动

1. 读取 `artifacts/00-input/requirements.md` 和当前任务列出的上游工件；文件是跨 Session 的交接依据。
2. 直接生成当前指定工件，不先进行分批问答，也不要求用户单独确认业务基线。
3. 区分原始需求中的事实、分析假设和待决策项。写明事实来源及不确定性对范围和验收的影响，不把推断标为已确认。
4. 业务疑点写入工件的开放问题部分，交由 Requirements Gate 集中审核。金额、期限、权责、权限、审批及异常后果等关键事实不能凭常识补造；人工可在 Gate 要求补充或缩小范围。
5. 修订时读取已有输出与人工反馈，逐项修正，不丢弃已经明确的约束和排除项。影响实现的关键规则未解决前，不应纳入下游编码范围。

## 工作流

1. **Empathize**：从利益相关者视角识别场景、痛点、动机和可衡量的目标，区分输入依据与推导内容。
2. **Define**：区分核心问题和候选解决方案，定义现状、目标状态、MVP 边界与约束。
3. **Ideate**：按用户旅程、Epic 和可交付薄切片组织能力，明确优先级与排除项。
4. 保留角色需求、MVP 能力、用户故事和验收标准之间的追溯关系。

## 质量原则

- 用户描述是证据，但不自动等于完整的问题定义。
- 保持 MVP 足够小，明确后续迭代和不做事项。
- 用户故事表达可观察价值：“作为…我想要…以便…”。
- 每个故事至少三条可测试验收标准，覆盖异常或边界情况。
- 除用户明确约束外，不提前决定实现技术。
- 不虚构法律、安全、预算或运营事实；关键未知项交由人工审核。

## 输出

扩展每次指定一个输出及模板：

- `evidence-personas.md`
- `evidence-problem-statement.md`
- `evidence-story-map.md`

以 `evidence_submit_artifact` 提交完整的当前工件，作为任务的最后一个动作。
