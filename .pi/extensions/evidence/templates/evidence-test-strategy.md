# 测试策略

## 目标与风险

从已批准的需求、验收场景、领域不变条件、API 契约及质量属性提取主要风险，引用来源和稳定 ID。保留 FM Context/Entity/Rule 引用及适用的 Fulfillment/Evidence/Scenario ID；模型模拟通过不是软件验收通过。纯领域结构和 lineage 不验证对象实例/操作/状态机，需为规则及 Modeling README / module-structure 中的表达 gap 安排正常、边界和反例的 Q1/Q2 测试，不补造单据场景。

## 四象限

按受众与目的分类，而不是按工具或测试层级分类。逐项说明 Q1–Q4 的适用性；不适用时写明原因和剩余风险，不能用空白代替判断。

| 象限 | 受众与目的 | 场景/风险来源 | 测试方式 | 执行时机 | 负责人角色 | 通过标准/证据 |
| :--- | :--------- | :------------ | :------- | :------- | :--------- | :------------ |

- Q1：技术导向、支持团队，提供细粒度反馈和问题定位。
- Q2：业务导向、支持团队，验证验收场景的业务行为。
- Q3：业务导向、评价产品，如探索性测试、可用性评价和 UAT。
- Q4：技术导向、评价产品，如性能、容量、可靠性和安全测试。

四象限不是四个执行阶段。提前规划 Q3/Q4 的环境、人员和时机；不要求全部自动化，也不等到最终审查才考虑。测试金字塔用于检查反馈速度与成本分布，不代替测试策略。

## 功能上下文

功能上下文是被测功能边界，不等于 DDD 限界上下文；可以是函数、组件，也可以是有理由合并测试的 API 与应用层。说明职责、接口、隔离点及拆分或合并的成本依据，不强制每个架构层单独测试。

| 功能上下文 ID | 模块/组件与职责 | 象限/目的 | 被测边界 | 拆分或合并理由 | 关联验收场景/风险 |
| :------------ | :-------------- | :-------- | :------- | :------------- | :---------------- |

## 测试替身

逐边界选择真实实现、Dummy、Fake、Stub、Spy 或 Mock，说明替换位置、理由及未覆盖风险。用于行为期望验证时再选择 Mock，不默认所有依赖都 Mock。不要替换被测业务逻辑。

| 功能上下文 ID | 真实依赖 | 替身依赖与类型 | 注入/隔离方式 | 未覆盖风险与补充验证 |
| :------------ | :------- | :------------- | :------------ | :------------------- |

按仓库事实选用现有工具，区分“已存在”“待引入”“待定”；读取 package.json、apps 中相关构建配置与测试。不要照搬课程示例引入 Jersey、MyBatis、H2 或 Flyway。持久化不适用时不虚构数据库；如使用内存数据库或 Fake，说明与生产数据库的差异及真实依赖验证方式。

## 追溯规则

定义“故事 ID → 验收场景 ID → Q2 测试 → 支撑工序任务/Q1 测试 → 实现”的关联方式，沿用 AC-001-01 等已有场景 ID，FM ID 保持独立关联。列举代表性映射说明规则，不在这里生成整个 Sprint 的实施任务。

Q1/Q2 可为多对多关系。访问数据库的组件测试也可能属于 Q1；Q2 不必都是浏览器端到端测试。Q1 为业务行为提供诊断支撑，但 Q2 失败不保证 Q1 同时失败，装配、配置及跨组件契约仍需要集成验证。明确 Q2 的真实执行路径和剩余替身边界，不能仅靠各层 Stub 测试宣称系统集成通过。

## 测试数据与环境

说明示例数据、正常/异常/边界数据、创建和清理方式、测试隔离、时钟/随机性/外部服务控制及可重复性。使用合成或脱敏数据和独立测试环境，不使用生产凭证或破坏生产数据。

## 执行与通过标准

区分聚焦反馈、故事验收、全项目回归及人工评价。为每项给出可执行命令或人工步骤、先决条件、输出证据和失败处理。未存在的脚本标为待建设，不写成已经运行成功；未经批准的性能或安全阈值标为待决策。

保留 .pi/evidence.json 的现有质量命令。npm test、lint、build 的通过不能自动证明四象限全覆盖、性能达标或 UAT 完成。

## 风险接受

记录未覆盖范围、环境缺失、替身局限和待决策项，说明影响、补充验证、负责人角色与需要人工批准的条件。交由 Architecture Gate 审核，不自行批准例外。
