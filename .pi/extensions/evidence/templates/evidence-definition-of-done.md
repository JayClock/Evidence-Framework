# Definition of Done

## 完成标准

| 维度 | 标准 | 验证命令或证据 |
| :--- | :--- | :------------- |

至少包含 8 个维度：验收标准、真实 TDD、Q1/Q2 测试、代码质量、架构契约、安全、文档、构建或可运行性。标准必须可观察、可重复验证，避免“代码质量良好”等主观表述。

依据 test-strategy.md、test-procedures.md 和 Sprint 任务补充：

- 每个承诺的验收场景 ID 有通过的 Q2 证据，并关联支撑 Q1 测试，不能以总体覆盖率或测试数量代替场景验收。
- 每个适用工序有对应测试/实现及验证结果，复用或不适用项有明确依据；核对真实依赖与替身符合策略。
- 按 Sprint 承诺明确适用 Q3/Q4 评价的完成时机、负责人角色、阈值来源、环境和证据；UAT 需要实际人工结论，不能由测试命令代替。
- 每个 tdd CHECK 有扩展记录的完整循环，所有适用任务及 verify 检查完成；故事级 Git 基线保留，全部计划检查和 .pi/evidence.json 的全项目质量命令重新通过，不把拟议脚本写成已执行。
- 结构化编码记录保存契约摘要、场景/任务/工序/检查项引用、逐循环输出和复用/验收结果；最终审查重新验证这些记录，不仅查看 Markdown。

机器验证声明和执行元数据，不证明测试断言覆盖全部场景语义、替身选择正确或 Q3/Q4 达标。逐场景覆盖与工序符合性仍需实际测试及人工审查。

## 验证顺序

说明聚焦反馈、故事验收、全项目回归及适用 Q3/Q4 评价的执行顺序。区分自动命令与人工步骤、已具备环境与待建设环境，并明确什么结果会阻塞完成。

## 例外处理

定义无法满足某项标准时如何记录影响、由谁批准、何时补验，以及技术债如何进入 Backlog。待人工执行或缺失证据不能标为通过；文档中的例外不允许绕过扩展现有阻塞质量检查。
