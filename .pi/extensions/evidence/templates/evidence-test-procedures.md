# 测试工序

## 工序目录

以 test-strategy.md 为依据定义通用工序，保持测试边界和替身决策一致；两份工件在 Architecture Gate 一起审核。工序是场景内的开发方法，不是新增宏观阶段，也不是一份按技术层排期的 Backlog。

| 工序 ID | 适用条件 | 功能上下文/象限 | 目标 | 输入 | 完成证据 |
| :------ | :------- | :-------------- | :--- | :--- | :------- |

使用稳定的 `TP-*` ID，例如 TP-DOMAIN、TP-API、TP-UI、TP-PERSISTENCE、TP-ACCEPTANCE；只保留实际适用的工序，不为凑齐目录虚构模块或基础设施。修订时保留 ID，合并或废弃时说明替代关系。

## 工序定义

对目录中的每个工序分别说明以下内容，不能只有一张目录表：

1. **目标与适用性**：解决的风险、被测功能上下文、所属象限及不适用条件。
2. **输入契约**：故事与验收场景 ID、目标组件/功能、相关领域规则或 API 契约、测试数据和预期结果；Planning 再填入具体场景。
3. **依赖与资源**：哪些是真实实现，哪些使用何种替身，如何注入；沿用测试策略，不重新随意选型。
4. **准备与清理**：环境先决条件、夹具和数据隔离、时钟/随机性控制、结束或失败后的清理。
5. **操作步骤**：先列场景与数据，再写测试并核对行为失败，最小实现使测试通过，重构保持行为不变，最后运行关联回归。已有行为复用现有测试，不能人为破坏它制造 Red。评价类工序应定义评价步骤，而不是强行套用 TDD。
6. **验证与产物**：测试文件位置/命名约定、现有执行命令或人工步骤、断言目标、结果证据、通过标准。待建设的脚本注明状态，不能伪装成现有命令。
7. **退出与异常**：环境失败不算 Red，失败如何定位和反馈；是否需要后续集成或人工评价才能完成场景。

技术细节放在对应工序小节中，编码时按适用工序读取；不要把所有实现范例塞进公共提示词。遵循现有 React/TypeScript、Spring Boot/Java、Vitest/Testing Library、JUnit 的实际配置，不引入未经批准的框架。

## 机器可读工序目录

只输出一个 `kind=test-procedures` 的 JSON 代码块，与工序目录和逐项定义一致。示例不是固定选型，应替换为当前项目的全部工序；每个工序有且只有一个主要象限。

```json
{
  "kind": "test-procedures",
  "version": 1,
  "procedures": [
    { "id": "TP-DOMAIN", "quadrant": "Q1" },
    { "id": "TP-ACCEPTANCE", "quadrant": "Q2" }
  ]
}
```

## 场景实例化规则

Planning 按“故事 → 验收场景 → 适用工序 → 可验证任务”实例化，保留场景 ID、工序 ID、数据和预期结果。每个验收场景关联 Q2 业务验证和支撑它的 Q1 测试；不涉及的边界记录 N/A 及理由。

按端到端薄切片安排场景内依赖，不固定“先做所有持久层，再做所有应用层”。允许合并低价值边界、复用已有测试及共享前置任务，说明理由并避免重复建设。集成工序明确真实执行路径，不以彼此隔离的替身测试代替场景集成验证。

Q3/Q4 评价按测试策略安排负责人、环境、时机和证据，不要求每个场景重复执行整套评价，也不留到最终审查才首次规划。

## 证据与例外

区分计划中的验证方式、已执行的命令结果、人工评价结论及尚未验证项。不适用、复用和缺失基础设施均需说明理由及影响；冲突或无法满足的要求交由 Gate 审核，不能静默改动策略或验收标准。

Planning 的机器计划为每项 Q1/Q2 任务指定 `tdd`、`verify` 或有理由的 `not-applicable`。新增行为通过 `evidence_tdd_red` → `evidence_tdd_green` → `evidence_complete_tdd_cycle` 追加循环，可在同一任务/检查项下完成多个行为，不消耗修订轮次；复用和业务验收通过 `evidence_verify_task` 实际执行全部检查，不伪造 Red。故事完成时重跑所有适用检查及质量命令。

Q3/Q4 仍由计划和 DoD 安排人工证据，不放入当前自动执行计划。机器核对的是声明的 ID、依赖、文件与命令记录；不能证明测试断言覆盖了全部语义、替身符合策略或 UAT 已完成，仍须人工审查。
