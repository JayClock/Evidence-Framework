# FM 到实现的映射

业务含义唯一维护在 [FM 源](../../.evidence/fm/model.json)、[业务概览](../../.evidence/fm/00-overview.md)和 [统一 JSON 词汇表](../../.evidence/glossary.json)。本页只规定实现映射，不建立第二套业务事实。

## 对象与行为

| FM 概念                | 实现选择                                                                           | 不允许的推导                                        |
| ---------------------- | ---------------------------------------------------------------------------------- | --------------------------------------------------- |
| 稳定主体 / Thing       | 根据实例身份与生命周期选择 Entity、强类型 ID 或 Ref                                | 每个声明 ID 都是数据库主键；每个节点都建表          |
| 无独立身份的描述       | 不可变 Description / 值对象                                                        | 为 HTTP 可写性修改领域不可变性                      |
| Context / rootRefs     | 业务边界与根集合入口；domain 声明 Context 接口，适配层注入实现，成员/角色拥有行为  | 每个 Context 自动建服务；所有对象全局 CRUD          |
| 主体角色               | 由 Context 接口切换得到的具体角色对象，如 `inSubscriptionContext().asReader(user)` | 角色名等同登录认证或权限凭证；`asRole` 默认重读主体 |
| 证明角色               | 消费方能力接口或原凭证视图                                                         | 新建一份证明及签发时刻；把资金责任移给消费者        |
| 拥有者关联             | HasOne、HasMany 或有语义的 Optional，必要时窄/宽接口                               | 为只读关系虚构写能力；用公共可变集合泄露内部状态    |
| 业务 Rule              | 实体、Description、角色对象及其拥有者关联的行为                                    | 放入 Resource、Mapper 或无领域责任的 Service        |
| Request / Confirmation | 保留事实、实际时间、匹配与数量语义                                                 | 请求受理就是到账/完成；以状态覆盖删除历史违约       |

映射细节与固定框架约束见 [设计规则](../../.agents/skills/evidence-task-planning/references/design-rules.md)。每个实际任务必须引用它消费的源 ID，而不是只引用本页。

## 中英文与字段追溯

业务中文、含义和源 ID 以正式术语/FM 为准；代码、HTTP 和数据库采用各层命名风格，并在任务中明确映射。英文名称不构成新的业务身份。

| 中文定位               | 源标识 / 字段                               | 实现映射纪律                                                                                       |
| ---------------------- | ------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 用户主体               | `party.user`                                | 已有 `User` / `Users`；不为读者、支付用户复制主体                                                  |
| 读者角色               | `role.reader`                               | 具体 `Reader` 角色类，通过 `SubscriptionContext.asReader(User)` 切换；不能合并为通用 User 权限字段 |
| 合格付款证明           | `role.payment-proof`                        | 证明能力，不对应新的资金结果表                                                                     |
| 专栏 / 上架版本        | `column_id` / `edition_id`                  | 身份粒度不同，不能互换或只保留当前版本                                                             |
| 请求开始 / 截止        | `started_at` / `expired_at`                 | Java 使用对应 camelCase 时保持业务含义与边界闭合                                                   |
| 签约 / 确认 / 补充记录 | `signed_at` / `confirmed_at` / `created_at` | 不统称 createdAt；通知到达另有含义                                                                 |
| 显示名称               | 本地软件字段 `displayName`                  | SQL `display_name`；非 FM 属性，范围见用户切片说明                                                 |

新增实体/属性时记录中文、英文代码名、源 ID、API 字段与 SQL 列名；含义或名称存在歧义时回到来源确认，不新增同义类绕过已有拥有者。通用工程词汇见 [命名规范](../engineering/conventions.md)。

## 场景到检查

按相关 FM 场景准备固定事实和业务时间，保留正常、边界、反例及失败不变性。例如恰到付款截止、晚到证明、退款后旧版资格与历史履约必须分别判断；精确规则仍引用对应 YAML，不在实现指南复制金额/时限。

domain 测试证明业务判断，API 测试证明协议与调用边界，persistent 测试证明 SQL/回滚，app 测试证明真实装配。业务期望不得从当前实现输出反推。
