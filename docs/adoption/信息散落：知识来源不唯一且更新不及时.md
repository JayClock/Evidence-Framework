# 信息散落：知识来源不唯一且更新不及时

## Bad Smell

计划里引用的是旧接口，代码已经改了，生成页面还停在前一次更新。三份材料都能打开，Agent 选了最顺手的一份开始实现，直到检查时才发现输入不一致。这里的麻烦不只是“资料太多”，还有每份资料负责什么、什么时候失效没有说清楚。

Evidence 的材料本来就分散在不同目录：`.evidence/fm/` 保存业务模型，`.evidence/api/api.json` 保存接口设计，`docs/requirements/` 界定软件职责，`docs/architecture/` 记录技术取舍，`plan.yaml` 保存任务及状态。不能为求方便把它们合成一份“最新说明”。同一件事如果在两个地方都能被修改，迟早会出现两个版本。

## Solution

### 给来源定归属，也给派生物定身份

[Guides 导航](../guides/index.md)的来源表把每类问题送回对应文件。业务事实不能靠当前代码反推，任务是否完成不能靠 `review.html` 判断。后者是可重建的审核投影，状态只在 `tasks[taskKey].status`。OpenWiki 页面也只作按需导航，源码和测试仍是实现行为的依据；生成页里标出的未知项只是待核实的问题，不会自动变成需求。

计划的 `sourceManifest` 保存来源路径、稳定 ID 和摘要，任务以 `sourceRefs`、`procedureRefs` 记录自己用了哪些来源。这让变化可以定位：接口设计文件的摘要对不上，依赖它的规划输入需要重新编译；架构指南变了，即使 FM/API 摘要都没变，任务的实现前提仍要重新核对。一个哈希能发现字节变了，不能判断变化的业务含义，更不能替代看当前代码和运行环境。

摘要还要和文件的职责一起读。假设 FM 的某个场景变了，来源摘要能提醒模型输入不一样，却不会自动告诉你接口是不是需要重设计，更不会替用户批准软件范围扩大。反过来，后端规范加了一条依赖限制，FM/API 的哈希可能一字未变，已规划任务的实现方式仍需重新评估。只盯着编译输入的哈希，就会把来源检查缩减成一道看似精确、实际覆盖很窄的门。

更新关系也不是简单的“谁新谁赢”。发现记录保存过往回答与更正链，FM 承载正式业务模型，需求写本次软件职责，代码呈现当下实现。发现记录里新出现一个问题，不表示 FM 已经错了；代码比接口契约更新得晚，也不表示代码的选择自动获批。要逐项说明变化影响哪一种事实，再决定是修实现、重编译计划，还是交给上游确认。

外部技术资料同样要有可复现版本。本项目的技术 profile 在相应 Skill 的依据文件里固定了文档版本；只记一个会移动的分支名，后面就没法确认当时按哪套规则设计。版本更新时应检查受影响约定，而不是偷偷让旧计划继续消费新文本。

### 新鲜度在开工时检查

[开工检查](../guides/index.md#任务开工检查)要求看直接依赖是否完成，来源摘要、工程指南、代码和 CHECK 环境有没有变化。`plan_state.py` 能报告结构状态，却不会替人做完全部新鲜度判断。昨天通过的测试，如果输入、依赖或环境已经变了，只能算历史记录。生成 API 投影与权威 `api.json` 不一致时，先重新生成，再讨论接口工作，不要改投影让它看上去一致。

OpenWiki 有定时更新工作流，产出通过 PR 供人检查，而不是直接把新页面提升为事实源。即使自动刷新成功，页面中的结论仍需追到源文件；即使刷新失败，已有页面也不能冒充当前仓库的完整快照。维护时应改源代码或源文档，让投影重新生成，不手工修饰生成页。

发现冲突时，先把不同文件各自声称什么写清楚。若是代码与契约不符，受影响的接口实现停下来核对；若是软件范围尚未确定，交给需求拥有者；若只是生成物过期，重建它。把所有差异都称作“文档没同步”，往往会把真正需要业务裁决的问题藏掉。
