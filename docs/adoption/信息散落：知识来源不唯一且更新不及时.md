# 信息散落：知识来源不唯一且更新不及时

## Bad Smell

信息散落指的是知识进了仓库却没有随来源更新，仓库里留下的是事实的旧版本。本项目的知识分布在多处：业务事实在 `.evidence/fm/`，API 设计在 `.evidence/api/api.json`，软件范围在 `docs/requirements/`，技术基线与领域映射在 `docs/architecture/`，做法在 `docs/engineering/` 与 `docs/howtos/`，任务状态在 `plan.yaml`，另有 `.evidence/*/generated/` 投影、`openwiki/` 生成页与 `.evidence/checks/` 检查记录。任何一处落后于来源，Agent 都会自信地按旧版本执行。

常见症状是：把生成产物或上次通过的检查当成当前事实；用 FM/API 摘要替代架构、规范与代码变化；沿用未核对的上游文档版本；`openwiki/` 页面在源码改动后仍被当作导航依据；计划还按旧 `api.json` 编译，却已经用于派发任务。

## Solution

项目把每条知识当作对外部来源的依赖：来源唯一、随计划登记、开工核对、摘要绑定、定时刷新。本仓库当前的外部来源主要是固定 commit 的 smart-domain 文档与仓库内权威源，于是把依赖信息拆在机器计划的 `sourceManifest`、上游依据与 OpenWiki 页面来源中，还没有单独的 SOURCE.md。

### 来源唯一：权威位置与冲突裁决

[AGENTS.md](../../AGENTS.md)的不变量先定死事实源：业务事实只在 `.evidence/fm/`，API 设计只在 `.evidence/api/api.json`；软件范围、实现设计与当前代码行为分别记录、不能相互冒充，生成产物不是新的事实源。

[Guides 导航](../guides/index.md)的“来源与冲突处理”表为每类问题指定唯一权威位置，并列出“不可替代它的内容”，生成产物、过期 OpenAPI、代码现状都不算数。冲突时的规则是：

> 先说明各自管辖范围及差异，停止受影响行动，交由相应拥有者确认；不能按读取先后、修改时间或“代码已经这样写了”裁决。

[README](../../README.md)的“仓库中的唯一职责”表把同一件事落到目录职责；[生成页](../../openwiki/concepts/evidence-sources.md)复述该模型只作导航，不构成新的事实源。

### 来源登记：计划清单、投影与页面元数据

- 机器计划的 `sourceManifest` 登记来源路径、稳定源 ID、摘要或版本与适用章节；任务记录用 `sourceRefs`、`procedureRefs` 声明本次实际消费的来源。
- `sourceManifest` 直接对权威来源记录 digest：业务模型、接口设计、软件范围、架构与工程规范逐条登记路径、稳定源 ID、适用章节与 sha256。权威来源一旦变化，摘要不再匹配，编译结果失效、必须重算，把“知识依赖升级”变成可检测的字节差异。
- 生成页面与其结论清单把每条结论绑定到具体文件，并带 `repo-file-v1:sha256:…` 文件级内容版本，源变化时可据此判断主张失效。

### 更新义务：开工前的新鲜度检查

[Guides 导航](../guides/index.md)“任务开工检查”第 3 项要求核对：依赖是否完成？源摘要、规范/架构变化、当前代码及 CHECK 环境是否使旧证据失效？[交付生命周期](../../.agents/skills/evidence-delivery/references/lifecycle.md)进一步要求判断哪些业务源、架构、规范、howto、代码或环境变化使旧证据失效，并明确不以 FM/API 摘要代替全部新鲜度判断；[机器计划模板](../../.agents/skills/evidence-task-planning/assets/plan-template.yaml)把相同纪律保存在任务 `guides.freshnessRisks`。

只读状态检查不假装做过这项判断：`plan_state.py` 每次输出 `sourceFreshness: "not-checked; recompile FM/API inputs before delivery"`，提醒先重算投影再做交付。

### 防过时：摘要与版本绑定

| 机制     | 落点                                                                           | 绑定方式                                                                                        |
| -------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| FM 校验  | [建模指南](../evidence-modeling.md)                                            | `modelDigest` 绑定相对路径与字节内容；`inputChanged` 标记检查期间输入变动；旧记录不证明当前版本 |
| 运行记录 | `.evidence/checks/<类别>/<运行标识>.json`（获授权时）                          | 只保存紧凑清单：命令、退出码、环境、输入摘要与日志 `sha256` 指针；旧记录清空后不再充当证据      |
| 输入摘要 | FM `modelDigest`、API `manifest.json`、计划 `sourceManifest`/`inputDigest`     | 输入/输出 sha256 绑定具体版本；投影与权威 API 哈希不一致时重新编译                              |
| 外部上游 | [上游依据](../../.agents/skills/evidence-task-planning/references/upstream.md) | 固定 smart-domain 文档 commit 与核对日期；“main 是定位入口，不是可复现版本标识”                 |
| 生成页面 | [openwiki/.page-manifest.json](../../openwiki/.page-manifest.json)             | 每页 `gitHead` + `sourceFingerprint` + `pageVersion` + `completedRunId`                         |

生成字节也被当作有版本的依赖：API 投影、OpenAPI 与派生交付按权威字节交付，`.prettierignore` 保护生成物不被格式化改写，使“用 `project` 逐字节复现”成为可验证的承诺。

### 主动刷新：OpenWiki 定时工作流

[.github/workflows/openwiki-update.yml](../../.github/workflows/openwiki-update.yml)每天 08:00 UTC（cron `0 8 * * *`）或手动触发一次 `openwiki code --update --print`：

- `fetch-depth: 0` 让更新能 diff“上次记录到哪个 commit”，浅克隆会退化成空变更摘要；
- 产出走 `openwiki/update` 分支的 PR，`add-paths` 限定 `openwiki`、`AGENTS.md`、`CLAUDE.md` 与工作流自身；
- `continue-on-error` 加 `create-pull-request`：生成失败时仍保留已完成页面，最后由 `exit 1` 把工作流标红。机器负责刷新，人工合并即审核；
- [.openwikiignore](../../.openwikiignore)限定文档代理读取集，排除 `node_modules/`、`.nx/`、`.gradle/`、构建与临时输出以及二进制；
- 运行状态由 [.last-update.json](../../openwiki/.last-update.json)与 [.page-manifest.json](../../openwiki/.page-manifest.json)推进基线，瞬态 `openwiki/.run.json` 在工作流结束时删除。

### 生成物不是事实源

`AGENTS.md` 的 `<!-- OPENWIKI:START -->` 受管块声明：`openwiki/` 是可选即时上下文而非启动必读；源码与测试才是权威，brief 中的未知项与 review 项是验证缺口；不要手改生成页面，应更新源码或文档让 OpenWiki 重新生成。`CLAUDE.md` 只保留指向 `AGENTS.md` 的指针。

同一方向也体现在检查范围上：[Guides 检查器](../../tools/guides/check.mjs)只扫描 `docs/`、规划/交付 Skill 的正文与模板等维护内容，`openwiki/` 生成页不在内；[测试指南](../engineering/testing.md)明确“生成产物、业务源 YAML、历史证据和第三方材料不重写为前馈”。

### 演进触发条件

- 当前不设单一来源清单文件：来源映射分散在权威表、计划 `sourceManifest`、上游依据与 OpenWiki `sources` 中；外部来源增多时再补一份 SOURCE.md 式的显式清单并接入定时核对。
- OpenWiki 当前只运行 code 模式，输入是仓库本身；需要引入 Gmail、Slack、Notion 等外部连接器时，在工作流中追加对应密钥。
- 非仓库知识源（如 smart-domain 上游文档、业务原始材料）仍靠固定 commit 加人工核对；变化频繁时再建立定时同步。
- 首次生成以 `interrupted` 结束（工作流文件在运行中变化），source checkpoint 未推进；下一次 `openwiki code --update` 会协调该差异，之后随每次 PR 合并向前。
