# 需求模糊：Agent 不知道“好”长什么样

## Bad Smell

需求模糊指的是把需要大量上下文的系统意图压缩成一句话交给 Agent 执行。在这个把业务事实、实施依据和验证结果都放进仓库的 Harness 里，它同时出现在三个层次上：业务事实在 `.evidence/fm/`，软件职责在 `docs/requirements/`，实施结果在机器计划的 `tasks[taskKey]`。只写一句“做一个专栏订阅系统”，Agent 会补齐一整套它自己理解的合同、支付与访问。约束、验收数据与边界情况不落进仓库文件，Agent 只能靠猜。

诊断信号有三个，严重程度依次上升：Agent 反问“这里我应该怎么做”；交付“看起来对、用起来不对”；验收时反复出现“我不是这个意思”。第三个信号往往伴随优先级丧失：口头修正对 Agent 的权重相同，它分不清核心约束、锦上添花与随口一说。

## Solution

消除这个坏味道的手法叫提取指令文件。这个仓库用三层文件把“猜”降下来：入口指令写约束，需求文件与任务 CHECK 写验收数据，范围与质量属性单独列出边界情况。

### 约束条件：入口文件与来源权威表

`AGENTS.md` 是仓库唯一的 Agent 入口，用 39 行把不可协商的约束、流程与完成底线写在一起：**不变量**声明技术栈、事实源、授权边界、领域行为归属与测试要求；“流程与状态”定下显式建模入口、Skill 分工和“每次只执行一个获授权且就绪的任务”；“验证底线”要求只有质量命令实际通过才能声称完成。

入口不装细节，具体读什么按 [Guides 导航](../guides/index.md)的两张表下发：“来源与冲突处理”为每类问题指定唯一权威位置，“阅读路由”按任务类型列出必要前馈。约束因此既具体，又不用 Agent 自己判断优先级。

### 验收数据：从故事验收落到任务 CHECK

验收数据分三层落。需求级的[故事与验收](../requirements/stories.md)用稳定 ID、Given/When/Then、具体输入、可观察结果与失败不变性写成可执行的样子，例如 AC-005-03 规定“父协议不存在返回 404、相同 `request_id` 已存在返回 409、`evidenceRefs` 为空返回 400”。任务级把预期固定成命令、输入与断言：[机器计划模板](../../.agents/skills/evidence-task-planning/assets/plan-template.yaml)要求每个 CHECK 带上真实依赖、固定输入、正常与边界输入、失败不变性和精确命令，`acceptanceCriteria` 再把逐例期望值保存为受限操作符与保留类型的 `expected`；`CHECK-CRM-DOM-004` 就把达标、不足、恰在周期闭合时刻等六组输入连同各自结果固定下来。项目级由[测试指南](../engineering/testing.md)兜底：每条质量命令写明“实际覆盖”和“不证明什么”，不允许用构建成功冒充业务验收。

命令未知时填 `null` 并关联 gap，不写“运行相关测试”充当可执行；执行后的真实结果写入 `tasks[taskKey].observedEvidence`，不停留在口头声称。

### 边界情况：集中单列，不混入主流程

正常流程之外的判断集中在一处：[Guides 导航](../guides/index.md)的“缺口与转向”写明只读、获授权实施、源业务未知、任务局部设计不足、环境不可用、代码问题六类情形各自的终止与交回规则；[质量属性](../requirements/quality-attributes.md)用“需要依据的专题”表把未知显式化，并拒绝为没有依据的指标填默认值；[软件范围](../requirements/scope.md)单列“MVP 与非目标”“未决范围”，避免把 FM/API 中存在的活动自动当成开发范围。

边界情况写成字段后能被机器核对：`plan_state.py verify` 要求 `blocked` 的任务必须关联已知 gap，空命令必须关联 gap。缺口只阻塞受影响任务，不通过扩范围或改上游制造通过。

### 用澄清代替猜测

约束与验收都写不出的部分交回澄清，而不是让 Agent 猜。`AGENTS.md` 规定问答工具每次只问一个业务问题，先保存回答与来源，再当轮沉淀明确术语，任一保存失败就停止；[建模指南](../evidence-modeling.md)区分访谈与术语沉淀、模型 JSON 编辑、只读验证，词汇表写入不扩大模型编辑权限，编辑授权不等于业务审核。发现记录保存用户原话、问题状态、解决依据与下游影响：一条记录先写“FM 实例已有固定标识，但原计划未获授权把它们作为 local/test 系统固定夹具”，用户确认后置为已解决，而生产身份、生产数据库与真实支付接入保持未决。问题解决了，未决范围留在原地。

### 开工检查

进入 Action 前按 [Guides 导航](../guides/index.md)的“任务开工检查”核对授权、来源、前置与新鲜度、设计、做法与环境、验证与退出六件事，最后一项直接问：每条验收条件是否引用本任务 CHECK，并包含可比较的具体期望数据与适用反例？检查通过只表示本次行动依据就绪，不表示实现或业务获批；结构通过只说明计划自洽，语义是否就绪仍要人工判断。
