# 需求模糊：Agent 不知道“好”长什么样

## Bad Smell

需求模糊指的是把需要大量上下文的系统意图压缩成一句话交给 Agent 执行。本项目把它放大到三个层次：业务事实在 `.evidence/fm/`，软件职责在 `docs/requirements/`，实施结果在机器计划的 `tasks[taskKey]`。比如只写一句“做一个专栏订阅系统”，Agent 会补齐一整套它自己理解的合同、支付与访问；只写“实现移动支付”，它也会自行决定金额、期限和失败语义。约束、验收数据与边界情况不落进仓库文件，Agent 只能靠猜。

诊断信号有三个，严重程度依次上升：Agent 反问“这里我应该怎么做”；交付“看起来对、用起来不对”；验收时反复出现“我不是这个意思”。第三个信号往往伴随优先级丧失，口头修正对 Agent 的权重相同，它分不清核心约束、锦上添花与随口一说。

## Solution

项目用三层文件把“猜”降下来：入口指令写约束，需求文件与任务 CHECK 写验收数据，范围与质量属性单独列出边界情况。落点顺序是先列约束，再列验收，最后从约束里拆出边界情况。

### 约束条件：入口文件与来源权威表

`AGENTS.md`（39 行）是仓库唯一的 Agent 入口，把不可协商的约束、流程与完成底线写在一起：

| 要素       | 本项目对应                                                                                       | 位置                         |
| ---------- | ------------------------------------------------------------------------------------------------ | ---------------------------- |
| 约束条件   | “不变量”：技术栈、事实源、授权边界、领域行为归属、测试要求                                       | [AGENTS.md](../../AGENTS.md) |
| 流程与状态 | 显式建模入口、Skill 分工、外层 PDCA 加内层 Guides → Action → Sensors → Steer、每次只执行一个任务 | 同上                         |
| 完成底线   | 仓库根质量命令与“只有实际通过才能声称完成”                                                       | 同上“验证底线”               |

入口不装细节：具体读什么按 [Guides 导航](../guides/index.md)的两张表下发。“来源与冲突处理”为每类问题指定唯一权威位置与不可替代它的内容，“阅读路由”按任务类型列出必要前馈。约束既具体，又不在一个文件里堆成需要 Agent 自己判断优先级的清单。

本次授权切片的范围同样被写成明确约束：[软件范围](../requirements/scope.md)写明当前切片是绩效协议主链——登记绩效协议、提出带周期与三项目标（联系总数、电话数、邮件数）的月度请求、登记客户联系记录、按规则判断月度目标是否完成；并逐条声明非目标：前端页面、生产身份与权限、生产数据库、协议参与方核验与 403、未达标后果、周度进度检查、客户档案生命周期。

### 验收数据：从故事验收落到任务 CHECK

| 层次   | 落点                                                                                  | 机制                                                                                                                   |
| ------ | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 需求级 | [故事与验收](../requirements/stories.md)                                              | US/AC 使用稳定 ID、Given/When/Then、具体输入、可观察结果与失败不变性；未决项在故事内单列                               |
| 任务级 | [机器计划模板](../../.agents/skills/evidence-task-planning/assets/plan-template.yaml) | `checks` 固定测试边界和命令；`acceptanceCriteria` 引用 CHECK，并以 `path/operator/expected` 保存具体、有类型的预期数据 |
| 项目级 | [测试指南](../engineering/testing.md)                                                 | 每个质量命令写明“实际覆盖”和“不证明什么”，不允许用构建成功冒充业务验收                                                 |

故事已经写成可执行的样子：AC-004-02 规定“缺少 `agreement_id` 或 `signed_at` 时按 API 契约拒绝（422）且不写入”，AC-005-03 规定“父协议不存在返回 404、相同 `request_id` 已存在返回 409、`evidenceRefs` 为空返回 400”，AC-006-05 规定“`confirmed_at` 恰为 `expired_at` 或位于请求区间之外时，记录仍可形成，是否计入由完成规则判断”。任务 CHECK 再把预期固定成命令、输入与断言，例如 `CHECK-CRM-DOM-004` 列出达标、不足、恰在周期闭合时刻、区间外、跨周期与总数达标但单项不足六组输入，并给出逐例期望值。

CHECK 的最低证据有统一要求：目的、真实依赖/Fake、固定输入与业务时间、正常/边界/反例、失败不变性、精确命令和 cwd；`acceptanceCriteria` 再把结果拆成稳定路径、受限操作符和保留类型的 `expected`。命令未知时填 `null` 并关联 gap，不写“运行相关测试”充当可执行。执行后的真实结果写入 `tasks[taskKey].observedEvidence`，而不是停留在口头声称。

### 边界情况：集中单列，不混入主流程

- 正常流程之外的判断集中在 [Guides 导航](../guides/index.md)的“缺口与转向”：只读、获授权实施、源业务未知、任务局部设计不足、环境不可用、代码问题六类，每类给出终止与交回规则。
- [交付生命周期](../../.agents/skills/evidence-delivery/references/lifecycle.md)把“观察 → 内层动作 → 外层动作”写成转向矩阵，覆盖编译失败、CHECK 不证明预期、单元重复、来源改变、缺事实、前馈不足、环境不可用、全部通过八种情形。
- [质量属性](../requirements/quality-attributes.md)用“需要依据的专题”表把未知显式化（QA-IDENTITY、QA-I18N、QA-AUDIT、QA-DATABASE、QA-INTEGRATION、QA-SLO），并写明“没有依据的性能、留存、权限或部署指标不填常见默认值”。
- [软件范围](../requirements/scope.md)单列“MVP 与非目标”“未决范围”，避免把 FM/API 中存在的活动自动当成开发范围；计划把范围外单元逐项记为 `not-applicable` 并附理由。

边界情况一旦被写成字段，就能被机器核对：`plan_state.py verify` 要求 `blocked` 的任务必须关联已知 gap，空命令必须关联 gap。缺口只阻塞受影响任务，不通过扩范围或改上游制造通过。

### 用澄清代替猜测

- `AGENTS.md` 规定问答工具每次只问一个业务问题，保存回答或控制状态后再继续，避免一次抛出过多问题导致优先级丧失。
- [发现记录](../../.evidence/discovery.md)保存用户原话、问题状态、解决依据与下游影响：一条记录先写“FM 实例已有固定标识，但原计划未获授权把它们作为 local/test 系统固定夹具”，用户确认后置为已解决，并同时写明仍未决定生产身份、生产数据库与真实支付接入。问题解决了，未决范围留在原地。
- [建模指南](../evidence-modeling.md)区分讨论、编辑、只读验证三种模式；编辑授权不等于业务审核。模型文件不保存审核状态，确认依据随发现记录与计划、任务记录维护。
- [Guides 导航](../guides/index.md)规定“源业务未知：交回发现/FM/API/需求拥有者，不在代码中猜测”。

### 开工检查

[Guides 导航](../guides/index.md)的“任务开工检查”要求进入 Action 前逐项核对六件事：授权与目标、来源、前置与新鲜度、设计、做法与环境、验证与退出。最后一项直接问：每条验收条件是否引用本任务 CHECK，并包含可比较的具体期望数据与适用反例？失败后应局部修复、重规划还是澄清？

检查通过只表示本次行动依据就绪，不表示实现或业务获批；结构通过只说明计划自洽，语义是否就绪仍要人工判断。
