# 需求模糊：Agent 不知道“好”长什么样

## Bad Smell

需求模糊指的是把需要大量上下文的系统意图压缩成一句目标就交给 Agent 执行。它在本项目的典型症状有三类：Agent 反问“这里我应该怎么做”；交付“看起来对、用起来不对”，因为它用通用常识填补了未说明的约束；验收时反复出现“我不是这个意思”，优先级在一次又一次的口头修正中丧失。当前状态更容易放大这个问题：FM 仍是 `draft`、业务审核为 `pending`，软件范围（SCOPE-MVP）尚未收敛——如果不把约束、完成条件和边界情况写进仓库文件，Agent 只能靠猜。

## Solution

项目用分层指令与可验证检查把“猜”降下来。

### 入口指令文件：AGENTS.md

`AGENTS.md`（26 行）是仓库唯一的 Agent 入口，把约束、流程与完成底线写在一起：

| 要素       | 本项目对应                                                                                       | 位置                         |
| ---------- | ------------------------------------------------------------------------------------------------ | ---------------------------- |
| 约束条件   | “不变量”：技术栈、事实源、授权边界、领域行为归属、测试要求                                       | [AGENTS.md](../../AGENTS.md) |
| 流程与状态 | 显式建模入口、Skill 分工、外层 PDCA + 内层 Guides → Action → Sensors → Steer、每次只执行一个任务 | 同上                         |
| 完成底线   | 仓库根质量命令与“只有实际通过才能声称完成”                                                       | 同上“验证底线”               |

它同时明确：“不要一次加载整个仓库，也不要依赖聊天记忆”“生成产物不是新的事实源”。

### 完成条件：三个层次都可验证

| 层次   | 落点                                                                                 | 机制                                                                                                                          |
| ------ | ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| 项目级 | [测试指南](../engineering/testing.md)                                                | 每个质量命令写明“实际覆盖”和“不证明什么”，不允许用构建成功冒充业务验收                                                        |
| 任务级 | [任务模板](../../.agents/skills/evidence-task-planning/assets/task-plan-template.md) | `checks` + `completionCriteria`。模板注释直接规定“工序退出条件逐项对应具体 CHECK；不以通用工序、文档存在或自评替代本任务验收” |
| 需求级 | [故事与验收入口](../requirements/stories.md)                                         | 要求稳定 ID、Given/When/Then、具体输入、可观察结果、边界与失败不变性；SCOPE-MVP 未定就不生成已批准的 US/AC                    |

CHECK 的最低证据也有统一要求：目的、真实依赖/Fake、固定输入与业务时间、正常/边界/反例、精确命令、cwd、完成条件；命令未知时填 `null` 并关联 gap，不写“运行相关测试”充当可执行。

### 边界情况：集中单列，不混入主流程

- 正常流程之外的判断集中在 [Guides 导航](../guides/index.md)的“缺口与转向”：只读、获授权实施、源业务未知、任务局部设计不足、环境不可用、代码问题六类，每类给出终止与交回规则。
- [交付生命周期](../../.agents/skills/evidence-delivery/references/lifecycle.md)把“观察 → 内层动作 → 外层动作”写成转向矩阵，覆盖编译失败、CHECK 不证明预期、单元重复、来源改变、缺事实、前馈不足、环境不可用、全部通过八种情形。
- [质量属性](../requirements/quality-attributes.md)用“未决专题”表把未知显式化（QA-IDENTITY、QA-DATABASE、QA-INTEGRATION 等），并写明“没有依据的性能、留存、权限或部署指标不填常见默认值”。
- [软件范围](../requirements/scope.md)单列“MVP 与非目标”“未决范围”，避免把 FM/API 中存在的活动自动当成开发范围。

### 用澄清代替猜测

- `AGENTS.md` 规定问答工具**每次只问一个业务问题**，保存回答或控制状态后再继续——避免一次抛出过多问题导致优先级丧失。
- [建模指南](../evidence-modeling.md)区分讨论、编辑、只读验证三种模式；编辑授权不等于业务审核。
- `Guides` 明确规定“源业务未知：交回发现/FM/API/需求拥有者，不在代码中猜测”。
- 当前 FM 标记为 `draft`、`stakeholderReview.status: pending`，任何下游工作都不得自行提升审核状态。

### 开工检查

[Guides 导航](../guides/index.md)的“任务开工检查”要求进入 Action 前逐项核对六件事：授权与目标、来源、前置与新鲜度、设计、做法与环境、验证与退出。最后一项直接问：**每个完成条件是否有 CHECK？包含可观察预期及适用反例？失败后应局部修复、重规划还是澄清？**
