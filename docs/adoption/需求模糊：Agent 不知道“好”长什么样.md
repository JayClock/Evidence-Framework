# 需求模糊：Agent 不知道“好”长什么样

## Bad Smell

需求模糊指的是把需要大量上下文的系统意图压缩成一句话交给 Agent 执行。本项目把它放大到三个层次：业务事实在 `.evidence/fm/`，软件职责在 `docs/requirements/`，实施结果在机器计划的 `tasks[taskKey]`。只写一句“做一个专栏订阅系统”，Agent 会补齐一整套它自己理解的合同、支付与访问；只写“实现移动支付”，它也会自行决定金额、期限和失败语义。约束、完成条件与边界情况不落进仓库文件，Agent 只能靠猜。

诊断信号有三个，严重程度依次上升：Agent 反问“这里我应该怎么做”；交付“看起来对、用起来不对”；验收时反复出现“我不是这个意思”。第三个信号往往伴随优先级丧失，口头修正对 Agent 的权重相同，它分不清核心约束、锦上添花与随口一说。

## Solution

项目用三层文件把“猜”降下来：入口指令写约束，需求文件与任务检查写完成条件，范围与质量属性单独列出边界情况。落点顺序是先列约束，再列验收，最后从约束里拆出边界情况。

### 约束条件：入口文件与来源权威表

`AGENTS.md`（39 行）是仓库唯一的 Agent 入口，把不可协商的约束、流程与完成底线写在一起：

| 要素       | 本项目对应                                                                                       | 位置                         |
| ---------- | ------------------------------------------------------------------------------------------------ | ---------------------------- |
| 约束条件   | “不变量”：技术栈、事实源、授权边界、领域行为归属、测试要求                                       | [AGENTS.md](../../AGENTS.md) |
| 流程与状态 | 显式建模入口、Skill 分工、外层 PDCA 加内层 Guides → Action → Sensors → Steer、每次只执行一个任务 | 同上                         |
| 完成底线   | 仓库根质量命令与“只有实际通过才能声称完成”                                                       | 同上“验证底线”               |

入口不装细节：具体读什么按 [Guides 导航](../guides/index.md)的两张表下发。“来源与冲突处理”为每类问题指定唯一权威位置与不可替代它的内容，“阅读路由”按任务类型列出必要前馈。约束既具体，又不在一个文件里堆成需要 Agent 自己判断优先级的清单。

本次授权切片的范围同样被写成明确约束：[软件范围](../requirements/scope.md)写明“登记包含全部 11 个必填字段的订阅合同、登记成功后自动派生付款要求、调用 local/test 支付端口、按规则判断完成并读取状态”，并声明非目标：生产身份系统、外部支付协议、多语言、审计留存、生产数据库选型不由本次前馈重构新增。

### 完成条件：从故事验收落到任务 CHECK

| 层次   | 落点                                                                                  | 机制                                                                                                                                                                      |
| ------ | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 需求级 | [故事与验收](../requirements/stories.md)                                              | US/AC 使用稳定 ID、Given/When/Then、具体输入、可观察结果与失败不变性；未决项在故事内单列                                                                                  |
| 任务级 | [机器计划模板](../../.agents/skills/evidence-task-planning/assets/plan-template.yaml) | `checks` 逐项写明目的、被测行为、真实依赖/Fake、固定输入与业务时间、正常/边界/反例、精确命令与证据要求；`completionCriteria` 禁止以通用工序、文件存在或自评替代本任务验收 |
| 项目级 | [测试指南](../engineering/testing.md)                                                 | 每个质量命令写明“实际覆盖”和“不证明什么”，不允许用构建成功冒充业务验收                                                                                                    |

故事已经写成可执行的样子：AC-001-02 规定“缺少任一必填字段时拒绝且不写入”，AC-002-04 规定“合格扣款恰在 `expired_at` 完成仍算完成”，AC-003-02 规定“付款要求尚未形成时读取返回 404”。任务的 CHECK 则把这些预期固定成命令、断言与证据要求，例如 `CHECK-DOM-PAY-001` 直接写出 `signedAt=2026-10-01T09:00:00Z`、900 秒、空证明与截止时证明两组输入。

CHECK 的最低证据有统一要求：目的、真实依赖/Fake、固定输入与业务时间、正常/边界/反例、失败不变性、精确命令、cwd、完成条件；命令未知时填 `null` 并关联 gap，不写“运行相关测试”充当可执行。执行后的真实结果写入 `tasks[taskKey].observedEvidence`，而不是停留在口头声称。

### 边界情况：集中单列，不混入主流程

- 正常流程之外的判断集中在 [Guides 导航](../guides/index.md)的“缺口与转向”：只读、获授权实施、源业务未知、任务局部设计不足、环境不可用、代码问题六类，每类给出终止与交回规则。
- [交付生命周期](../../.agents/skills/evidence-delivery/references/lifecycle.md)把“观察 → 内层动作 → 外层动作”写成转向矩阵，覆盖编译失败、CHECK 不证明预期、单元重复、来源改变、缺事实、前馈不足、环境不可用、全部通过八种情形。
- [质量属性](../requirements/quality-attributes.md)用“需要依据的专题”表把未知显式化（QA-IDENTITY、QA-I18N、QA-AUDIT、QA-DATABASE、QA-INTEGRATION、QA-SLO），并写明“没有依据的性能、留存、权限或部署指标不填常见默认值”。
- [软件范围](../requirements/scope.md)单列“MVP 与非目标”“未决范围”，避免把 FM/API 中存在的活动自动当成开发范围；计划把范围外单元逐项记为 `not-applicable` 并附理由。

边界情况一旦被写成字段，就能被机器核对：`plan_state.py verify` 要求 `blocked` 的任务必须关联已知 gap，空命令必须关联 gap。缺口只阻塞受影响任务，不通过扩范围或改上游制造通过。

### 用澄清代替猜测

- `AGENTS.md` 规定问答工具每次只问一个业务问题，保存回答或控制状态后再继续，避免一次抛出过多问题导致优先级丧失。
- [发现记录](../../.evidence/discovery.md)保存用户原话、问题状态、解决依据与下游影响。`Q-MOBILE-FIXED-VALUES-001` 先记录“FM 实例已有固定标识，但原计划未获授权把它们作为 local/test 系统固定夹具”，经用户确认后置为已解决，并明确“未决定生产身份、生产数据库和真实支付接入”。
- [建模指南](../evidence-modeling.md)区分讨论、编辑、只读验证三种模式；编辑授权不等于业务审核。模型文件不保存审核状态，确认依据随发现记录与计划、任务记录维护。
- [Guides 导航](../guides/index.md)规定“源业务未知：交回发现/FM/API/需求拥有者，不在代码中猜测”。

### 开工检查

[Guides 导航](../guides/index.md)的“任务开工检查”要求进入 Action 前逐项核对六件事：授权与目标、来源、前置与新鲜度、设计、做法与环境、验证与退出。最后一项直接问：每个完成条件是否有 CHECK？包含可观察预期及适用反例？失败后应局部修复、重规划还是澄清？

检查通过只表示本次行动依据就绪，不表示实现或业务获批；结构通过只说明计划自洽，语义是否就绪仍要人工判断。
