# 需求模糊：Agent 不知道“好”长什么样

## Bad Smell

“做一个订阅系统”听起来是一个任务，实际留给实现者的空白太多了。订阅从什么时候生效？付款请求发出就算付款完成吗？失败后原记录还在不在？Agent 如果没看到依据，很可能套用熟悉的支付流程，把未定的业务关系补全。页面和接口都能跑，验收时才发现交付的是另一套系统。

在 Evidence 里，这类问题常发生在几个不同层次。业务活动记在 `.evidence/fm/`，本次软件负责哪些活动看[范围](../requirements/scope.md)，接口能力以 `.evidence/api/api.json` 为准。FM 有某项活动，不代表本次一定要开发它；接口设计里有一个能力，也不代表已经做出实现。把这几层混成一句“照模型做”，Agent 很难知道哪些是事实，哪些是工作范围，哪些仍在等待决定。

## Solution

### 从一句要求走到可检查的结果

[故事与验收](../requirements/stories.md)把用户想看到的行为写成有稳定 ID 的条件：给定什么输入、采取什么动作、应观察到什么结果，以及失败后什么不能改变。任务计划再把它接到具体 CHECK。比如一项领域行为的检查，不该只写“月度联系目标完成”，还要给出周期、匹配记录、总数、电话数和邮件数的输入，并分别检查达标、不足和周期边界。单项不足却被总数掩盖，也得有反例。测试因此有了可以比较的数据，而不只是“跑绿了”。

`plan.yaml` 里的 `acceptanceCriteria` 引用本任务的 CHECK，用稳定路径、操作符和有类型的 `expected` 表达结果。命令还没确定，就填 `null` 并关联缺口，不能填“运行相关测试”占位。等实际执行时，`observedEvidence` 才记录命令、退出码与观察。计划写得再完整，也不能冒充已经验证。

### 把不能决定的部分留下来

需求澄清不等于替业务方做选择。可信身份、代表权限、生产数据库或真实支付接入若没有依据，[质量属性](../requirements/quality-attributes.md)会把它们列为待确认专题。为 local/test 场景准备固定标识，也不能顺势推导出生产标识的生成规则。未知项应说明影响哪条验收，只拦住依赖它的任务；纯领域行为若已有确定规则，仍可独立设计和测试。

还有一种模糊发生在词的使用上。业务方说“已受理”，实现者却把它读成“已到账”；两边都觉得自己听懂了，直到状态变更后的数据对不上。碰到这种词，先找 FM 里的概念与对应场景。如果它尚未建模，访谈时记录业务方的定义和使用位置，不靠代码里的英文名倒推中文含义。术语确定后也不能跳过验收条件：同一个词在登记、查询和通知三个动作里，读者看到的结果可能不同。

边界情况还应分清是已知规则还是待决定的策略。比如父协议不存在时返回什么、重复请求怎么处理，已有故事验收可据此写 CHECK；谁可以代表别人操作，如果材料只说明参与者、没有身份验证办法，就不能把角色名字解释成登录权限。前一种情况拿反例测试，后一种情况留缺口。这种区分让 Agent 既不会漏掉已经明确的失败路径，也不会把未知方案伪装成“按常识处理”。

业务问题先回到发现记录，保存回答原话和来源；术语按规定当轮沉淀到词汇表。访谈中的回答不会自动授权修改 FM、API 或开始实施。之后由各自的拥有者更新模型、范围或契约，再重算受影响计划。这个顺序看起来慢一些，但比做完才听到“我不是这个意思”省事。

开工时可以用一个简单的问题检查需求是否够用：对于当前任务，能否指出一条正常输入、一条失败或边界输入、各自可观察的结果，以及本次明确不做的事？答案必须来自当前来源和 CHECK。只会说“系统应该支持订阅”，还不够实施。只有链接和字段都填齐，也还要判断这些条件是否忠于业务原意。
