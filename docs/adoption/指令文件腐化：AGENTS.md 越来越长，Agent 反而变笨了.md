# 指令文件腐化：AGENTS.md 越来越长，Agent 反而变笨了

## Bad Smell

一次交付违反了约定，往 `AGENTS.md` 加一句；下次又遇到边界情况，再加一段“除非”。起初每条补充都合理，过几个月却没人知道同一规则在入口、Skill、任务模板里哪个版本生效。Agent 读过所有内容，照样可能选错。问题不在于它漏读了某一句，而在于这些句子已经互相争夺解释权。

Evidence 的入口文件目前承担的事很有限：指向 [Guides 导航](../guides/index.md)，声明技术和授权边界，说明任务状态、交付纪律与验证底线。具体实现细节另有负责人。这里不靠固定行数衡量好坏，入口小是因为它只负责长期有效、每次都必须读的内容。

## Solution

### 新规则先找拥有者

写下一条约定前，先看它属于哪一层。业务定义属于 FM，HTTP 能力属于 `api.json`，本次软件范围属于需求文档，模块取舍在架构文档；实施时某个任务的行为拥有者、文件范围和 CHECK 放在任务 Guides。工程做法则由 `docs/engineering/` 与相关 howto 维护。`AGENTS.md` 告诉执行者去哪里找，不再复写这些文件的正文。

比如“Context 实现在适配层提供”是跨任务的不变量，可以留在宪法；某个任务的 Context 依赖哪一个公开契约，则该写进任务 `design`。把后者也抄到入口，既会给未来任务造成错误暗示，源契约变化后也多出一份需要同步的旧答案。`CLAUDE.md` 只指向入口，不另建一份项目宪法。

### 替换旧说法，不追加兼容说明

发现一条规则写错了，先确定权威位置，再修改它和所有指向它的路由。正文直接写当前约定，Git 历史保存旧版本；“以前如此，现在例外”留在现行指南里，读者仍可能按旧半句行动。若变化影响 Skill、模板或检查，也一起核对。这不意味着删除业务原话和历史执行证据，它们保存的是发生过什么，不能当作过时的操作指南清掉。

[Guides 检查器](../../tools/guides/check.mjs)给维护提供了有限反馈：`npm run guides:verify` 运行回归、本地链接与格式检查，也拒绝一些已知过期表述。链接能打开不代表两份文档没有语义矛盾；检查器不会替人裁决 FM 和代码之间的冲突。尤其遇到“代码已经这样写了”时，应先区分当前行为与应当实现的契约，而不是把代码现状搬进宪法。

有时规则看似重复，其实负责的环节不同。宪法写“不自动批准业务结论”，访谈方法再说明回答怎样保存、何时停止，这不必机械去重；前者管权限，后者管操作。需要清理的是同一个事实被多处独立改写，比如计划模板、导航和某篇 howto 各留一版“任务何时算完成”，改了一处却没动另外两处。比较时应看能否指出唯一维护者，其他位置是否只提供路由和必要的局部差异。

碰到冲突，先暂停受影响的动作，找到对应层的负责文件。若是范围变更，要走需求收敛；若是当前 CHECK 定义不足，改任务的检查设计；若是架构基线要换，必须有明确授权并记录决定。不能因为入口级别高，就把用户新说的业务事实硬塞进宪法，也不能因为任务文件离实现近，就允许它推翻正式接口契约。清理文件时把这些关系留成链接，比重排整套“优先级顺序”更可靠。

生成物也有自己的维护方式。OpenWiki 可以帮助定位资料，但页面由工作流生成，手改生成页只会等下次刷新再次分叉。项目约束或源码变了，应改真正的来源并重新生成。受管块和历史页面不该被拿来当另一套手写规则。

治理指令文件时，最有效的一次修改常常是删掉重复解释，并补上原位置的链接和检查。新增规范还要回答由什么测试或人工评估发现违反它；若答不上来，仅仅多写一句“必须遵守”，下次评审仍得靠人碰运气。
