# 状态污染：状态存在但不可信

## Bad Smell

任务记录还在，检查结果也有，下一轮 Agent 却沿着错误的结论继续工作。执行者把自己的判断写成已验证事实，审查时又用同一段对话里的解释说服自己，最后把任务标成完成。后来的会话只能看见留下的状态，很难分辨它来自原始证据，还是来自上一轮尚未核实的推断。

[跨会话状态丢失](<跨会话状态丢失：每次对话 Agent 都不记得上次的事.md>)讨论信息该存在哪里。状态污染更难察觉：文件没有丢，内容也像一份完整记录，但临时结论已经混进正式依据。多保存几份摘要解决不了这个问题，反而可能让同一个未经核实的说法出现在计划、审核页和交接报告里，看起来像有多处佐证。

## Solution

### 执行和审查不沿用同一段对话

Evidence 的[独立交付入口](../../.pi/extensions/evidence-delivery/README.md)把执行与审查分成两个新会话。主 Agent 核对授权与来源后派发 worker，worker 只做当前任务并交回候选产物。随后另启 reviewer，从任务来源、实际文件和原始日志检查交付，不续接执行者的会话，也不要求它复述推理过程。

主 Agent 通过 `evidence_worker` 传入精确的 `taskKey`，在 `assignment` 中说明本轮授权、目标与非目标，用 `sourceRefs` 指向原始来源文件，并把可改动范围逐个列入 `allowedFiles`，不传整段聊天代替来源。拿到交接后，再把返回的运行目录作为 `workerRun` 交给 `evidence_review`。这两个[工具入口](../../.pi/extensions/evidence-delivery/index.ts)让审查对应同一次交付，而不是让另一个 Agent 泛泛地看一遍仓库。

[调度源码](../../.pi/extensions/evidence-delivery/runner.ts)每次启动新的 Pi 子进程，使用 `--no-session`，不传父会话历史，同时关闭自动发现的扩展、Skills 和提示模板。必要方法通过文件引用重新读取，项目 AGENTS 仍然生效。这样审查者拿到的是可重新核对的材料，不必先接受执行者对这些材料的解释。会话隔离减少了沿用旧判断的机会，但不会让一个模型自动变成可靠裁判。

读写工具权限直接来自 [worker](../../.pi/agents/evidence-worker.md) 与 [reviewer](../../.pi/agents/evidence-reviewer.md) 的 subagent 定义。调度器读取 frontmatter 的 `tools`，没有另外维护一份权限表。执行者有 shell 和文件编辑工具，审查者只有读取与搜索工具，不能边审边修，也不能声称自己重跑过命令。需要复验时，它把具体命令与目的交回主 Agent 安排。

### 交接先留在临时目录

一次运行会留下任务包、基线摘要、原始事件、错误输出和结果文件，目录由工具明确返回。这些材料能帮助主 Agent 分辨原有工作树改动与本轮增量，也能追查一个完成声明是怎样产生的。它们只是本轮执行材料，不是新的业务事实源，更不承担长期进度。

调度器不会只看子进程是否正常退出。模型报错、中止、没有最终回答、事件损坏或越界改动，都可能使交接失败，日志仍保留。即便成功返回，工具也只承认收到了待核验交接，不会替任务写入完成状态。worker 报告里写的退出码还要与原始命令输出对照，不能用模型自己填写的数字证明命令确实跑过。

审查还要对应同一份产物。worker 交付后，调度器会在启动 reviewer 前重新比较工作树，变化了就拒绝旧交付。快照覆盖 Git 索引中的文件及非忽略的未跟踪文件，比较内容与文件模式，不证明忽略的构建目录、Git 元数据或外部文件没有变化。主 Agent 归档前仍需核对受审文件、来源和 CHECK 环境，不能把一次新鲜度检查当成此后一直有效的保证。

### 核验后再由主 Agent 归位

[生命周期协议](../../.agents/skills/evidence-delivery/references/lifecycle.md)把持久记录的写入留给主 Agent。worker 交接实际产物与检查，reviewer 独立给出规范和需求两个维度的审查意见，主 Agent 对照来源、日志与当前文件后，才按授权归位。业务任务的真实观察进入 `observedEvidence`，唯一状态仍在 `tasks[taskKey].status`，审核页只是投影。用户原话、执行发现和局部决定各有归属，不把整段交接复制成一份万能记忆。

比如交接里同时出现检查失败、对失败原因的猜测和用户的临时取舍，主 Agent 不能把三者合成一条结论。检查失败要对照本轮命令与日志，记录实际覆盖和影响范围；原因尚未核实，就保留为待查问题。用户取舍则保留原话来源、作出者和适用场景，确认授权后再决定归属，不能把仅适用于本地测试的例外推广成项目规则。若新旧说法冲突，保留各自来源并交有权者确认，工具返回成功不会消除这些未决事项，更不能据此把任务改成 `done`。

历史记录能说明这种区分为什么有用。[2026 年 9 月 25 日的独立交付检查记录](../../.evidence/checks/harness/independent-delivery.json)保存了真实 worker 与 reviewer 的验证链，同时明确总门禁未通过：当时 `npm test` 被既有未跟踪 write Skill 的目录断言阻塞，部分 Nx 检查命中缓存。机制得到核对，并没有被写成所有质量检查通过。这是该日期的历史观察，不是本文这一轮的检查结果，也不代表完整真实 Agent 行为评测已经完成。

临时路径可能被操作系统清理。主 Agent 归档前需要按授权保留必要、脱敏的原始证据，留下摘要和稳定指针，不能只存一个以后打不开的临时目录。没有保存或整合失败的内容要明确交接未保存，下次会话不能把聊天里的承诺当成文件证据。

这些安排仍有边界。worker 的 shell 保留调用者的操作系统权限，共享工作树不是文件系统沙箱，允许文件清单与事后差异检查也不能阻止写入发生。唯一归档依赖角色协议，发现异常只能报告并保留证据，不能自动回滚用户材料。当前机制让污染更容易被发现和追查，并不保证污染已经完全消除。
