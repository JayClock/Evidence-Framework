# 状态污染：状态存在但不可信

## Bad Smell

一次检查的结果存下来了，下个会话却把它当成长期成立的结论。比如把 Gradle 返回的 `UP-TO-DATE` 简写成“测试通过”，接手的 Agent 就无法分辨那次是实际执行还是复用了旧结果。

Evidence 的任务记录同时包含局部设计、执行结果和进度，访谈还会带来用户偏好与业务回答。如果把这些内容都压成一份会话总结，一次任务里的取舍就可能变成全项目约定，执行者的推测也可能被后续会话当成正式事实。

## Solution

### 执行记录按用途保存

[交付协议](../../.agents/skills/evidence-delivery/references/lifecycle.md#5-知识交接与归位)把收尾时需要保留的内容分为用户意见、执行发现和决定。用户意见保留原意与适用场景，执行发现带上证据位置和影响范围，决定则注明由谁作出、依据什么授权。记录时就区分这些内容，恢复时才能判断它们各自能支持什么行动。

本任务的设计写入 `guides` 或 `design`，检查结果写入 `observedEvidence`，阻塞事项进入 `gaps` 并关联受影响任务。状态统一放在 `tasks[taskKey].status`，`review.html` 从计划重建。

[测试指南](../engineering/testing.md#check-的最低证据)要求执行结果保留命令、工作目录、退出码、环境和输出定位，缓存命中也一并记录。获授权的检查目录保存紧凑运行清单，包含输入摘要、日志校验和与指针，完整日志按指针查回。下一次恢复可以核对当时的输入和环境，不必从一句“已验证”猜发生了什么。

### 跨任务结论先交接，再归位

内层任务可以保存有权限写入的局部信息。需要跨任务复用，或者会改变 FM、API、需求和工程约定的内容，则向外层交接来源、建议归属、影响与待决条件。外层在验收本轮交付和派发下一任务前，逐项对照现有来源，按授权交给相应拥有者处理。

这一步保留了局部决定的范围。一次本地测试采用的做法留在任务设计里，项目级约定由工程指南维护。新说法与旧说法冲突时，两者的来源和适用条件一起保留，由有权决定的人裁决。保存过程中的失败也要明确交接，避免下一会话误以为文件已经更新。

### 用只读检查发现错误状态

[计划状态检查器](../../.agents/skills/evidence-delivery/scripts/plan_state.py)负责检查可以机械判断的条件：完成任务必须有非空执行证据，验收条目必须引用本任务的 CHECK，阻塞任务必须关联已知缺口，进行中或完成的任务必须满足前置完成条件。检查器只报告问题和结构候选，不修改计划。

这些条件有对应的[回归测试](../../.agents/skills/evidence-delivery/tests/test_plan_state.py)。其中一个测试把任务标成 `done`，再删除验收条目并保留空证据，要求检查失败。另一个测试在前置未完成时把后续任务设为 `in-progress`，要求报告依赖错误。只读测试还比较检查前后的文件字节，保证查看状态不会顺手改变状态。
