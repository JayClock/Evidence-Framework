# 反馈过载：Sensors 太多，Agent 不知道哪个信号重要？

## Bad Smell

反馈过载指的是反馈信号太多又没有分级，互相淹没，Agent 无法确定先修哪个。本项目里，一次任务收尾可能同时出现：Nx 的构建输出、Gradle 的 `UP-TO-DATE` 与缓存命中、ESLint 的警告、Guides 检查器的链接与格式结果、Skill 聚合回归、`plan_state.py` 的结构诊断，以及任务自己的 CHECK。这些信号的性质并不相同：有的是真实失败，有的是缓存命中，有的是环境问题，有的是历史记录。

如果不分级，Agent 会把“缓存命中”当成“刚跑过”、把“历史通过”当成“现在通过”、把“结构通过”当成“业务批准”；或者反过来，在一堆 lint 警告和几个测试失败之间随机挑选，改好一条又弄坏另一条。诊断信号是“看起来在动，但没有方向”。

## Solution

项目用“成功静默、失败完整、按证明力分级”的方式收敛信号。

### 成功静默，失败才输出

- [Guides 检查器](../../tools/guides/check.mjs)成功时只在 stdout 写一行摘要（文档数、链接数、错误数），失败时才把逐条错误写到 stderr 并返回非零退出码。
- `plan_state.py next` 只输出当前候选任务的 JSON；`verify` 输出结构与新鲜度事实，不输出解释性长篇。
- `AGENTS.md` 的 OpenWiki 受管块写明验证原则：选择能证明改动行为的最窄、最安静的检查，完整保留失败输出。
- `.evidence/checks/` 只保存紧凑运行清单（命令、退出码、时长、环境、输入摘要、日志 `sha256` 指针），不复制完整输出；约 1.0 MB 过期记录被清空，避免噪声稀释当前信号。
- `npm test` 串联应用、建模扩展、Skills 与 Guides 四段检查，任何一段非零都会让整体失败，不吞掉失败。

### 按严重程度分级

| 级别   | 本项目信号                                                                                 | 处理方式                                            |
| ------ | ------------------------------------------------------------------------------------------ | --------------------------------------------------- |
| 阻塞级 | 当前任务 CHECK 失败、编译/测试/静态分析失败、前置任务未 done、来源或前馈未就绪、环境不可用 | 修完才能继续；环境不可用记为阻塞，不伪装成业务失败  |
| 警告级 | 不阻塞的 Nx/Gradle 配置警告、缓存告警、语义存疑、既有失败的历史线索                        | 记录在 `observedEvidence` 或 `gaps`，不阻塞本轮通过 |
| 信息级 | 缓存命中、`UP-TO-DATE`、实际执行计数、文档/链接统计、历史检查记录                          | 作为上下文记录，不当作新运行或当前证据              |

真实记录里三层是分开写的：一次交付写明“28 个 Gradle task 中 13 个实际执行、15 个 up-to-date”，Nx 写明“35 个成功任务中 34 个命中缓存、backend build 实际执行”，并单独记录 Nx 的配置警告“未导致失败”。缓存命中是信息级，配置警告是警告级，实际执行的测试结果才是阻塞级依据。

三层的分界不只是严重程度，也是责任分界。阻塞级是 Agent 必须处理的；警告级由 Agent 给出事实，人决定是否继续完善；信息级只作上下文，通常可以直接转成前馈。再细分只会让 Agent 花力气判断级别，反馈过载换个形式回来。

### 按证明力分级

[README](../../README.md)要求区分**结构校验、运行验证和人工业务判断**：结构自洽、文件写入和命令成功不能替代业务批准。[测试指南](../engineering/testing.md)为每条命令配“实际覆盖 / 不证明什么”两栏，让每条信号只承担它证明的范围；[Guides 导航](../guides/index.md)进一步注明“`plan_state.py` 检查任务结构，不替代语义检查；`guides:verify` 检查文档结构，不证明任务就绪”。

分级之后，Agent 面对“Guides 通过、测试通过、身份缺口仍未解决”的局面，不会把绿色信号读成业务完成，也不会把仍然开放的 `GAP-IDENTITY` 误当成必须现在修的测试失败。

### 注意力纪律：任务只加载需要的信号

反馈过载的另一半来自上下文：把所有指南、全部任务、整个知识库一次性塞给 Agent，重要信号同样会被淹没。[Guides 导航](../guides/index.md)规定按任务选择必要前馈、同一来源只加载一次、长文件只读相关章节与实际源码符号；[交付流程](../../.agents/skills/evidence-delivery/SKILL.md)要求只加载当前任务的记录、直接前置产物和所引用的来源，不把完整知识库或任务图塞进上下文。任务记录集中在 `plan.yaml`，状态只在 `tasks[taskKey].status` 维护，也减少了重复信号。

### 分级同时是处理顺序

[交付生命周期](../../.agents/skills/evidence-delivery/references/lifecycle.md)的转向矩阵把优先级写成动作：编译或测试失败在当前文件范围修复并重跑；CHECK 不能证明业务预期时修订测试设计；任务拥有重复或缺失工作单元时停止实施、回到 Plan；来源改变时停止使用旧证据；缺业务事实时记录 gap 交回；环境不可用标记 blocked；全部通过时写入证据并停止。分级不只是显示顺序，也是修复顺序。

### 分级不等于隐瞒或降级

- 失败不得被改写成通过：不删失败测试、不改业务预期、不手改机器报告。
- 缓存命中不得描述为新运行；需要复验时使用 `--rerun-tasks` 或 `--skip-nx-cache`。
- 环境失败与实现失败分开记录，环境阻塞不伪装成业务测试结果。
- 历史检查只在输入、环境和依赖仍有效时作为有限的前置证据；旧记录清空后不再充当证据。
- 完整失败输出保留在工作流日志、PR body 或获授权的检查记录中，即使记录只保留摘要。

### 演进触发条件

- 目前没有统一的分级反馈规范文件，也没有把质量命令输出自动分级或静默的开关；分级依赖记录时的纪律（`observedEvidence` 的字段结构）与人工判断。
- Gradle/Nx 原生命令输出仍然较长，任务记录是人工收敛后的摘要；信号继续增多时，可以为常用命令提供 quiet 模式或统一的三级汇总入口。
- 三层划分是示例性的，尚未成为质量属性或规则字段；语义判断与人工评估无法自动分级，需要在任务内显式说明。
