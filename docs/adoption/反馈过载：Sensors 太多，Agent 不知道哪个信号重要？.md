# 反馈过载：Sensors 太多，Agent 不知道哪个信号重要？

## Bad Smell

一次检查结束，屏幕上有 Nx 缓存命中、Gradle 的 `UP-TO-DATE`、一条链接错误、几条配置警告、领域测试失败和 `plan_state.py` 的结构报告。如果把这些输出统称为“检查结果”，Agent 很容易修掉最显眼的警告，然后说主要检查都通过了。输出越多，越需要知道每条信号能说明什么。

Evidence 的验证入口本来就不止一个。项目质量命令检查不同技术部分，任务 CHECK 检查具体交付，计划状态工具检查结构，业务适用性还要有人对照来源。绿灯之间不能互相抵消：文档路径有效，不能解释领域断言失败；项目构建成功，也不能解决缺少生产身份依据的问题。

## Solution

### 先看会不会阻塞本次交付

当前任务的 CHECK 失败、编译失败、前置任务未完成，都会挡住相应工作。环境缺依赖同样让验证无法继续，但要记成环境阻塞，不能说成实现失败。业务事实或授权缺失，只阻塞依赖那个答案的任务；已有依据的纯领域工作不必跟着全部停下。

警告需要记录和判断，不应自动当作阻塞，也不能一概忽略。比如配置警告没有导致本次命令失败，可以说明它出现在哪里、是否影响当前结论；语义存疑则要看它是否触及本任务验收。缓存命中和 `UP-TO-DATE` 主要告诉我们构建工具做了什么，不能算成刚运行了新的测试。需要实际重跑时，[测试指南](../engineering/testing.md)给出了 Nx 跳过缓存和 Gradle 强制重跑的办法。

分级的依据是对本次任务的影响和信号的证明力，不是给每类日志贴一个永久标签。相同一条警告，换了环境或验收要求，处理方式也可能不同。

### 成功可以短，失败必须看得见

[Guides 检查器](../../tools/guides/check.mjs)成功只给简短摘要，失败返回非零退出码和具体错误。计划只读检查报告状态和候选，不替执行者写长篇结论。这样 Agent 不必在每次成功后重读一屏“已通过”，能把注意力留给当前任务的异常。

安静不等于隐藏。测试失败时要保留完整输出，至少让人追得回失败断言和环境条件；留存到获授权检查目录的记录则按[测试指南](../engineering/testing.md)保存命令、退出码、输入摘要与日志指针，不把整段历史输出再复制进当前上下文。历史记录可供追溯，只有输入、依赖和环境仍有效时才能充当有限前置证据。

信号的范围还取决于检查怎样运行。执行 `npm test` 后只记一个总退出码，会丢掉是哪一段失败；只记最后一屏“成功”，则可能漏掉某个子命令根本没开始。任务证据应保留与本次 CHECK 相符的具体观察，必要时给出日志路径和运行标识。把所有命令输出原样粘进 `observedEvidence` 也不可取，下一次阅读会被重复日志盖住关键断言。完整失败详情留在实际日志，任务记录指出如何找到它。

信号之间还可能发生表面冲突。`plan_state.py` 报告结构候选就绪，但工作树里已有未提交改动或接口输入变了，任务仍需要开工检查；Java 领域测试通过而端到端 HTTP 测试失败，应该先看失败在哪一层，不能拿领域绿灯盖掉 HTTP 红灯。环境失败时保留原样输出和环境依赖，修好环境再跑，别为了“把所有检查变绿”去修改业务预期。

还有一类输出根本不是自动裁判能给出的结论。`plan_state.py verify` 证明任务、CHECK、证据字段等结构关系满足规则，不证明 CHECK 测到了真正的业务结果。`npm run guides:verify` 能发现维护文档的链接或格式问题，不证明任务设计已经就绪。检查通过之后，仍要按[Guides 开工检查](../guides/index.md#任务开工检查)核对来源、边界与验收含义。

出现多条信号时，先处理影响当前 CHECK 和来源可信度的失败，再记录不影响本轮结论的警告与信息。修复后重跑受影响检查，不靠前一轮的绿灯作保证。如果发现 CHECK 自己写错了，就停下来修检查设计；若需要业务裁决，交回对应拥有者。靠压低日志级别换取整洁输出，只会让偏差更难发现。
