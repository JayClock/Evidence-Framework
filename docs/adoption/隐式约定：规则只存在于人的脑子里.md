# 隐式约定：规则只存在于人的脑子里

## Bad Smell

隐式约定指的是需求已经明确，但实现方式只存在于人的脑子里。本项目是多模块后端（domain / api / persistent 技术库与后续业务模块），模块之间存在依赖方向、数据归属、事务入口、命名映射与业务边界等约定；一旦没有写下来，Agent 会按通用方案处理——直连数据库、把业务规则写进 Resource、为每个 Context 建服务、顺手引入 JWT/RBAC 或某个数据库。症状是：评审时反复说“这里应该用我们约定的方式”，以及 Agent 迟迟无法完成，因为它在从头发明解决方案。

## Solution

项目把实现约定分层写进仓库，并用来源权威表裁决冲突。

### 入口层：AGENTS.md 只写不变量与入口

`AGENTS.md` 标题即“Evidence 项目宪法”，共 39 行（27 行正文加 12 行 OpenWiki 受管块），主要篇幅是**不变量**——本项目的红线：

- 保留 Nx、React/TypeScript、Spring Boot/Java；改变基线需要明确授权及架构决定；
- 业务事实来自 `.evidence/fm/`，API 设计来自 `.evidence/api/api.yaml`；软件范围、实现设计、当前代码行为不能相互冒充；
- 区分讨论、编辑和只读验证；未获授权不修改正式 FM/API，不提升审核状态；
- 不自动暂存、提交、回滚、重写 Git 历史或删除业务证据；
- 领域行为归实体、Description、Context 接口暴露的角色对象和拥有者关联；跨业务模块不得访问私有表和内部 Mapper；
- 行为变更必须有相应测试；只有实际通过才能声称完成。

入口文件不装细节：只声明不可协商的边界、事实来源、阅读入口与停止纪律，具体做法按需路由到项目基线与工程指南。

### 优先级与冲突裁决：来源权威表

[Guides 导航](../guides/index.md)的“来源与冲突处理”表为每类问题指定唯一权威位置，并列出“不可替代它的内容”（生成产物、过期 OpenAPI、代码现状都不算数）。冲突时的规则是：

> 先说明各自管辖范围及差异，停止受影响行动，交由相应拥有者确认；不能按读取先后、修改时间或“代码已经这样写了”裁决。

本项目的裁决顺序大致如下（由不变量与来源表共同表达，尚未编号成字段）：

| 优先级       | 本项目对应物                                                      | 说明                                             |
| ------------ | ----------------------------------------------------------------- | ------------------------------------------------ |
| 不可协商     | `AGENTS.md` 不变量                                                | 用户一句话不能覆盖；改基线要“明确授权及架构决定” |
| 用户指令     | 当前任务的明确授权：mode、目标、允许改动范围                      | 在宪法与来源约束内生效                           |
| 项目级约定   | `docs/engineering/*`、Guides 导航、架构基线                       | 适用所有模块与会话                               |
| 模块级决定   | `docs/architecture/modules.md`、`domain-mapping.md`、任务局部设计 | 记录拥有者、依赖、数据与事务边界                 |
| 通用最佳实践 | Skills 通用方法、范例索引                                         | 上下文冲突时让步                                 |

### 模块层权衡记录在哪里

- [架构基线](../architecture/overview.md)：技术决定表（工作区、后端运行时、smart-domain、持久化、HTTP、数据库）+ 依据链接；“改变当前技术基线时必须有明确授权，记录决定的来源、理由、影响范围与验证要求”。
- [模块边界](../architecture/modules.md)：技术库职责与允许依赖表；“FM 到业务模块”要求每项至少记录 Context/规则来源、公开能力、数据拥有者、依赖与禁止访问、事务入口五类信息。
- [领域映射](../architecture/domain-mapping.md)：概念到实现的映射表，并单列“不允许的推导”（例如 Context 不自动建服务、角色名不等于认证、请求受理不等于到账）。
- [任务模板](../../.agents/skills/evidence-task-planning/assets/task-plan-template.md)的“局部设计”一节把行为拥有者、数据归属、关联、HTTP、本地事务、外部集成逐项写清——相当于实例级 ADR。
- 实施计划把模块级取舍写进 `slicing.designItems` 与任务详情：订阅模块公开合同根集合与 `PaymentProof` 窄能力，移动支付模块保留协议、请求和机构结果，自动触发不新增对外 capability，固定标识与业务时间只用于 local/test。

### 决策框架而非规则清单

- [测试工序](../engineering/procedures.md)的选择矩阵按“变化或风险”选工序（边界与契约设计、领域行为、持久化适配、HTTP 契约、应用装配、前端交互、旅程验收），并明确“工序目录不是‘每个实体执行全部工序’的流水线”。
- [通用命名](../engineering/conventions.md)规定代码/API/SQL 的命名与中英文映射，冲突时“API 路由、关系名、参数和字段以已有契约为准，不为统一代码风格擅自更名”。
- [质量属性](../requirements/quality-attributes.md)拒绝填默认值：没有依据的权限、数据库、审计、多语言和集成方案必须先有专项依据，直接封住“顺手用 JWT/RBAC/某个数据库”的隐式约定。
- [模块边界](../architecture/modules.md)还划定影响范围：未知生产数据库只阻塞相应 SQL/并发验收，不阻塞已知纯领域设计。

### 固定技术 profile 与上游版本

- [上游依据](../../.agents/skills/evidence-task-planning/references/upstream.md)：固定 smart-domain 文档 commit `6ff4c1b9…`、核对日期与兼容范围 0.3.x；明确“main 是定位入口，不是可复现版本标识”。
- [设计规则](../../.agents/skills/evidence-task-planning/references/design-rules.md)承载固定技术 profile：模块化单体、no-service、MyBatis XML 映射、Jersey 子资源等。
- 这样 Agent 不需要“发明方案”：通用方法来自 Skill profile，项目取舍来自项目文件，二者都有来源。

### 演进触发条件

- 当前不单设决策记录目录：`AGENTS.md` 承担入口与不变量，架构三篇承担项目级技术决定，模块级取舍随切片 `designItems` 与任务局部设计记录；同一问题在两个模块出现不同答案时，再建立独立的决策记录目录并接入路由。
- 优先级通过“不变量 + 来源权威表 + 架构变更治理”表达，尚未逐条编号；出现裁决争议时可显式排序。
- 不变量多为结论式，未逐条附 Rationale；架构、模块、工序文档已写明依据，可按需要补齐。
- 固定技术 profile 与上游 commit 已有唯一来源；profile 变更必须同时更新设计规则、上游依据和规划回归，不能只在单个任务里临时放宽。
