# 隐式约定：规则只存在于人的脑子里

## Bad Smell

Agent 收到一个接口任务，写出 Resource、Service、Mapper 三层，把权限判断和业务状态转换都放进 Service。看上去很常见，甚至能通过接口测试，但在这个仓库里已经偏离设计。领域行为应由实体、Description、Context 接口暴露的角色对象和拥有者关联承担；API 与持久化分别依赖领域，不接管业务规则。Agent 不知道这些约定，就会用它熟悉的结构填空。

这种偏差很少以提问开头。实现者往往确信自己的写法合理，评审才听到“我们这里不是这么做的”。只靠评审者记住所有例外，下次换一个会话还会重来。

## Solution

### 约定要写在能找到的位置

[项目宪法](../../AGENTS.md)只放跨任务的不变量：保留 Nx、React/TypeScript、Spring Boot/Java，后端按模块化单体组织；未获授权不改正式 FM/API；不自动提交或删除业务证据；行为变更需要测试。这是每次开工都要读的入口，却不是一本厚重的实现手册。

具体取舍由[架构基线](../architecture/overview.md)、[模块边界](../architecture/modules.md)和[领域映射](../architecture/domain-mapping.md)承接。比如技术库的目录是技术分层，不能直接当业务模块边界；跨业务模块要通过进程内公开契约协作，不能读对方的私有表或内部 Mapper。Context 是领域中的角色与协作接口，并不意味着要给每个 Context 造一个 Service。Context 实现在适配层独立文件中经依赖注入提供，这些限制会直接影响代码放在哪里。

任务里的 `design` 再记录局部决定：行为拥有者是谁，数据由哪个模块保存，事务从哪里进入，哪些依赖可访问。这类决定若只留在聊天里，后续实现很容易退回通用模板。反过来，也不能因为某次任务做过某种选择，就把它当成全项目默认方案。

### 冲突时别靠“看起来更新”裁决

[Guides 导航](../guides/index.md)为业务、API、范围、架构、任务状态各自指定了权威位置。代码当前恰好这么运行，只能说明当前行为，不能替代业务事实。生成的 OpenAPI 或审核页即使更新较晚，也不能反过来修改 `api.json` 或任务状态。遇到两份文件说法不同，应指出差异及各自管辖范围，停下受影响的改动，请对应拥有者确认。

模块化单体里的“公开”也需要落实到调用方式。某业务模块需要另一个模块的用户信息，可以经它公开的 Context 或契约进入，而不是为省一次调用去查它的表。持久化适配器拥有自己的表和事务写入，领域对象处理状态判断；HTTP 层负责协议输入输出，不因为要组合一个响应就把计数规则挪进 Resource。一个接口看似只差几行代码，这些行放错地方，下一项需求会不得不沿着同一条错误依赖继续扩展。

计划中的局部设计要把这样的取舍说到能执行。例如涉及客户联系记录时，应指出谁拥有记录、完成判断读哪些周期内数据、其他模块怎样引用客户档案；若只写“新增客户联系功能”，代码很容易顺手生成档案 CRUD，而本次软件范围未必包含它。选择也要带适用条件：local/test 的固定值服务于可重复测试，不能凭它推出生产数据库或身份方案。

同样，角色对象不等于认证身份，付款请求受理不等于款项到账。这些名称看似接近，推断出的权限或资金状态却可能完全不同。缺少依据时，[质量属性](../requirements/quality-attributes.md)保留问题，而不是选一个常见的 JWT、RBAC 或数据库方案填上。未知生产数据库会影响相应 SQL 和并发验收，但不会自动阻塞已经明确的纯领域规则。

约定能不能用，最后还要看反馈。[测试工序](../engineering/procedures.md)按变化与风险选择检查，架构依赖由架构测试约束，业务判断由领域测试约束。文档负责把选择讲清楚，测试负责暴露实现偏差；测试无法判断的业务授权，仍要找有权决定的人。
