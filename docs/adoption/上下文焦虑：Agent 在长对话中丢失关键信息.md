# 上下文焦虑：Agent 在长对话中丢失关键信息

## Bad Smell

一个任务开始时，Agent 会对照来源检查输入，做完一小步就运行测试。对话拖长以后，同一个任务的收尾却变成“文件已经改好”，CHECK 没跑，前面的授权边界也不再被提起。单凭这种表现无法断定是上下文窗口造成的，但它已经足以让本轮完成声明失去可信度。

Evidence 的 FM、API 和计划文件都可能很长，实施过程还会不断积累日志、设计讨论和错误排查。若一口气做多个任务，把全部过程留在同一会话里，后面的执行很容易只记得刚看到的输出。这里不靠提醒 Agent “注意上下文”来保证质量，而是让单次工作有边界，并把恢复依据放进文件。

## Solution

### 一次只做一个获授权的任务

[项目宪法](../../AGENTS.md)把外层 PDCA 用来管理任务，内层 Guides、Action、Sensors、Steer 用来完成当前交付。每次只执行一个已授权且就绪的任务，完成后停止。恢复时再读 [Guides 导航](../guides/index.md)、任务计划、直接前置和本次来源，不能凭旧对话直接接着做下一个。

这个边界也保护验证环节：任务的 CHECK 必须在本次实施后按真实环境执行，结果进入 `tasks[taskKey].observedEvidence`。`status` 只在任务记录里维护，审核页可重建但不保存另一份进度。若在长对话末尾发现自己想跳过检查，应先停下来盘点已保存的进度和未完成事项，别为了凑一个完整交付而补写通过结果。

### 保存可以恢复的依据

这里没有额外建一个通用 checkpoint 文件。任务 `design` 与 Guides 记录局部取舍及来源，`observedEvidence` 留命令、退出码和实际观察，`gaps` 留未决问题、影响与下一步动作。访谈回答另有发现记录和词汇表，不能为方便恢复把业务原话改写成任务结论。

比如可信身份还没有决定，下次会话需要看到的是它阻塞哪些 403 验收，以及谁来补依据，而不只是“身份待做”。再比如上次 Gradle 输出了 `UP-TO-DATE`，记录应保留这是缓存相关结果，不能压成“Java 测试通过”。摘要越短，越要确保这类影响结论的限定没有丢。

保存依据时要分清两种“还没做完”。若测试还没运行，记录未执行，不填一个虚构的退出码；若测试已运行且失败，保存失败输出和当前改动，下一轮从失败处定位。只把会话压成“正在修复领域测试”会丢掉输入条件，也可能把仍未保存的工作描述成已经落盘的状态。停止前检查真正写进文件的是哪些，余下的向用户明确交接。

还有一类危险是跨任务惯性。第一个任务的测试通过后，Agent 不停止，直接照上一份上下文开始第二个任务，第二项的授权、来源和前置被上一项的结论替代。项目要求完成一个就停止，不是因为下一个任务一定难，而是每个任务的开工依据都要重新装配。若一个任务本身大到必须分段恢复，分段时也不能把 `status` 提前改成 `done`，只有本任务 CHECK 和项目质量检查真正完成后才能记录结果。

新会话恢复时，先看工作树已有改动，核对计划输入和来源新鲜度，再用只读工具检查任务结构和候选。候选出现不代表可以执行，还要核对授权、前置、局部设计、CHECK 与环境。历史证据即便完整，也只能在输入和依赖仍适用时提供有限帮助。这些步骤依赖仓库文件，不依赖上一轮聊天留下的一句“接着做”。

单个任务也可能读得太多。读长文件之前先定位章节，检查输出成功时留摘要，失败时保留完整诊断但不反复塞回上下文。确实需要跨很多资料的工作，可以在职责明确的分支分别处理，交接时带来源和产物，不把中间对话当作证据。如果当前任务还没验证完就必须停止，应如实交接未运行的 CHECK，等恢复后重验，不能先把状态改成完成。
