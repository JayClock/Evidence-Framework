# 上下文倾倒：信息过多，Agent 反而迷失

## Bad Smell

“先把仓库看一遍再动手”，听起来谨慎。真正动手时，Agent 已经读了整份 FM、接口设计、计划和生成 Wiki，却说不出当前任务需要哪条规则。资料没有少，相关信息反而被淹没。更糟的是，FM 中出现过的活动可能被误认成本次必须开发的功能。

Evidence 的资料有明确分工。业务事实由 `.evidence/fm/` 管，接口以 `.evidence/api/api.json` 为准，本次软件职责要看[范围](../requirements/scope.md)，任务授权与 CHECK 则在 `plan.yaml`。这些文件各有必要，但不是每次改一个映射就要把它们全部读进会话。读得多不能替代读得对。

## Solution

### 从任务定位到必要来源

[Guides 导航](../guides/index.md)先按工作类型列出阅读路线。动后端领域行为，就核对模块边界、领域映射、后端规范和相关规则场景；做 API，就读对应能力和 API、安全规范；维护前馈文档，重点看路由、模板与验证规则。长文件只读相关章节，同一来源不重复加载。没有读到的部分不声称已经核对过。

恢复实施时，从当前任务记录、直接前置产物和 `sourceRefs`、`procedureRefs` 指向的文件开始。引用能帮助定位，但不能把未列入引用的真实风险排除掉：代码或指南发生了影响本任务的变化，仍需重新检查新鲜度。`docs/engineering/examples.md` 提供真实范例的入口与适用限制；要复用时回到源码和测试，不把索引当可直接复制的实现。

计划中有一份 API 规划输入投影，只挑出这次授权消费的能力。投影里没出现的能力，仍留在权威 `api.json` 中，不能说它们被删除；投影的摘要如果与权威文件对不上，也不能继续把它当最新输入。这类压缩对规划很有用，前提是清楚它压掉了什么，以及如何回到原始契约。

查找时还要区分定位与消费。搜索 `context.subscription` 可以找到几处可能相关的路径，不表示这几处都已读过，更不表示搜索结果就是业务定义。准备改某个领域行为，要回到对应规则与场景；准备验证某个接口，要回到 `api.json` 中那项能力的请求和响应约定。只读索引能省下翻文件的时间，却不能取代对承重段落的逐字核对。

按需加载也不是把阅读范围写死。如果当前任务原计划只碰 domain，结果发现领域对象构造必须借用另一个模块的内部 Mapper，就得停止检查模块边界与任务设计，而不是坚持“sourceRefs 没列它，所以不看”。同样，CHECK 执行失败后可以按错误定位相关测试和源码，不能为了守住初始的阅读清单忽略新证据。预算约束的是无目的倾倒，不是调查必要问题。

### 哪些内容不能随手压缩

一段很长的执行日志可以变成命令、退出码、运行环境、输入摘要和日志指针，前提是失败详情还能找回。任务的不变量、验收的具体 `expected`、gap 的影响与下一步动作却不能概括成“按规范处理”。决定行为和停止边界的句子被压掉，再短的摘要也没用。

同样，OpenWiki 是可选索引，不是必读背景，更不是源码和测试的替身。生成页能告诉你去哪里查，源文件才能回答当前行为到底是什么。遇到来源冲突时，不能按哪份更短、更像总结来选择；应分别核对权威位置，停下受影响的行动。

可以用一个实用的标准控制读取范围：如果不给 Agent 这段材料，它会做错当前任务中的哪个决定？答得出，就读原文相关部分；答不出，先保留路径。执行遇到新的缺口再向内展开，不需要提前把整个知识库变成一次对话的负担。
