# 跨会话状态丢失：每次对话 Agent 都不记得上次的事

## Bad Smell

访谈里用户确认 local/test 可以用固定标识，下次会话接手实施的 Agent 只看到一句“使用固定值”，可能把它写成生产生成规则。又或者这轮已经发现可信身份来源不明，下轮只看见接口测试绿色，顺手宣布权限验收完成。聊天里说过的话没有消失，但离开那段对话，接手的人很难知道它属于哪类决定。

Evidence 同时有访谈、建模、需求、规划和交付工作。每个环节能写入的文件不同，也有不同的确认权限。用一份万能的“会话记忆”保存所有结论，反而会把用户原话、暂时的理解和正式授权混成一层。恢复的关键是让信息进入它本来归属的文件。

## Solution

### 用户说的话先存成可追溯材料

访谈时，问题、回答原话和来源先写入 `.evidence/discovery.md`。明确术语当轮按 FM 方法沉淀到 `.evidence/glossary.json`：尚未建模的术语保存定义，已有 FM 概念只引用模型，不复制一份名称与含义。记录与术语任一保存失败，就停下来说明哪部分已保存、哪部分没有保存。口头理解不能代替写入结果。

订阅业务的发现记录就区分了 local/test 固定标识与生产身份问题。前者可以成为相应测试的夹具，后者仍等待依据。访谈得到这个回答，并不自动允许修改正式 FM JSON、API 或扩展开发范围；拥有者还要按授权更新对应来源。下次若收到更正，应保留原回答及影响，核对适用场景，而不是让“更新的一句话”无条件覆盖旧记录。

### 实施结果进入任务，不进入聊天摘要

任务执行前，`plan.yaml` 里的 `guides`、`design` 和来源引用说明本次允许改什么、为什么这样设计。执行后，唯一状态在 `tasks[taskKey].status`，真实命令与观察写在同一任务的 `observedEvidence`。未解决的问题进入 `gaps`，指明阻塞哪些工作、由谁提供下一步依据。`review.html` 只展示这些数据，不能成为另一份记忆或批准记录。

可信身份是个很具体的交接例子。可以说明 local/test 主链的哪些行为已经测到，也要说明生产 403 和他人实例拒绝还缺什么。这样下次会话不会因为看到某项测试通过，就把所有权限问题一起划掉。反过来，也不会因一个局部 gap 停掉无关的领域设计。

有些反馈还没有资格进入正式业务模型，但仍值得保存。例如用户在访谈中纠正了一个词的适用范围，应先留原话、来源和下游影响；若尚无模型编辑授权，不能为了下一次会话好读，就直接改 FM。实施中发现某项接口请求体与契约对不上，先留差异和复现条件，再判断是实现错误还是接口设计需要拥有者确认。交接的价值不在于给每件事贴一个“已解决”标签，而是让接手者知道哪些观察还等待裁决。

任务自身的局部决定也不能偷换为全局习惯。一次 local/test 使用固定夹具，下一次执行生产相关任务时要重新核对输入来源；一次 SQL 检查在 H2 上通过，只能说明那次适配测试的范围。把这种限定连同决定的理由存下来，比保存一长段会话总结更能防止误用。若决定需要改变模块所有权或任务依赖，应回到 Plan 调整，不能只改本任务备注继续实施。

代码和文档有冲突时，任务记录不能写一句“以实际代码为准”自行裁决。业务事实回到 FM 与发现记录，HTTP 契约回到 `api.json`，软件职责回到范围与故事，代码说明的是当前实现行为。先说明差异，暂停受影响的工作，再找对应拥有者确认。

### 新会话从仓库重新开工

接手时先读 [项目宪法](../../AGENTS.md)和 [Guides 导航](../guides/index.md)，查看工作树，核对来源、计划输入与直接前置，再读取当前任务及其引用。只读状态检查可以帮助发现没有证据却标成完成、没有 gap 却标成阻塞等结构错误；它不替人检查业务语义与环境新鲜度。旧命令的退出码只有连同输入和环境看才有用。

结束本轮前，要清点新收到的回答、执行中发现的差异和做出的决定：有权限的写进相应文件，没有权限或写入失败的明确交接未保存。下一次会话不必“记住上次聊了什么”，但必须知道上次真正留下了什么。
