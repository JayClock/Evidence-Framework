# 前馈痴迷：Agent 做完就交，从来没人检查

## Bad Smell

Agent 又把业务规则放进了 Resource。评审意见是“再给它写清楚一点”，于是入口多了提醒，后端指南多了一段，任务模板也加了同一句话。下一次生成换了个位置犯错，检查仍只能靠评审者看到。规则写得越来越细，结果有没有偏离却始终没有独立信号。

在 Evidence，前馈确实有用。[项目宪法](../../AGENTS.md)规定领域行为归实体、Description、Context 接口暴露的角色对象和拥有者关联；[后端规范](../engineering/backend.md)说明层间依赖与适配边界。它们让 Agent 开工前知道怎么做。但指南能提高做对的机会，不能证明提交的实现就遵守了这些约束。

## Solution

### 写新规则时，也写下如何发现违例

[测试指南](../engineering/testing.md)要求行为变更有相应测试。计划里的 CHECK 从具体输入和可观察结果出发，写出正常、边界与反例；`acceptanceCriteria` 再用具体期望值引用 CHECK。这一步通常比写“必须正确处理异常”费力，因为要确定异常输入是什么，失败后哪些状态不能变化。费力之处也有价值：如果没人说得清预期，Agent 就算看过再多规则也没法自行验收。

不同约束适合不同反馈。模块依赖能用架构测试拦截，Java 格式交给 Spotless，前端静态问题由 ESLint 检查，文档链接和已知过期表述由 Guides 检查器处理。领域里的周期边界、计数规则或失败不变性，要靠对应领域测试。要判断一条业务活动是否属于本次软件范围，仍需对照需求和授权，不能拿脚本替人决定。

因此新增约定时，先写清楚会出现什么可见的错误，再选检查方式。如果只能进行人工复核，也把要看的来源与判断问题写出来，别伪装成自动测试覆盖。`npm run guides:verify` 通过，只说明维护文档满足它能检查的结构条件，不证明业务规则正确。

反馈的设计还得跟着交付对象走。做持久化时，只检查 Mapper 方法能返回对象不足以证明事务回滚、XML 映射和真实表关系；做 API 时，只测试 Java 方法返回值不足以证明请求的序列化和 HTTP 状态。仓库把纯领域、独立 HTTP、真实 H2/MyBatis/Flyway 以及应用装配分成不同测试边界，[测试工序](../engineering/procedures.md)按本次变化和风险选用，不要求每个实体机械地走完所有层。少一个本来必须有的边界，检查再多也会留下盲区。

也有难以变成测试断言的判断。比如一份任务切片是否让两个业务模块互相读取私有数据，部分依赖可以通过架构检查发现，但切片本身是否合理，仍要对照 FM、范围和模块设计审查。此时把审查问题、要看的来源和可能导致停止的条件写明即可。把“人工评估”写成一个没有输入也没有观察结果的假 CHECK，对交付没有帮助。

### 检查失败后要能转向

假设 HTTP 测试通过，但领域测试发现联系记录跨周期被算进完成数。该回到领域行为与其测试，不是再给 Resource 加一段提示。若 CHECK 自己没有包含跨周期输入，应补检查设计；若来源中根本没有确定周期定义，则停止受影响任务，交给业务拥有者澄清。三种情况对应不同的行动，统称“继续改提示词”会误导修复方向。

检查结果还得如实保存。命令、工作目录、退出码、观察和未覆盖范围应在交付记录里说清；缓存命中与实际执行分开标明。`plan.yaml` 的 `observedEvidence` 保存任务的真实结果，不预填，不拿历史绿灯冒充本次通过。失败输出也不能因为太长就只剩一个“未通过”。

前馈仍需维护，尤其当错误来自不清楚的来源路由或设计边界时。只是每加一条说明都应问：下次出现同类偏差，会在哪里看到？如果答案仍是“等评审碰到”，这次修改只让文档变厚，没有改善验收。
