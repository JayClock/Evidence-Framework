# 交互发现评测：上下文识别与业务引导

`evals.json` 是本地 Evidence 引导方式的评测输入，不是业务来源或已批准模型。它与 `.agents/skills/evidence-fm/evals/` 中的完整 FM 生成基准分开：首轮通常应停在问题等待，不能因未生成 YAML 判失败。不要将此文件交给只检查完整模型的 `run_modeling_evals.py`。

## 覆盖与观察

三十八个案例覆盖合同履约、领域、渠道、混合依赖及低信息输入。所有路线采用“类型展开 → 追溯业务来源 → 保存依据／缺口 → 必要时逐问与回放”的同一循环，不将类型属性或疑似派生作为免除／启动来源追溯的开关。

- 第1–14例保留上下文识别、责任方向、简单胶水、时间结构和名称／分析分离；第15–23例检查既有规则复用、真实歧义、跨回答覆盖及各路线的业务边界。
- 第24–25例区分时间结构与业务来源：仍不强索公式或生产日期，但必须保留和按影响澄清来源未知。第11、14例同步收窄旧版“不因缺公式追问”的表述；不再把类型展开当作期限已解决。
- 第26–34例保留六类时间的展开、签约／采信／原事件争议、派生候选及明确非派生输入；这些都纳入同一来源追溯过程，不另设时间／派生流程。
- 第35–38例覆盖非派生金额来源未知、已接受报价的引用与历史版本、类型／机器通过不能关闭期限问题，以及纯领域关键属性的来源未知。

每项包含输入、预期交互及人工检查点，不提供 Agent 可冒充的人工答案。

确定性回归 `discovery-prompt.spec.ts` 验证固定系统指南真实加载、恢复提示与合法检查点；`discovery-context.spec.ts` 和 `discovery-session-context.spec.ts` 验证有界包、长输入补读、1000轮请求级投影及会话原文保留；`discovery.spec.ts` 验证工具停止、人工回答、更正、来源与共同 Gate；`discovery-resolutions.spec.ts` 验证稳定 gapKey、防重复、跨回答解决关联、原文摘录、失效／撤回、停止控制和多入口一致展示。它们不调用语言模型，也不能证明语义识别或提问质量。

### 时间交互覆盖索引

| 类型                     | 直接展开／已知规则复用 | 不得掩盖的真实缺口                            |
| ------------------------ | ---------------------- | --------------------------------------------- |
| RFP／Proposal            | 10、25                 | 9：明确无期限与本地约束冲突；23：接受条款冲突 |
| Fulfillment Request      | 15、34                 | 16–17、24、33、37：规则或确定依据未知／冲突   |
| Contract                 | 26                     | 27：何种行为构成签约影响价格版本              |
| Fulfillment Confirmation | 28                     | 29：扣款或到账的采信冲突影响按时判断          |
| Other Evidence           | 30                     | 31：原事件时间缺失影响佣金归属                |

第32–38例另外观察：所有关键数据是否都核对来源，而不是等出现计算线索。已知直接记录或引用不重复问；来源性质未知先核实确定依据，不强行选输入或派生。人工否定派生关系后不再换题号索取公式，但仍保留其已明确业务来源。

按同一输入分别观察首轮及消化／重载后的接续，不以列出时间字段就认定 Agent 交互正确。正例不能凭空制造时间争议；反例不能靠自由 timestamp 参数、类型知识或摘录存在就关闭真实阻塞。

## 实际运行方法

1. 使用独立临时项目副本、受信任的项目扩展及测试用 gh 账号；不要重置真实项目运行。材料均为合成输入，不放生产敏感数据。
2. 在副本启动 Pi，运行 `/evidence-init <某条 prompt>`，按提示执行 `/evidence-run`。保存实际会话和提问结果到副本外的评测工作目录；不要伪造回答或修改状态。
3. 检查候选及来源、问题是否具体且相关、有无无依据推断、是否遵循人工等待。需要资料时停下来是正确结果，首轮没有 FM 不算失败。
4. 由真人逐项检查 expectations，并记录 actual、passed/failed/not-run 和具体会话依据。没有调用 Agent 的案例标 not-run，不填写通过率或生成模拟成功结论。
5. 对比旧版时，分别使用旧版与新版的独立副本、同一模型/思考级别和相同输入；不要在一个会话中让模型记住另一版的答案。至少多次运行后再讨论稳定性；人工可盲评两版提问。

## 多轮接续检查（人工执行）

选择合同案例继续检查以下步骤，预设文本仅由测试操作者通过 `/evidence-answer` 输入，不交给 Agent 冒充人工回答：

- **逐问自适应**：每轮只有一个核心问题，而不是将多个子问题捆绑成一题。回答后自动启动消化，先保存候选与合同权责视图，再说明变化及下一缺口；下一问必须受回答影响，不是依次弹出预排问题。
- **一次补充多项信息**：在回答计算依据时主动补充账期。应同时吸收，不再重复询问账期；不强制用户将一段回答拆成多次输入。
- **历史问题**：在当前运行中回访先前问题。应先消化，不要求全部回答，不自动排除；已被其他有效事实充分覆盖的未答／未知题可通过 resolution 关联解决，仍未知的保留，不使用旧快照作为兼容测试。
- **跨问题覆盖**：先暂缓一条题，再由操作者在另一题回答中同时提供两项事实；Agent 应引用该回答的 A-ID 与逐字摘录，解释覆盖关系，不要求按原题重答、不生成新 A-\*。随后人工更正提供依据的回答，旧关联应失效；更正、撤回和重建只追加记录，问题原文不变。人工停止时仍不可自动恢复问答。
- **缺口防重**：针对同一对象和事实维度改写问法，检查沿用原 gapKey／Q-ID；不能通过更换 key 绕过暂缓或已知事实。不同对象或不同事实维度仍可提出新问题。程序只验证标识与部分文本重复，任意语义改写需要人工检查。
- **请求—确认凭证候选**：先展示所属约定、履约项、谁向谁提出要求、要求／依据、期限和谁提供什么确认凭证，再问一个缺口。检查双方角色是否正确、不同履约中的权责能否互换、箭头是否被误解成资金方向；当前问题须对应目标合同／履约，不能串到另一合同。未知内容显示待明确，异常仅在有依据时形成新履约。问答主界面不堆叠工程阶段、Gate 或问题统计。
- **确认语义**：交稿案例不得默认编辑验收；已明确需要验收的案例不得删除验收。外部支付回执可承担确认凭证，不把其提供者硬塞为合同第三方，也不从权利方／义务方推导审批人。只有凭证名称时保留名称，提供方仍待明确；不因“确认”一词强加人工审批阶段。
- **名称与分析分离**：用第14例检查每个候选的 label 是否为业务短语、description 是否保留长分析，标题与请求箭头是否只出现短名称；不重复“外部系统不是合同一方”等建模纪律，不因期限未知抹去已明确的支付义务。机器回归用长描述夹具验证卡片、菜单、完整原文及名称更正的追加追溯；不能替代实际模型输出质量评测。
- **低信息／无合同**：没有合同依据时保持空关系，不为界面完整而造合同、角色、期限或确认凭证。
- **未知／跳过**：对阻塞期限或标准选择未知或跳过，自动整理后不得仅凭未知／跳过声称阻塞已解除、补造默认值或换 Q-ID 重问跳过的缺口；确有其他充分事实时才可追加有摘录的 resolution，不篡改人工状态。
- **时间结构与来源分离**：六类均展开自身必备属性，再追溯业务来源，不补请求区间、不互换时间、不强索生产日期或公式。用第24–25、37例检查保留已知类型和未知来源；影响当前判断时逐问，不用字段或机器通过关闭业务缺口。第15–17、26–31例继续覆盖已知复用及真实规则／采信冲突。`.agents/skills/evidence-fm/tests/test_evidence_times.py`（仓库相对路径） 验证非派生时间的结构、lineage、编译和实例约束，不证明业务来源充分。
- **期限历史题**：在第24例由真人结束本轮或暂缓后，观察整理是否保留未明依据，不得只引用“规定时间内付款”及类型知识就生成 resolution。之后由操作者主动补充第15例的规则事实或第34例的逐笔约定事实；已有事实充分覆盖原题时才可关联解决。重载后复用原来源、gapKey／Q-ID，不改旧题、不代填答案、不自动恢复停止／暂缓。
- **直接与引用来源**：用第35、38例检查没有计算线索时仍追溯来源；用第36例检查保留原报价的金额、币种、版本和当时可见性，不用最新值回算、不索取存储字段。候选说明保留部分已知，来源的业务区分不能变成新 Schema 或预排问卷。
- **具体回答**：补充真实约定。应自动消化最新 A-ID，推进该履约项的下一个必要缺口，不重开范围问卷。
- **主动结束**：从与场景同级的入口结束本轮；之后补答不自动恢复提问。已有信息足够时可保存并停止，不为一问一答强行凑题。
- **更正**：用原 Q-ID 更正。旧回答保留、旧草稿/定稿失效，不再引用旧 A-ID 支撑明确事实。
- **范围分歧**：明确指出某个已排除活动其实影响当前结果。应核实具体依赖，不自行扩大到整个企业，也不忽略对结果有影响的责任。
- **保存和重载**：追加发现后 `/reload`，再 `/evidence-run`。应由日志重建当前候选和案例继续，不提前进入统一语言，不新增固定查询工序。
- **长会话与上下文**：多轮问答后恢复或压缩，检查任务消息不再重复方法全文、已消化回答不反复内嵌，旧发现轮次只从模型请求中收束而不删除磁盘会话。超长／多项新回答必须有明确补读动作；切换讨论对象按明细行号读取，不把摘要遗漏当作业务排除或已解决。记录实际模型输入 token 与语义遗漏，不将合成字符预算当成真实模型质量或整个会话永不溢出的证明。
- **只追加解释**：只提交本轮变化；已有对象的更正／撤回引用当前 D-ID，不重交整份模型、不把遗漏当删除。检查原始记录未改写、当前视图反映新解释、历史依据仍可追溯；D-ID 不能充当独立业务来源。当前视图缓存可重建，但不是新的凭证事实源。

## 验收边界

实际模型、账号、时间、执行次数、输出与人工评价都应随评测结果另存。此目录只提供输入和方法，没有声称已完成真实 TUI、Agent A/B 评测、具名业务确认或 UAT。业务专家审核、Schema 校验、单据模拟与 Modeling Gate 仍是不同结论。
